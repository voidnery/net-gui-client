**Статус:** ✅ Завершён. Обходной путь найден — драйвер не нужен вообще
**Итерация:** И-0
**Дата:** 2026-08-24
**Контекст:** после отрицательного результата [E1](E1-windivert.md) собственный драйвер стал единственным путём к `Redirector`. Заказчик не готов к расходам на EV-сертификат — задача переформулирована с «сколько стоит» на «как обойтись без этого».

## Часть 1. Факты о подписи драйверов

### Обязательность EV-сертификата

| Факт | Метка |
|---|---|
| Для регистрации в Microsoft Partner Center (Hardware Dev Center) и для submission на attestation аккаунт **обязан** иметь привязанный **EV-сертификат**. Стандартный код-сайнинг не принимается | ✅ Актуальная документация Microsoft, обновлена в ноябре 2025 и позже |
| EV-сертификат должен быть **действителен на момент submission** | ✅ |
| Отдельные submission можно подписывать обычным Authenticode-сертификатом, но он должен быть зарегистрирован в аккаунте — а сам аккаунт всё равно требует EV | ✅ |

### Стоимость (2026)

| Позиция | Цена |
|---|---|
| EV Code Signing — Sectigo / Certera / Comodo через реселлеров | от **$280/год** |
| EV Code Signing — DigiCert | **$300–580/год** |
| **⚠️ С 15 февраля 2026 максимальный срок действия сертификата — 1 год** | Многолетние скидки более недоступны при поставке с токеном |
| Аппаратный токен FIPS 140-2 L2 / CC EAL4+ | Обязателен с июня 2023, входит в поставку 1-летних сертификатов |

**Итог:** не разовые $280, а **рекуррентные $280+/год**, бессрочно, пока продукт живёт.

### Проверенные обходные пути — все закрыты

| Путь | Результат |
|---|---|
| **Azure Trusted Signing** (~$10/мес) | ❌ **Не поддерживает подпись драйверов Windows.** Подтверждено Microsoft Q&A. Официальных планов добавить нет |
| **SignPath Foundation** — бесплатная подпись для OSS | ❌ Выдаёт сертификаты уровня **OV**, а Partner Center требует **EV**. Наш GPL-3.0 даёт право на программу, но не на нужный уровень |
| **Cross-signing** | ❌ Убит политикой апреля 2026 |
| **Self-signed / test-signing** | ❌ Требует от каждого пользователя отключения проверки подписи. Неприемлемо для продукта |

**Вывод части 1:** дешёвого или бесплатного пути к подписи kernel-mode драйвера в 2026 году не существует. Минимальная планка — $280/год рекуррентно.

### Сравнение с WinDivert

| | `wintun.sys` | `WinDivert64.sys` |
|---|---|---|
| Подписант | **Microsoft Windows Hardware Compatibility Publisher** | 成都密思听科技有限公司 |
| Издатель | **Microsoft Windows Third Party Component CA 2012** | Sectigo Public Code Signing CA EV R36 |
| Тип | ✅ **Attestation / WHCP** | ❌ Обычный Authenticode |
| Сертификатов Microsoft в цепочке | ✅ есть | ❌ ни одного |
| Отношение подписанта к проекту | ✅ WireGuard LLC — авторы | ❌ посторонняя организация |

Это наглядная иллюстрация разницы между «драйвер подписан» и «драйвер подписан правильно».

### ⭐ Главное следствие

**Wintun поставляется в виде подписанной Microsoft DLL с вложенным драйвером. Нам не нужно ничего подписывать, чтобы поднять TUN-адаптер.**

А в TUN-режиме sing-box поддерживает правила по процессам **нативно** (`process_name` / `process_path`), без какого бы то ни было драйвера с нашей стороны.

## Часть 3. Обходной путь

Из частей 1 и 2 следует переоценка варианта **V3** («всегда TUN, режимы как пресеты политики»), отвергнутого в [Фазе 1](../01-analysis.md) §4.4.

### Признание ошибки Фазы 1

Я отверг V3 с формулировкой: *«убивает главное преимущество лёгких режимов — работу без админ-прав»*.

**Это было неверно.** Преимущество исчезло в тот момент, когда мы приняли [ADR-006](../adr/ADR-006-privilege-security.md) — службу под LocalSystem, устанавливаемую инсталлятором. Админ-права стали **разовой стоимостью установки**, а не платой за каждый запуск. Лёгкие режимы к моменту принятия решения по Q3 уже не давали того преимущества, ради которого я их защищал.

### Что остаётся реальным минусом TUN-always

- Постоянный overhead: весь трафик проходит через userspace-стек, даже когда default action = `DIRECT`.
- Постоянный, а не эпизодический риск конфликта с другими VPN-клиентами (R11).
- Постоянно повышенный риск R5 («интернет пропал»).
- Нагрузка на CPU и батарею ноутбука.

### Уточнённое предложение: адаптивный выбор механизма

Механизм перехвата выбирается **автоматически, по тому, что требуют текущие правила**, а не жёстко привязан к названию режима:

| Ситуация | Механизм | TUN поднят? |
|---|---|---|
| Режим «Прокси» или «Системный прокси», правил по процессам **нет** | Локальный listener (+ системные настройки прокси) | ❌ Нет — легко и без риска |
| Любой режим, правила по процессам **есть** | TUN, `defaultAction = DIRECT`, правила уводят в `PROXY` | ✅ Да |
| Режим «Полный туннель» | TUN, `defaultAction = PROXY` | ✅ Да |

**Что это даёт:**
- Требование **T3 выполняется полностью** — правила по приложениям работают во всех трёх режимах.
- Драйвер собственной разработки **не нужен**. Стоимость подписи — **$0**.
- Риски R3 (антивирусы), R13 (сроки подписи), R14 (BSOD) — снимаются или резко снижаются.
- Лёгкие режимы остаются лёгкими, **когда могут** — пока пользователь не задал правил по процессам, TUN не поднимается.
- Из проекта уходит целый компонент: разработка драйвера, тестовый контур с kernel debugging, submission, сопровождение подписи.

**Чего это стоит:**
- Как только появляется хоть одно правило по процессу, лёгкий режим перестаёт быть лёгким. Это должно быть **честно показано в UI**, а не происходить молча.
- Понятие «режим» смещается: из «механизма перехвата» в «пресет политики». Терминология в интерфейсе должна это отражать.

## Рекомендация

Принять адаптивную схему, `Redirector` вынести за пределы MVP.

Абстракция `Redirector` из [ADR-002](../adr/ADR-002-traffic-interception.md) **сохраняется в коде** — интерфейс остаётся, реализаций ноль. Если в будущем появится бюджет на EV или Microsoft разрешит подпись драйверов через Azure Trusted Signing, бэкенд `wfpcallout` добавляется без изменения архитектуры.

Единственный сценарий, ради которого драйвер остаётся объективно нужен: пользователь хочет правила по приложениям и при этом принципиально не хочет поднимать TUN. По совокупности — не стоит $280/год плюс месяцы разработки.

# ADR-004: Контракт управления — gRPC поверх named pipe

**Статус:** Принято
**Дата:** 2026-08-24
**Решает:** §10.3 и §10.4 (принцип P1) документа [01-analysis.md](../01-analysis.md), требование T9
**Связано с:** [ADR-006](ADR-006-privilege-security.md) — безопасность канала

## Контекст

Разделение на непривилегированный GUI и службу LocalSystem обязательно (ADR-006). Значит между ними нужен канал. Требования к нему:

- **Двунаправленность с потоками.** Служба должна стримить в GUI статусы, метрики трафика, логи, события failover — не по опросу, а push'ом.
- **Мультиклиентность.** Клиентов минимум два (`net-gui`, `net-cli`), в перспективе третий — web UI для Linux server edition (T9).
- **Версионирование.** GUI и служба обновляются независимо; старый GUI не должен ломаться о новую службу.
- **Дешевизна для потока метрик.** Метрики идут постоянно, пока открыто окно.
- **Принцип P1.** API — продукт первого класса, а не деталь реализации GUI. Любое действие GUI выражается вызовом API.

Из исследования: sing-box начиная с 1.14.0 сам предоставляет gRPC-сервис для наблюдения и управления, включая gRPC-Web и WebSocket-транспорт для двунаправленных стримов. Hiddify использует gRPC как control interface к ядру.

## Решение

**gRPC поверх Windows named pipe**, контракт описан в `.proto` и версионирован.

- Транспорт: named pipe с явным DACL (детали — ADR-006). На Linux/macOS — Unix domain socket, тот же `.proto`.
- Схема: единый пакет `proto/` в репозитории, кодогенерация для Go; для будущего web UI — тот же контракт через gRPC-Web.
- Версионирование: поле версии в handshake; политика — аддитивные изменения без ломки; несовместимость даёт понятную ошибку «обновите клиент», а не таймаут.
- Разделение на сервисы: `SessionService` (подключение, режимы), `ProfileService`, `RoutingService` (правила, тестер), `FailoverService` (цепочки, история), `DiagnosticsService` (логи, экспорт), `EventService` (единый стрим событий).

## Рассмотренные варианты

### A. gRPC поверх named pipe ✅

| Измерение | Оценка |
|---|---|
| Сложность | Средняя |
| Двунаправленные стримы | **Нативно** |
| Версионирование | **Встроено** (protobuf) |
| Мультиязычность клиентов | **Высокая** |
| Накладные расходы | Низкие (binary) |

**Плюсы:** стримы из коробки; protobuf даёт схему, кодогенерацию и правила совместимости; тот же контракт работает через gRPC-Web для будущего web UI; sing-box уже говорит на gRPC — единый подход в проекте; смена GUI-технологии не затрагивает службу.
**Минусы:** тяжелее JSON-RPC; кодогенерация в сборке; gRPC поверх named pipe требует кастомного диалера (не проблема, но и не из коробки).

### B. JSON-RPC 2.0 поверх named pipe

**Плюсы:** проще, без кодогенерации, читается глазами при отладке.
**Минусы:** стримы приходится изобретать (long-polling или свой фрейминг); версионирование вручную; схема не формализована → расхождения клиента и сервера ловятся в рантайме, а не при сборке; для потока метрик текстовый формат дороже.

### C. Собственный протокол «длина + JSON»

**Плюсы:** минимум зависимостей, полный контроль.
**Минусы:** пишем сами всё, что gRPC даёт бесплатно: фрейминг, мультиплексирование, отмену, дедлайны, версионирование. Классический случай изобретения велосипеда в месте, где он не даёт преимущества.

### D. HTTP REST на localhost

**Минусы:** локальный TCP-порт — это дополнительная поверхность атаки, доступная любому процессу в системе. Named pipe с DACL строго безопаснее. Отвергнуто по соображениям ADR-006.

## Анализ компромиссов

**Сложность против возможностей.** JSON-RPC (B) на старте проще на день-два. Но стрим метрик, стрим логов и push-события failover — это три места, где пришлось бы городить своё. gRPC окупается уже на первой из них.

**Локальный порт против named pipe.** REST (D) удобнее отлаживать, но открывает канал управления привилегированной службой всем локальным процессам. С учётом прецедентов из RQ8 это неприемлемо.

## Последствия

**Становится проще:**
- Принцип P1 выполняется автоматически: `net-cli` — просто второй gRPC-клиент.
- Linux server edition получает готовый API-слой без переделки.
- GUI можно заменить целиком, не трогая службу.
- Схема в `.proto` служит документацией контракта.

**Становится сложнее:**
- Кодогенерация в сборочном конвейере.
- Нужен кастомный диалер gRPC поверх named pipe.
- Изменения контракта требуют дисциплины совместимости.

**Что придётся пересмотреть:**
- Если web UI для server edition потребует прямого доступа из браузера — понадобится gRPC-Web прокси или отдельный HTTP-фасад поверх того же контракта.

# ADR-006: Разделение привилегий и безопасность IPC

**Статус:** Принято
**Дата:** 2026-08-24
**Решает:** §8 документа [01-analysis.md](../01-analysis.md), RQ8, риск R4 (критический)
**Связано с:** [ADR-004](ADR-004-ipc-contract.md)

## Контекст

Приложению требуются права администратора: установка драйвера Wintun, создание TUN-адаптера, изменение таблицы маршрутизации, WFP-фильтры, машинные настройки WinHTTP-прокси. Запрашивать UAC при каждом запуске — неприемлемый UX.

Стандартное решение — служба LocalSystem, устанавливаемая один раз инсталлятором, и непривилегированный GUI, общающийся с ней по IPC. Именно так устроен [Clash Verge Rev](https://github.com/clash-verge-rev/clash-verge-rev) (разделение service/sidecar).

**Но это же и главная уязвимость класса.** Исследование (RQ8) нашло прецеденты у практически всех крупных игроков:

| CVE | Продукт | Суть |
|---|---|---|
| [CVE-2024-4877](https://www.cve.news/cve-2024-4877/) | OpenVPN для Windows | Локальный атакующий с минимальными правами **перехватывает named pipe** GUI → полный доступ SYSTEM |
| CVE-2024-24974 | OpenVPN | Несанкционированный доступ к named pipe `\\openvpn\service`, включая удалённое взаимодействие |
| [CVE-2025-8069](https://aws.amazon.com/security/security-bulletins/rss/aws-2025-014/), CVSS 7.8 | AWS Client VPN | Загрузка конфига OpenSSL из пути, **доступного на запись непривилегированному пользователю** → выполнение кода с повышением привилегий |
| [CVE-2024-6975](https://blog.amberwolf.com/blog/2024/july/cve-2024-6975-cato-client-local-privilege-escalation-via-openssl-configuration-file/) | Cato Client | IPC клиент→служба по named pipe `cato-VPN` с ProtoBuf → LPE |
| CVE-2025-26168, -26169 и др. | IXON VPN | Три уязвимости, LPE на Windows и Linux |
| 4 уязвимости от Microsoft Research | OpenVPN | Цепочка до RCE и LPE |

Вывод: в Фазе 1 я оценил вероятность R4 как «среднюю». Это была ошибка. **Этой ошибкой переболели все**, включая OpenVPN и AWS. Вероятность — высокая, влияние — критическое.

## Решение

**Двухпроцессная модель с мерами S1–S8, переведёнными из категории «рекомендуемые практики» в категорию «acceptance-критерии итерации».**

Ни одна итерация, затрагивающая IPC, запуск процессов или файловые пути службы, не считается завершённой без прохождения чек-листа ниже.

### Обязательные меры

| # | Мера | Прецедент нарушения |
|---|---|---|
| **S1** | Явный DACL на named pipe: доступ только интерактивным пользователям целевой группы; явный запрет сетевого доступа. `NULL DACL` запрещён | CVE-2024-4877, CVE-2024-24974 |
| **S2** | Верификация подключившегося клиента: проверка подписи и пути исполняемого файла процесса, а не только SID. Защита от «первый занял pipe» — служба создаёт pipe первой, с `FILE_FLAG_FIRST_PIPE_INSTANCE` | CVE-2024-4877 |
| **S3** | Строгая валидация всех команд. Служба **не принимает** от клиента: произвольные пути к исполняемым файлам, произвольные аргументы, сырой конфиг ядра. Только декларативная модель; конфиг генерируется **внутри службы** | CVE-2024-6975 |
| **S4** | Всё, что служба загружает или исполняет (`wintun.dll`, драйвер `Redirector`), берётся из фиксированной директории в `%ProgramFiles%` с проверкой подписи/хеша перед загрузкой. Никаких путей, доступных пользователю на запись | **CVE-2025-8069** — ровно этот сценарий |
| **S5** | Директория данных службы недоступна на запись непривилегированным пользователям. Проверяется при старте, при нарушении — отказ запуска с сообщением | CVE-2025-8069 |
| **S6** | Секреты (приватные ключи AmneziaWG, UUID VLESS, пароли) хранятся через DPAPI в machine scope. В памяти — минимальное время жизни, обнуление после использования | — |
| **S7** | Логи не содержат секретов. Маскирование при записи, а не при экспорте. Экспорт диагностики дополнительно проходит фильтр | — |
| **S8** | Обновления только по HTTPS с проверкой подписи пакета. Автообновление службы SYSTEM — отдельная поверхность, требует собственного ревью | — |

### Дополнительно

- **S9.** Ядра и вспомогательные процессы запускаются с **пониженными** привилегиями, а не под SYSTEM. Служба сохраняет права только для себя.
- **S10.** Отдельная итерация плана — **аудит безопасности IPC** с воспроизведением сценариев из таблицы CVE на нашем коде.
- **S11.** Быстрое переключение пользователей: служба одна, сессий несколько. Политика — один активный привилегированный клиент; остальные получают отказ, а не молчаливое подключение.

## Рассмотренные варианты

### A. Монолит с UAC при каждом запуске

**Плюсы:** нет IPC → нет этого класса уязвимостей.
**Минусы:** неприемлемый UX — запрос UAC при каждом старте и при автозапуске вообще невозможен. Отвергнуто.

### B. Служба + GUI без строгой верификации клиента

Модель «как у всех», где pipe защищён только SID.

**Плюсы:** быстрее в разработке.
**Минусы:** ровно то, на чём подорвались OpenVPN, Cato и IXON. Отвергнуто.

### C. Служба + GUI с полным набором S1–S11 ✅

**Плюсы:** закрывает известные векторы; меры дешевле применить сразу, чем ретрофитить.
**Минусы:** каждая мера — работа; верификация клиента усложняет отладку и локальную разработку (нужен режим разработчика с явным ослаблением, недоступный в релизной сборке).

### D. Служба + GUI, привилегированные операции по одноразовым elevation-запросам

Как в Clash Verge Rev: режим sidecar без прав + опциональная установка службы.

**Плюсы:** пользователь без TUN может работать вообще без службы — меньше поверхность.
**Минусы:** после решения Q3 (драйвер в MVP) права нужны почти всегда. Идея сохраняется как **опция**, а не как основной режим.

## Анализ компромиссов

**Безопасность против скорости разработки.** Меры S1–S11 замедляют разработку — особенно S2 (верификация клиента ломает запуск GUI из-под отладчика). Компенсируется режимом разработчика, физически отсутствующим в релизной сборке (проверка на этапе сборки, а не на этапе рантайма).

**Строгость против гибкости.** S3 запрещает передавать в службу сырой конфиг ядра. Это неудобно: пришлось бы поддерживать декларативную модель для каждой возможности ядра, вместо того чтобы дать «продвинутый режим с JSON». Мы сознательно жертвуем этим удобством — прецедент CVE-2024-6975 показывает цену.

Компромисс для продвинутых пользователей: расширенные параметры доступны через типизированные поля декларативной модели (ADR-005, §11 UX), а не через сырой конфиг.

## Последствия

**Становится проще:**
- Известные векторы LPE закрыты до первого релиза, а не после первого отчёта исследователя.
- Модель угроз документирована и проверяема.

**Становится сложнее:**
- Каждая итерация с IPC несёт чек-лист.
- Нужен режим разработчика и гарантия его отсутствия в релизе.
- S3 запрещает «просто прокинуть JSON» — декларативную модель придётся расширять под каждую новую возможность ядра.
- Отладка усложняется.

**Что придётся пересмотреть:**
- Если появится потребность в продвинутом режиме с сырым конфигом — проектировать его как отдельный, явно включаемый механизм с собственной моделью угроз, а не как послабление S3.

## Задачи

1. [ ] Реализовать DACL на named pipe + `FILE_FLAG_FIRST_PIPE_INSTANCE` (S1, S2)
2. [ ] Верификация подписи и пути клиентского процесса (S2)
3. [ ] Декларативная модель конфигурации; генерация конфига ядра только внутри службы (S3)
4. [ ] Проверка подписи/хеша `wintun.dll` и драйвера перед загрузкой (S4)
5. [ ] Проверка ACL директорий службы при старте (S5)
6. [ ] Хранилище секретов на DPAPI (S6)
7. [ ] Маскирование секретов при записи в лог (S7)
8. [ ] Режим разработчика с гарантией отсутствия в релизной сборке
9. [ ] Чек-лист безопасности как acceptance-критерий итераций с IPC (S10)

# E6 — что остаётся в системе после падения с поднятым туннелем

| | |
|---|---|
| **Вопрос** | Оставляет ли аварийное завершение процесса с поднятым TUN машину без интернета? Что именно приходится восстанавливать? |
| **Статус** | ✅ Завершён. Следов не остаётся; режим туннеля работает |
| **Стенд** | `cmd/e6-tun-probe`, профиль AmneziaWG заказчика |
| **Зачем** | Определяет объём механики восстановления в И-5 |

## Постановка

Итерация И-5 отвечает на один вопрос: умеем ли мы безопасно поднять туннель и
гарантированно вернуть систему в исходное состояние. Ключевой сценарий
приёмки — **убийство службы через диспетчер задач не оставляет машину без
интернета**.

Писать механику восстановления до того, как измерено, что именно требует
восстановления, — значит угадывать. Правдоподобных исходов три, и они требуют
совершенно разного объёма работы:

| Исход | Что придётся делать |
|---|---|
| Адаптер и маршруты исчезают сами | Ничего. Достаточно проверки при старте |
| Адаптер остаётся, маршруты уходят с ним | Убрать адаптер при следующем запуске |
| Остаются и адаптер, и маршруты | Снимок состояния до изменений и его восстановление |

Третий случай — самый дорогой, и именно он записан в плане. Но драйвер Wintun
считает ссылки на адаптер и убирает его при закрытии последнего дескриптора, а
дескрипторы закрываются при смерти процесса. Поэтому вероятен первый исход, и
проверить это дешевле, чем реализовывать третий.

## Метод

Проба `cmd/e6-tun-probe` снимает состояние сети трижды: до подъёма туннеля, во
время работы и после завершения. Сравнение показывает разницу.

Главный измеряемый показатель — **наличие интернета**, а не совпадение таблиц.
Лишний маршрут, который ничему не мешает, и пропавший маршрут по умолчанию —
события совершенно разного веса, и различать их надо по последствию.

Проверка связи идёт **в обход** переменных окружения `HTTP_PROXY`: на машине
разработки стоит посторонний прокси, и без этого проба измеряла бы его
доступность, а не работоспособность сети.

### Почему состояние снимается через PowerShell

Точный способ — IP Helper API (`GetIpForwardTable2`). Он требует ручного
описания раскладки `MIB_IPFORWARD_ROW2`: около сотни байт из вложенных
объединений `SOCKADDR_INET`. Ошибка в раскладке даёт не отказ, а обращение по
неверному адресу — этот проект уже получал такой отказ на константе WFP
(см. [gui_client_study.md](../gui_client_study.md), раздел 6.7).

Для диагностического средства цена такой ошибки не оправдана. `Get-NetRoute` и
`Get-NetAdapter` возвращают то же самое, а разбор JSON проверяется глазами.
Если окажется, что производственному коду нужен разбор таблицы маршрутов, он
будет написан через IP Helper — но уже зная, что именно из неё нужно.

## Порядок проведения

⚠️ **Требуются права администратора** и **готовность на короткое время
остаться без интернета**. Сценарий «crash» намеренно оставляет систему в том
состоянии, в каком её оставляет упавшая служба.

Все команды — из окна с правами администратора, из корня репозитория.

Шаг 1. Контрольный снимок и проверка, что штатный цикл работает:

```bash
bin\e6-tun-probe.exe up -conf testdata\live\test2-ams1.awg.conf -hold 20s
```

Ожидание: во время работы появляется адаптер `netgui` и маршруты `0.0.0.0/1`,
`128.0.0.0/1`; после штатного закрытия состояние совпадает с исходным.

Шаг 2. Аварийное завершение:

```bash
bin\e6-tun-probe.exe crash -conf testdata\live\test2-ams1.awg.conf -hold 10s -out e6-before.json
```

Процесс завершится кодом 3, не закрыв ядро.

Шаг 3. Что осталось:

```bash
bin\e6-tun-probe.exe compare -before e6-before.json
```

### Дефект, найденный тем же прогоном: перехват IPv6 без возможности его нести

Строка «во время работы: интернет НЕТ» — это не побочная деталь, а отказ
серьёзнее того, ради которого эксперимент затевался. **Машина осталась без
интернета при поднятом туннеле**, то есть в штатном режиме работы.

Журнал заполнился сотнями записей:

```
ERROR connection: listen packet connection using outbound/wireguard[proxy]:
      missing IPv6 local address
```

Причина в конфигурации, которую собирали мы. Адрес IPv6 выдавался адаптеру
**безусловно**, а маршруты в sing-tun выводятся из списка адресов
(`BuildAutoRouteRanges`, проверка `len(Inet6Address) > 0`). У профиля ams1 есть
только `10.9.0.15/32` — адреса IPv6 нет. Система послушно направила весь трафик
IPv6 в туннель, который его не несёт, и он провалился в чёрную дыру.

**Исправлено:** адрес IPv6 выдаётся адаптеру, только если профиль
действительно способен передавать IPv6. Для WireGuard это точно известно из
конфигурации; для протоколов-прокси ответ неизвестен в принципе — зависит от
сервера, — и выбран осторожный вариант «нет».

Правило, которое из этого следует: **перехватывать только то, что умеем
донести.** Чёрная дыра хуже отсутствия перехвата — она ломает связь, причём
молча и в месте, никак не связанном с причиной.

⚠️ Следствие, которое надо знать: для профилей без IPv6 трафик IPv6 идёт мимо
туннеля, то есть **утекает**. Это осознанная граница И-5. Закрытие утечек —
итерация И-8, и закрывать их надо явной блокировкой, а не случайной чёрной
дырой, которая заодно ломает работу.

Закреплено тестами `TestTunnelDoesNotCaptureIPv6WithoutSupport` и
`TestTunnelCapturesIPv6WhenProfileHasIt`.

### Изменение разрешения имён (основание — устройство системы, не измерение)

Секция DNS собиралась с резолвером `local`, то есть системным. В режиме прокси
это работает и проверено с И-1. В режиме туннеля — замкнутая петля:

1. `sing-tun` перехватывает запросы DNS и направляет их в ядро;
2. ядро отвечает через транспорт `local`, то есть спрашивает систему;
3. запрос системы снова попадает в туннель — к шагу 1.

При этом в профиле ams1 **был задан** `DNS = 1.1.1.1, 1.0.0.1`, мы его
разбирали — и никогда не использовали.

**Изменено:** в режиме туннеля заводится второй резолвер, доступный через сам
туннель (`udp` с `detour` на прокси), и основным становится он. Системный
резолвер остаётся, но только для разрешения адреса самого VPN-сервера, если
тот задан именем: через ещё не поднятый туннель это невозможно.

⚠️ Изменение сохранено НЕ потому, что доказано измерением — измерение
оказалось загрязнено, см. ниже. Основание другое и самостоятельное: без
`detour` запрос DNS уходит мимо туннеля, и наблюдатель на стороне провайдера
видит, какие имена запрашиваются. Туннель, не скрывающий этого, бесполезен
ровно в том, ради чего его поднимают.

Параметр `detour` здесь не деталь: без него запрос DNS ушёл бы мимо туннеля, и
наблюдатель на стороне провайдера видел бы, какие имена запрашиваются.

Закреплено четырьмя тестами, включая защиту прежнего поведения в режиме
прокси — чинить то, что не сломано, было бы отдельной ошибкой.

## Загрязнение измерения сторонними инструментами

⚠️ Важная оговорка ко всем прогонам: на машине одновременно работали
**Hiddify** (в режиме системного прокси) и **Proxifier**.

Строка «во время работы: интернет НЕТ» во всех трёх прогонах сопровождалась
одним и тем же адресом:

```
причина: имя разрешилось в 127.206.0.124, но соединение не устанавливается
```

Адрес **петлевой** и **одинаковый до и после** исправления разрешения имён —
то есть исправление на этот симптом не повлияло. Без туннеля то же имя
разрешается нормально (`34.160.111.145`), связь есть.

Подставные адреса раздают инструменты, перехватывающие разрешение имён:
Proxifier отдаёт приложению адрес из петлевого диапазона, клиенты на базе
sing-box — из `198.18.0.0/15`. Что именно произошло при поднятом нашем
туннеле — вопрос открытый.

**Следствие для честности выводов:** утверждение «системный резолвер в режиме
туннеля даёт петлю» остаётся **непроверенным**. Оно правдоподобно и
подкреплено устройством sing-tun, но приведённое ниже измерение его не
доказывает. Соответствующее изменение конфигурации сохранено по другому
основанию — см. ниже.

Проба доработана: адрес из петлевого диапазона или из `198.18.0.0/15` теперь
распознаётся и называется прямо, вместо бесполезного «соединение не
устанавливается».

**Чистое измерение требует остановки Hiddify и Proxifier.**

### Прогон 4 (26.08.2026): чистое измерение — загрязнение подтвердилось

Hiddify и Proxifier остановлены. Подставной адрес `127.206.0.124` **исчез** —
он действительно принадлежал стороннему инструменту, а не нашему коду.

Симптом сменился на настоящий:

```
причина: имя ifconfig.me не разрешается (DNS): lookup ifconfig.me: i/o timeout
```

При этом в журнале видно, что трафик через туннель ИДЁТ: ответы

дошедшие через ams1. Восстановление после штатного закрытия снова полное.

Итог: сам туннель передаёт данные, а разрешение имён по системному пути — нет.

### Доработка пробы: два независимых замера

Чтобы не гадать дальше, проба измеряет связь ДВУМЯ путями:

| Замер | Что использует |
|---|---|
| **[а] напрямую** | системный резолвер + таблица маршрутизации Windows |
| **[б] через локальный прокси ядра** | резолвер и маршрутизацию самого ядра |

Расхождение указывает виновника однозначно:

- **[б] работает, [а] нет** — туннель исправен, сломан системный путь: перехват
  DNS, порядок маршрутов, посторонний клиент;
- **оба не работают** — не работает сам туннель;
- **[а] работает, [б] нет** — неисправность в ядре.

Без этого различения «интернета нет» одинаково выглядит в трёх совершенно
разных случаях — на чём первые прогоны и застряли.

Проба проверена на себе в режиме прокси (права администратора там не нужны):

```
[а] напрямую (системный путь):    есть (31.28.6.149)
[б] через локальный прокси ядра: есть (132.243.234.217)
⇒ Оба пути работают.
```

Это отдельный полезный результат: **сам туннель AmneziaWG, разрешение имён и
маршрутизация внутри ядра исправны.** Неисправность режима TUN находится не в
них.

### Третий дефект: перехват DNS не был включён

`sing-tun` прописывает адаптеру резолвер — адрес самого туннеля плюс один
(у нас `172.19.0.2`):

```go
dnsServers := common.Filter(t.options.DNSServers, netip.Addr.Is4)
if len(dnsServers) == 0 && HasNextAddress(t.options.Inet4Address[0], 1) {
    dnsServers = []netip.Addr{t.options.Inet4Address[0].Addr().Next()}
}
```

Это **фиктивный** адрес: никакого сервера DNS там нет. Расчёт на то, что
запросы к нему будут перехвачены и отданы подсистеме разрешения имён ядра.

Перехват включается отдельным правилом маршрутизации, и его у нас не было.
Пакеты к `172.19.0.2` уходили в никуда, а системный резолвер ждал ответа до
истечения времени ожидания — отсюда `i/o timeout`.

**Исправлено:** в режиме туннеля первыми идут два служебных правила —
определение протокола (`sniff`) и перехват (`hijack-dns`). Они стоят ДО
правил пользователя: иначе правило «всё через туннель» поймало бы запрос
первым, и перехват не сработал бы.

Закреплено тремя тестами, в том числе на порядок правил и на отсутствие
перехвата в режиме прокси, где системный резолвер работает и проверен с И-1.

### Чему учит цепочка из трёх дефектов

Все три — IPv6, разрешение имён через туннель, перехват DNS — проявлялись
ОДИНАКОВО: «интернета нет». Отличить их удалось только измерением, которое
разделяет пути и называет шаг.

Порядок был такой: сначала проба говорила «нет интернета» (бесполезно), потом

путь» (указало точно). Каждая доработка пробы стоила минут и экономила
итерацию догадок.

## Итоги

### По основному вопросу

Аварийное завершение процесса с поднятым TUN **не оставляет следов**: драйвер
Wintun убирает адаптер при закрытии последнего дескриптора, маршруты исчезают
вместе с интерфейсом. Механику снимка и восстановления состояния сети —
самый дорогой пункт плана И-5 — писать не требуется.

Полезной остаётся проверка при старте: адаптер мог остаться по причине,
которую этот эксперимент не воспроизвёл.

### Три дефекта, найденных попутно

Все три проявлялись ОДИНАКОВО — «интернета нет» при поднятом туннеле:

| № | Дефект | Как проявлялся |
|---|---|---|
| 1 | Перехват IPv6 без возможности его нести | Сотни `missing IPv6 local address` |
| 2 | Разрешение имён шло мимо туннеля | (устранён вместе с 3) |
| 3 | Не был включён перехват DNS | `lookup: i/o timeout` |

Отличить их удалось только измерением, которое разделяет пути и называет шаг:

| Что говорила проба | Насколько сузило поиск |
|---|---|
| «интернета нет» | никак |
| «не разрешается имя» | вдвое |
| «туннель исправен, сломан системный путь» | точно |

Каждая доработка пробы стоила минут и экономила заход догадок. Это главный
методический вывод эксперимента: **вкладывать в различающую способность
измерения выгоднее, чем в скорость перебора гипотез.**

### Известная шероховатость: первые запросы после подъёма

В начале работы туннеля видно:

```
ERROR dns: exchange failed for ... : dial UDP connection: WireGuard is not ready yet
ERROR router: process DNS packet: dial UDP connection: WireGuard is not ready yet
```

Перехват DNS начинает работать раньше, чем завершается рукопожатие WireGuard.
Несколько первых запросов отваливаются, дальше всё приходит в норму.

Само по себе это не ломает работу, но означает, что состояние «подключено»
показывается раньше, чем туннель действительно готов нести трафик.
Пользователь в эти секунды увидит неоткрывшуюся страницу.

Правильное место для исправления — **наблюдение за живостью (И-9)**: состояние
должно оставаться «подключение» до тех пор, пока туннель не подтвердит
готовность. Здесь это фиксируется как известное ограничение, а не чинится
наспех: заплатка в виде паузы после подъёма скрыла бы симптом, не решив
задачу.

## Побочная находка: Wintun вкомпилирован, а не загружается с диска

Обнаружено при подготовке эксперимента, зафиксировано отдельно, потому что
меняет постановку меры **S4**.

План И-5 требует «загрузки официального `wintun.dll` с проверкой подписи».
Действительность иная: `sing-tun` вкомпилировывает драйвер директивой
`//go:embed` и загружает его **самописным загрузчиком PE прямо из памяти**
(`memmod.LoadLibrary`). Файл не попадает на диск, Windows в загрузке не
участвует, проверять подпись в этот момент нечего и негде.

Следствия два.

**Первое — переформулировка S4.** Осмысленная гарантия сдвигается на этап
сборки: убедиться, что вкомпилированы именно официальные байты. Это проверяется
тестом `internal/platform/wintun`, и проверка проходит:

```
подписант:     CN=WireGuard LLC, O=WireGuard LLC, L=Boulder, S=Colorado, C=US
издатель:      CN=DigiCert EV Code Signing CA (SHA2)
метка времени: CN=DigiCert Timestamp 2021
статус:        Valid
```

Сертификат истёк 14.12.2021, и это не делает подпись недействительной: она
содержит метку времени от независимого центра, доказывающую, что подписание
произошло, пока сертификат был действителен. Ради этого метки и существуют.
Отдельный тест закрепляет этот факт, чтобы будущий читатель, увидев дату, не
решил, что проверка сломана.

Что проверка ловит: подмену в кэше модулей, вредоносное обновление зависимости,
подмену в цепочке поставки. Чего не ловит: подмену уже собранного двоичного
файла — от неё защищает подпись самого приложения.

**Второе — усиление риска R3.** Ручная загрузка PE из памяти является
классическим приёмом вредоносного ПО (reflective DLL injection) и распознаётся
эвристиками антивирусов как таковая. План (дефект D5) требует повторной
проверки реакции антивирусов именно на этой итерации — теперь у этого
требования есть конкретное основание, а не общее соображение «добавили
драйвер».

⚠️ Проверка через мультисканер означает **загрузку двоичного файла на внешний
сервис**, где он станет доступен посторонним. Без отдельного разрешения
заказчика не проводится.

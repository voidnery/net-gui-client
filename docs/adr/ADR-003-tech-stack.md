# ADR-003: Технологический стек и границы процессов

**Статус:** Принято
**Дата:** 2026-08-24
**Решает:** RQ9, Q5, риск R18
**Зависит от:** [ADR-001](ADR-001-protocol-core.md)

## Контекст

Заказчик не наложил ограничений на стек (Q5), решение — по итогам исследования. В среде разработки установлены Node 22.12, .NET SDK 10.0.201, Python 3.11; Go и Rust отсутствуют.

Два факта из Фаз 1–2 переопределили задачу:

1. **ADR-001 делает Go обязательным.** Форк sing-box — это Go-код, который мы будем собирать и ребейзить независимо от остального выбора. Go-тулчейн, Go-CI и Go-экспертиза нужны в любом случае.
2. **GPL-3.0 разрешает линковку** (Q2), и ради этого права выбиралась лицензия. Отказ от линковки в пользу процессной границы обесценивает решение Q2.

Требование T9 (Linux server edition) означает, что демон обязан быть headless-first, а GUI — лишь один из клиентов API.

Прецеденты из исследования:
- [Hiddify](https://github.com/hiddify/hiddify-app): Flutter UI + Go-ядро на базе sing-box, скомпилированное в разделяемую библиотеку, связь через FFI (`libcore.h`) и gRPC. Доказано в проде на всех платформах.
- [Clash Verge Rev](https://github.com/clash-verge-rev/clash-verge-rev): Tauri + Rust, ядро Mihomo отдельным sidecar-процессом, разделение service/sidecar для привилегий.
- [wireguard-windows](https://www.wireguard.com/repositories/): служба Windows и WFP-правила killswitch реализованы **на чистом Go** — прецедент, что Go справляется с Windows-специфичной привилегированной работой.

## Решение

| Компонент | Технология |
|---|---|
| `net-core` — ядро протоколов | **Go** (форк sing-box, линкуется как пакет) |
| `net-svc` — служба LocalSystem | **Go** |
| `net-cli` — CLI-клиент | **Go** |
| `net-gui` — GUI и трей-агент | **Wails v2** (Go + WebView2, фронт на вебе) |
| Бэкенд `Redirector` | **C** (драйвер) + Go-обвязка |
| Контракт между GUI/CLI и службой | gRPC поверх named pipe — см. [ADR-004](ADR-004-ipc-contract.md) |

Один язык, один тулчейн, один CI для всего, кроме драйвера — который на C будет в любом стеке.

## Рассмотренные варианты

### A. Всё на Go, GUI на Wails ✅

| Измерение | Оценка |
|---|---|
| Сложность | **Низкая** — один язык |
| Стоимость | Низкая |
| Масштабируемость на платформы | **Высокая** |
| Экспертиза команды | Требуется Go (но он обязателен по ADR-001) |
| Размер дистрибутива | **~8 МБ** GUI + ядро |

**Плюсы:**
- Go нужен в любом случае → второй язык добавляет стоимость, не добавляя возможностей.
- Прямая линковка ядра: доступ к rule-engine, списку соединений, метрикам, hot-reload — без FFI-границы и без сериализации.
- Форк `sing-box-lx` уже содержит headless-демон и gRPC CommandClient — готовая заготовка под принцип P1 и под Linux server edition.
- Wails v2 стабилен, применяется в проде, даёт трей, нативные диалоги, меню, подпись кода и упаковку MSI.
- Кроссплатформенность из коробки (T9).
- Прецедент wireguard-windows: WFP и служба Windows на чистом Go работают.

**Минусы:**
- ⚠️ Go — не идеальный язык для тонкой работы с Windows API. `golang.org/x/sys/windows` не покрывает `fwpuclnt`; придётся писать свои syscall-биндинги. Смягчается прецедентом wireguard-windows.
- ⚠️ Wails на Windows требует WebView2 — предустановлен в Windows 11, но не гарантирован в Windows 10 (риск R18; смягчается bootstrapper'ом в инсталляторе).
- GUI на вебе, а не нативный — вопрос вкуса, но на визуальный дизайн (отдельная итерация) влияет положительно.

### B. Go-ядро как разделяемая библиотека + GUI на другом языке

Модель Hiddify: Go-ядро → C-ABI → FFI-биндинги в Flutter / Rust / C#.

| Измерение | Оценка |
|---|---|
| Сложность | Средняя |
| Стоимость | Средняя |
| Масштабируемость на платформы | Высокая |
| Экспертиза команды | Два языка |

**Плюсы:** свобода выбора GUI-технологии; доказано в проде; при желании .NET 10 (уже установлен) даёт лучшую интеграцию с Windows.
**Минусы:** FFI-граница между службой и ядром там, где она не нужна — служба и ядро живут в одном процессе; два тулчейна, два CI; сборка усложняется.

### C. Ядро отдельным процессом + IPC

Модель Clash Verge Rev.

**Плюсы:** максимальная изоляция отказов — падение ядра не роняет службу (идея Amnezia с изоляцией служб по протоколам).
**Минусы:** теряется прямой доступ к rule-engine и метрикам — ровно то, ради чего добивались права на линковку (Q2). Дублируется сериализация. Обновление ядра всё равно требует пересборки (ADR-001), так что выигрыш «подменить бинарник» иллюзорен.

### D. C# / .NET 10 для службы + GUI на WPF/WinUI

| Измерение | Оценка |
|---|---|
| Сложность | Средняя |
| Стоимость | Средняя |
| Масштабируемость на платформы | **Средняя** (Avalonia решает, но это доп. выбор) |
| Экспертиза команды | Два языка |
| Размер дистрибутива | ~70 МБ self-contained |

**Плюсы:** SDK уже установлен; лучшая в классе интеграция с Windows (службы, реестр, WFP через P/Invoke); быстрая разработка GUI; прецедент Netch (C#, GPLv3, per-process редирект).
**Минусы:** Go всё равно нужен для ядра → два тулчейна; ядро через FFI или IPC; путь на Linux/macOS слабее; размер дистрибутива в 8 раз больше.

### E. Electron / Node

**Плюсы:** Node установлен; максимальная скорость UI-разработки.
**Минусы:** 150+ МБ, высокое потребление памяти, слабый системный доступ, привилегированная часть всё равно на другом языке. Отвергнуто.

## Анализ компромиссов

**Главный компромисс — интеграция с Windows против единства стека.** .NET (вариант D) объективно удобнее для Windows-специфичной работы: службы, реестр, P/Invoke, WFP. Но он не отменяет необходимости Go для ядра, а лишь добавляет вторую границу. Прецедент wireguard-windows показывает, что Go эту работу тянет — значит преимущество .NET реально, но не решающее.

**Второй компромисс — изоляция отказов против прямого доступа.** Вариант C надёжнее при падении ядра. Мы сознательно выбираем прямой доступ, компенсируя изоляцию тем, что ядро линкуется в службу, а не в GUI: падение затрагивает службу, но не пользовательский интерфейс, и служба перезапускается менеджером служб Windows.

**Третий компромисс — WebView2.** Внешняя зависимость GUI против размера дистрибутива. 8 МБ против 70 МБ (.NET) и 150 МБ (Electron) окупает bootstrapper в инсталляторе.

## Последствия

**Становится проще:**
- Один тулчейн, один CI, один набор линтеров и тестов.
- Прямой доступ к внутренностям ядра без прослоек.
- `net-cli` — тот же код, что и служба, тривиально писать вместе с функциями.
- Порт на Linux/macOS: Orchestration переносится без изменений, переписывается только слой Platform.

**Становится сложнее:**
- Нужно писать свои syscall-биндинги к WFP (`fwpuclnt`) — Go их не покрывает.
- WebView2 как внешняя зависимость GUI.
- Разработка драйвера на C остаётся отдельным миром со своим циклом сборки.
- Требуется установить Go-тулчейн — в текущей среде его нет.

**Что придётся пересмотреть:**
- Если биндинги к WFP на Go окажутся неподъёмными — вынести `WfpBlocker` и `Redirector` в нативный компонент на C с тонкой Go-обвязкой (граница уже предусмотрена интерфейсами слоя Platform).
- Если Wails окажется недостаточным для целевого визуального дизайна (отдельная итерация) — GUI можно заменить, не трогая службу: контракт gRPC это позволяет (ADR-004).

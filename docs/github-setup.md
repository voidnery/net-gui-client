# Публикация на GitHub — пояснительная записка

Пошаговая инструкция под **GitHub Desktop** для Windows. Рассчитана на то, что вы не работаете с git из командной строки.

**Что уже сделано за вас:**
- репозиторий инициализирован локально (`git init`), ветка по умолчанию — `master`;
- подготовлены `README.md`, `NOTICE`, `SECURITY.md`, `VERSION`, `.gitignore`, `.gitattributes`;
- настроены два рабочих процесса CI: [`ci.yml`](../.github/workflows/ci.yml) — сборка и тесты, [`release.yml`](../.github/workflows/release.yml) — автоматические подписанные теги и релизы.

**Что предстоит сделать вам** — шаги 1–7 ниже. На всё уходит около получаса, из которых половина — генерация GPG-ключа.

---

## Коротко о том, что получится

```
   работаете здесь
        ↓
   ┌─────────┐   Pull Request    ┌──────────┐
   │  beta   │ ────────────────► │  master  │
   └─────────┘   (вы одобряете)  └──────────┘
        │                             │
   пред-релиз                     релиз
   v0.1.0-beta.7                  v0.1.0
   (подписан GPG)                 (подписан GPG)
```

- Вся разработка идёт в ветке `beta`.
- В `master` изменения попадают **только** через Pull Request, который вы сами одобряете. Прямой пуш в `master` запрещается настройкой на GitHub.
- Тег версии проставляется и подписывается автоматически при пуше — вручную ничего создавать не нужно.

## Шаг 1. Добавить файл LICENSE

Проект под GPL-3.0, и полный текст лицензии обязан лежать в репозитории. Его удобнее всего добавить средствами GitHub — там есть встроенный шаблон, который гарантированно даёт точный текст.

Это делается **после** публикации репозитория, в шаге 3.1. Пока просто имейте в виду, что файл появится.

## Шаг 2. Опубликовать репозиторий

1. Откройте **GitHub Desktop**.
2. Меню **File → Add local repository…**
3. Нажмите **Choose…** и выберите папку:
   ```
   D:\Temp_Danya\Projects\net_gui_client
   ```
4. Нажмите **Add repository**.
   GitHub Desktop увидит уже инициализированный репозиторий и покажет список неотслеживаемых файлов.

5. Слева внизу, в поле **Summary**, введите текст первого коммита, например:
   ```
   Начальная структура проекта: документация, ADR, каркас Go, CI
   ```
6. Нажмите **Commit to master**.

7. Вверху появится кнопка **Publish repository**. Нажмите её.
   В диалоге:
   - **Name**: `net-gui-client`
   - **Description**: `GUI-клиент для VPN- и прокси-протоколов`
   - ⚠️ **Снимите галочку «Keep this code private»** — репозиторий обязан быть публичным. Это требование GPL-3.0 и условие бесплатной подписи кода через SignPath Foundation.
8. Нажмите **Publish repository**.

## Шаг 3. Донастроить на github.com

Откройте репозиторий в браузере: в GitHub Desktop меню **Repository → View on GitHub**.

### 3.1. Добавить LICENSE

1. На главной странице репозитория: **Add file → Create new file**.
2. В поле имени файла введите `LICENSE` — справа появится кнопка **Choose a license template**. Нажмите её.
3. В списке слева выберите **GNU General Public License v3.0**.
4. Справа нажмите **Review and submit** → **Commit changes**.
5. В диалоге коммита выберите **Commit directly to the master branch**.

### 3.2. Забрать изменение к себе

Вернитесь в GitHub Desktop и нажмите **Fetch origin**, затем **Pull origin**. Файл `LICENSE` появится в локальной папке.

## Шаг 4. Создать ветку beta

В GitHub Desktop:

1. Меню **Branch → New branch…**
2. **Name**: `beta`
3. Убедитесь, что в **Create branch based on…** выбран `master`.
4. Нажмите **Create branch**.
5. Нажмите **Publish branch** — ветка появится на GitHub.

С этого момента работайте в `beta`. Текущая ветка видна вверху окна в поле **Current branch**.

## Шаг 5. Запретить прямой пуш в master

Это и есть тот самый «переливочный механизм», который вы контролируете. Настраивается один раз на github.com.

1. В репозитории: **Settings** → в меню слева **Rules → Rulesets** → **New ruleset** → **New branch ruleset**.
2. **Ruleset Name**: `Защита master`
3. **Enforcement status**: переключите на **Active**.
4. В разделе **Target branches** нажмите **Add target** → **Include default branch**.
5. В разделе **Rules** поставьте галочки:
   - ✅ **Restrict deletions** — ветку нельзя удалить;
   - ✅ **Require a pull request before merging** — прямой пуш запрещён;
     - **Required approvals**: поставьте `0`.
       *Почему ноль:* GitHub не позволяет одобрить собственный Pull Request. Если поставить 1, вы заблокируете сами себя. Контроль всё равно остаётся: слить может только человек, нажав кнопку **Merge**.
   - ✅ **Require status checks to pass** → **Add checks** → выберите `build`.
     Это не даст слить в `master` код, который не собирается или не проходит тесты.
   - ✅ **Block force pushes**
6. Нажмите **Create**.

> **Важно:** как владелец репозитория вы можете обойти это правило. Чтобы правило действовало и на вас, в разделе **Bypass list** никого не добавляйте — по умолчанию список пуст, и это правильно.

## Шаг 6. Настроить подпись тегов

Теги версий будут подписываться GPG-ключом автоматически, а на GitHub получат отметку **Verified**. Ключ создаётся один раз.

### 6.1. Создать ключ

GPG уже установлен вместе с Git — он лежит в `C:\Program Files\Git\usr\bin\gpg.exe`, но не прописан в `PATH`. Поэтому запускать его нужно по полному пути.

Откройте **PowerShell** (обычный, не от администратора) и выполните:

```powershell
& 'C:\Program Files\Git\usr\bin\gpg.exe' --full-generate-key
```

Отвечайте так:

| Вопрос | Ответ |
|---|---|
| `Please select what kind of key you want` | `1` — RSA and RSA |
| `What keysize do you want?` | `4096` |
| `Key is valid for?` | `0` — не истекает |
| `Is this correct?` | `y` |
| `Real name` | ваше имя или название проекта |
| `Email address` | ⚠️ **тот же адрес, что в вашем аккаунте GitHub** |
| `Comment` | можно оставить пустым |
| `Change (N)ame, (C)omment, (E)mail or (O)kay` | `O` |
| Парольная фраза | придумайте и **сохраните** — она понадобится в шаге 6.3 |

### 6.2. Добавить публичный ключ в аккаунт GitHub

Получите отпечаток ключа:

```powershell
& 'C:\Program Files\Git\usr\bin\gpg.exe' --list-secret-keys --keyid-format=long
```

В выводе найдите строку вида `sec   rsa4096/AABBCCDDEEFF0011` — часть после косой черты и есть идентификатор ключа.

Выведите публичный ключ, подставив свой идентификатор:

```powershell
& 'C:\Program Files\Git\usr\bin\gpg.exe' --armor --export AABBCCDDEEFF0011 | Set-Clipboard
```

Ключ скопирован в буфер обмена. Теперь на github.com: **аватар → Settings → SSH and GPG keys → New GPG key** → вставьте → **Add GPG key**.

### 6.3. Добавить приватный ключ в секреты репозитория

⚠️ Приватный ключ — это секрет. Он попадает в защищённое хранилище GitHub Actions и в репозиторий **не** коммитится.

Экспортируйте приватный ключ в буфер обмена:

```powershell
& 'C:\Program Files\Git\usr\bin\gpg.exe' --armor --export-secret-keys AABBCCDDEEFF0011 | Set-Clipboard
```

На github.com, в репозитории: **Settings → Secrets and variables → Actions → New repository secret**.

Создайте два секрета:

| Name | Secret |
|---|---|
| `GPG_PRIVATE_KEY` | вставьте содержимое буфера обмена целиком, включая строки `-----BEGIN PGP PRIVATE KEY BLOCK-----` и `-----END PGP PRIVATE KEY BLOCK-----` |
| `GPG_PASSPHRASE` | парольная фраза из шага 6.1 |

> Если пропустить этот шаг, теги всё равно будут создаваться — но без подписи, и в журнале сборки появится предупреждение. Репозиторий останется работоспособным.

## Шаг 7. Повседневная работа

### Обычные изменения

1. Убедитесь, что в **Current branch** выбрана `beta`.
2. Внесите изменения в файлы.
3. В GitHub Desktop введите **Summary** и нажмите **Commit to beta**.
4. Нажмите **Push origin**.

CI соберёт проект и прогонит тесты. Результат виден на вкладке **Actions** на github.com.

### Перелить beta в master

Отвечая на ваш вопрос — **да, это делается через GitHub Desktop**, но финальное подтверждение происходит в браузере. Так и задумано: слияние в стабильную ветку требует осознанного действия.

1. В GitHub Desktop, находясь на ветке `beta`, нажмите **Preview Pull Request** (или меню **Branch → Create Pull Request**).
2. Откроется окно предпросмотра — здесь видно, что именно уйдёт в `master`. Нажмите **Create Pull Request**.
3. Откроется браузер с формой. Проверьте, что стрелка направлена `base: master ← compare: beta`. Нажмите **Create pull request**.
4. Дождитесь, пока проверки CI станут зелёными.
5. Нажмите **Merge pull request** → **Confirm merge**.

Сразу после слияния запустится рабочий процесс `Release`.

### Выпустить новую версию

1. Откройте файл `VERSION` в корне и измените число, например с `0.1.0` на `0.2.0`.
2. Закоммитьте и запушьте в `beta` (см. выше).
   → появится пред-релиз `v0.2.0-beta.<номер>` с пометкой *Pre-release*.
3. Когда версия готова — перелейте `beta` в `master` через Pull Request.
   → появится релиз `v0.2.0`.

Ничего создавать вручную не нужно: тег проставляется, подписывается и публикуется автоматически. Если `VERSION` не менялся, тег уже существует и рабочий процесс просто завершится без действий.

## Возможные затруднения

**«Publish repository» неактивна.** Сначала нужно сделать первый коммит — шаг 2, пункты 5–6.

**CI падает на шаге «Verify go.mod is tidy».** Значит `go.mod` или `go.sum` не соответствуют импортам. Выполните в папке проекта:

```bash
go mod tidy
```

затем закоммитьте изменённые файлы.

**Тег создался без подписи.** Не заданы секреты из шага 6.3. Проверьте, что имена секретов написаны точно: `GPG_PRIVATE_KEY` и `GPG_PASSPHRASE`.

**Не удаётся запушить в master.** Так и должно быть после шага 5. Работайте в `beta` и переливайте через Pull Request.

**GPG сообщает `Inappropriate ioctl for device`.** Запрос парольной фразы не смог открыться. Запустите команду в обычном окне PowerShell, а не во встроенном терминале редактора.

Это уберёт предупреждения SmartScreen у пользователей. Условия и обоснование — [E0-signing-and-av-baseline.md](experiments/E0-signing-and-av-baseline.md).

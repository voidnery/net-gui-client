**Дата:** 2026-08-24
**Вход:** [03-architecture.md](03-architecture.md) + ADR-001…006
**Приоритет (решение заказчика):** ранний рабочий сквозной срез, затем наращивание

## 1. Принципы построения плана

| # | Принцип | Почему |
|---|---|---|
| **P-A** | **Вертикальный срез вперёд горизонтальных слоёв.** Первая продуктовая итерация даёт работающую цепочку «профиль → подключение → трафик идёт», а не отдельно взятый слой | Решение заказчика по приоритету; риски вскрываются рано |
| **P-B** | **Эксперименты E1/E4 — до продуктового кода.** E2 стартует параллельно и идёт фоном | E1 определяет бэкенд `Redirector`; E2 — внешний процесс с неконтролируемым лагом, его нельзя ставить в конец (риск R13) |
| **P-C** | **GUI появляется рано и растёт вместе с функциями**, а не собирается в конце | Продукт — GUI-клиент. UX-решения надо проверять на живом интерфейсе, а не на бумаге |
| **P-D** | **`net-cli` пишется вместе с функцией, а не после.** Он же — инструмент интеграционных тестов | Принцип P1 (headless-first, T9); CLI даёт демонстрируемость до готовности GUI |
| **P-E** | **Меры S1–S11 — acceptance-критерии итераций**, затрагивающих IPC, запуск процессов и файловые пути. Не отдельная итерация «безопасность» в конце | RQ8: LPE-уязвимости класса «VPN-клиент» дешевле предотвратить, чем ретрофитить |
| **P-F** | **Каждая итерация завершается рефакторингом, баг-чекингом и обновлением `gui_client_study.md`** | Требование заказчика по процессу + освоение Go по ходу разработки |
| **P-G** | **Обратимость сетевых изменений — инвариант, а не фича.** Каждая итерация, трогающая сеть, обязана иметь авто-откат и watchdog | Риск R5: «интернет пропал» — самый болезненный отказ для пользователя |

## 2. Definition of Done — общий для всех итераций

Итерация закрыта, когда выполнено **всё**:

1. ✅ Функциональность работает и проверена вручную по сценарию из описания итерации
2. ✅ `net-cli` покрывает новые функции (P-D)
3. ✅ Автотесты: юнит на логику, интеграционный на сквозной сценарий
4. ✅ CI зелёный: сборка, тесты, линтеры, `go vet`
5. ✅ **Рефакторинг** проведён: устранено дублирование, вынесены абстракции, которые проявились по ходу
6. ✅ **Баг-чекинг** проведён: прогон негативных сценариев из списка итерации
7. ✅ Чек-лист безопасности пройден, если итерация трогает IPC / запуск процессов / пути (P-E)
8. ✅ Сетевые изменения обратимы: проверен сценарий «убить процесс на середине» (P-G)
9. ✅ **`docs/gui_client_study.md` дополнен** разбором новых конструкций Go (P-F)
10. ✅ Документация обновлена: изменения архитектуры отражены в ADR

## 4. Итерации

### И-0. Фундамент и разведка

**Цель:** снять блокирующую неопределённость и подготовить площадку.

**Состав:**
- Установка Go-тулчейна, фиксация версии
- Каркас монорепозитория: `net-core`, `net-svc`, `net-cli`, `net-gui`, `proto`, `internal/platform`
- CI: сборка, тесты, линтеры
- **E1** — загружается ли WinDivert 2.2 на Windows 11 24H2/25H2 с обновлениями апреля 2026+. `signtool verify /v /kp WinDivert64.sys` + фактическая загрузка драйвера
- **E4** — прототип: поставить блокирующий WFP-фильтр из user-mode на Go, без драйвера
- **E2** — *запустить* процесс получения EV-сертификата и выяснения сроков attestation. Идёт фоном до И-10

**DoD дополнительно:**
- Отчёты по E1 и E4 записаны в `docs/experiments/`
- Бэкенд `Redirector` выбран и зафиксирован в ADR-002
- ADR-002 переведён из «под условием E1» в «Принято»

**Разбор Go:** модули и `go.mod`, структура пакетов, `internal/`, сборка под Windows, build-теги, `syscall` и `golang.org/x/sys/windows`.

⚠️ **Развилка:** если E1 провалился — бэкенд `wfpcallout`, и разработка драйвера выносится в отдельный параллельный трек, стартующий здесь же. Продуктовые итерации от него не зависят до И-10.

### И-1. ⭐ Вертикальный срез: «трафик пошёл»

**Цель:** сквозная работающая цепочка на минимальном наборе. Это точка, где проект перестаёт быть бумагой.

**Состав:**
- `net-core`: форк sing-box создан, ребейз-процесс настроен, линкуется как Go-пакет
- `net-svc`: **пока консольное приложение**, не служба Windows. Режим «Прокси»: локальный mixed-inbound (HTTP+SOCKS5) на `127.0.0.1`, один outbound типа SOCKS5
- Декларативная модель `Profile` → транслятор в конфиг ядра (сразу по S3: конфиг генерируется внутри `net-svc`)
- `ProfileStore`: хранение профилей на диске
- `proto`: минимальный контракт — `SessionService.Connect/Disconnect/GetStatus`, `EventService.Subscribe`
- `net-cli`: `connect`, `disconnect`, `status`, `profile add/list`

**Сценарий приёмки:** `net-cli profile add --socks5 ...` → `net-cli connect` → браузер, настроенный на `127.0.0.1:<порт>`, ходит в интернет через указанный SOCKS5-сервер. `net-cli status` показывает живые метрики.

**Баг-чекинг:** порт занят · сервер недоступен · неверные креды · отключение при активных соединениях · повторный connect без disconnect.

**Разбор Go:** интерфейсы и неявная реализация, структуры и методы, `context.Context`, горутины и каналы, `defer`, обработка ошибок и `errors.Is/As`, работа с `net`.

### И-2. Служба Windows и безопасность IPC

**Цель:** перевести `net-svc` в привилегированную службу и закрыть класс уязвимостей до того, как код разрастётся.

**Состав:**
- `net-svc` как служба Windows под LocalSystem, автозапуск, корректная обработка Start/Stop/Shutdown
- Named pipe с явным DACL, `FILE_FLAG_FIRST_PIPE_INSTANCE` (**S1**)
- Верификация клиента: подпись и путь исполняемого файла (**S2**)
- Строгая валидация команд; сырой конфиг ядра от клиента не принимается (**S3** — заложено в И-1, здесь закрепляется тестами)
- Проверка ACL директорий службы при старте, отказ запуска при нарушении (**S5**)
- Режим разработчика с гарантией отсутствия в релизной сборке (проверка на этапе сборки)
- Минимальный инсталлятор: установка службы, директории в `%ProgramFiles%` с правильными ACL

**Сценарий приёмки:** служба ставится инсталлятором, стартует при входе в систему, `net-cli` подключается без прав администратора; попытка подключения из непривилегированного процесса-самозванца отклоняется.

**Баг-чекинг:** гонка «кто первый занял pipe» · подключение двух клиентов · падение службы при активном клиенте · переустановка поверх · удаление.

**Чек-лист безопасности (P-E):** S1, S2, S3, S5.

**Разбор Go:** пакет `golang.org/x/sys/windows/svc`, работа с security descriptors из Go, `net.Listener` поверх named pipe, gRPC-сервер и кастомный диалер, потоковые RPC.

### И-3. ⭐ GUI-каркас

**Цель:** дать живой интерфейс рано, чтобы UX-решения проверялись на практике. Визуальный дизайн — **не сейчас**, только функциональный каркас.

**Состав:**
- `net-gui` на Wails v2: процесс стартует с сессией, живёт в трее, окно скрываемое
- Экран **[1] Подключение**: кнопка с фазами, активный профиль, живые метрики из потока событий
- Трей-меню: статус, быстрое подключение, открыть окно, выход
- Подписка на `EventService`, отображение потока в реальном времени
- Каркас навигации на 7 экранов (пустые заглушки для будущих)
- Буферизация событий на стороне службы — уведомления, произошедшие до старта GUI, не теряются

**Сценарий приёмки:** GUI подключается к службе, кнопка подключает и отключает, метрики обновляются вживую, окно сворачивается в трей и разворачивается.

**Баг-чекинг:** служба не запущена · служба падает при открытом GUI · два экземпляра GUI · быстрое переключение пользователей (**S11**) · разрыв pipe и переподключение.

**Разбор Go:** Wails — привязка Go-методов к фронтенду, события, жизненный цикл приложения; синхронизация состояния между горутинами; `sync` и подводные камни разделяемого состояния.

### И-4. Протоколы

**Цель:** закрыть протокольные требования T1 и Q1.

**Состав:**
- VLESS с TLS / Reality / XTLS-Vision, WS, gRPC
- Hysteria2
- **AmneziaWG** — реализация заимствуется из GPL-форка, интегрируется в `net-core` за build-тегом (ADR-001)
- «Бесплатно» с ядром: VMess, Trojan, Shadowsocks, WireGuard
- Парсер ссылок: `vless://`, `hy2://`, `ss://`, `trojan://`, `vmess://`; импорт из файла и буфера обмена

- Экран **[2] Профили**: список, добавление, редактирование, базовый и расширенный вид (прогрессивное раскрытие)
- **E3** — проверка AmneziaWG против живого сервера

**Сценарий приёмки:** все четыре целевых протокола подключаются; ссылки импортируются; в файлах на диске нет секретов в открытом виде.

**Баг-чекинг:** битая ссылка · неподдерживаемые параметры · протокол-специфичные ошибки хендшейка · AmneziaWG с нестандартными параметрами обфускации · очень длинные и не-ASCII имена.

**Чек-лист безопасности:** S6, S7.

**Разбор Go:** организация кода форка и build-теги на практике, парсинг URL и кодировки, работа с криптографическими типами, взаимодействие с Windows DPAPI через `syscall`.

### И-5. Полный туннель (TUN)

**Цель:** самый функциональный режим. Правила по процессам здесь работают нативно, без драйвера.

**Состав:**
- `TunManager`: загрузка официального `wintun.dll` с проверкой подписи (**S4**), создание адаптера
- `RouteManager`: маршруты `0.0.0.0/1` + `128.0.0.0/1`, `::/1` + `8000::/1`, исключение маршрута до эндпоинта
- **Транзакционность и авто-откат**: снимок состояния сети до изменений, восстановление при выходе, при падении и при старте (P-G, риск R5)
- Watchdog: если служба умерла некорректно — очистка при следующем старте
- Правила по процессам через `process_name` / `process_path` ядра
- Детект конфликта с другими VPN-клиентами (риск R11)

**Сценарий приёмки:** TUN поднимается, весь трафик идёт через туннель, правило на конкретный `.exe` работает; **убийство службы через Task Manager не оставляет систему без интернета**.

**Баг-чекинг:** убийство процесса на середине подключения · отсутствие `wintun.dll` · адаптер уже существует · конфликт с корпоративным VPN · отсутствие прав · перезагрузка с активным туннелем.

**Чек-лист безопасности:** S4.

**Разбор Go:** `cgo` и вызов нативных DLL, `unsafe.Pointer` и правила его использования, финализаторы и почему на них нельзя полагаться, паттерн cleanup через `defer` и сигналы ОС.

### И-6. DNS

**Цель:** без этого доменные правила в TUN не работают (ADR-005).

**Состав:**
- fake-IP с настраиваемым пулом
- Четыре обязательные защиты: авто-фильтр доменов эндпоинтов · предустановленный intranet-фильтр · настраиваемый диапазон · детект петли
- Режим sniffing (SNI / HTTP Host) как переключаемая альтернатива
- DoH/DoT для собственного апстрима
- Тест утечек DNS и IPv6
- Экран **[7] Настройки → DNS**
- **E5** — матрица совместимости fake-IP с типовыми приложениями

**Сценарий приёмки:** доменное правило срабатывает в TUN-режиме; петля на домене эндпоинта детектится и даёт понятную ошибку, а не зависание; тест утечек проходит.

**Баг-чекинг:** домен эндпоинта в fake-IP · приложение с проверкой на `198.18/15` · локальный DNS корпоративной сети · mDNS и WPAD · смена DNS системой на середине сессии.

**Разбор Go:** работа с DNS на уровне пакетов, таблицы соответствия и их конкурентная безопасность, кэши с TTL, `sync.Map` против мьютекса.

### И-7. Маршрутизация

**Цель:** выполнить T3 и T4 в объёме, доступном без драйвера.

**Состав:**
- `RulesEngine`: модель правил, валидация, порядок, транслятор в `route.rules` ядра
- Обе политики (whitelist / blacklist) + действие `BLOCK`
- Матчеры: процесс, домен (точный / суффикс / ключевое слово / regex), IP/CIDR, порт, L4-протокол
- Системные исключения слоя [0] — жёстко зашиты
- **Тестер правил** через dry-run ядра — показывает фактическое решение
- Предупреждения о правилах, перекрытых вышестоящими
- Экран **[3] Маршрутизация**: переключатель политики, вкладки Приложения и Сайты, выбор приложения из запущенных
- Индикатор доступности типов правил в текущем режиме (матрица §4.1 архитектуры)
- Предустановленные наборы: локальная сеть напрямую, реклама и телеметрия в блок

**Сценарий приёмки:** обе политики работают; тестер правил для введённого домена показывает то же решение, что принимает ядро на реальном трафике.

**Баг-чекинг:** противоречивые правила · перекрытые правила · правило на `svchost.exe` · дочерние процессы браузера · очень большой список правил · неверный regex.

**Разбор Go:** проектирование доменной модели, трансляция в чужой формат конфигурации, табличные тесты, property-based тестирование правил.

### И-8. Защита от утечек

**Цель:** закрыть N2, N3 и риск R8 — **без драйвера**, через user-mode WFP (главный вывод исследования).

**Состав:**
- `WfpBlocker` на базе прототипа из E4, доведённый до продакшена
- Kill-switch: блокировка всего трафика мимо туннеля
- Политика IPv6: блокировать / туннелировать / игнорировать
- Детект и опциональная блокировка стороннего DoH (по умолчанию — предупреждать)
- Опциональная блокировка QUIC/HTTP3
- Защита окна переключения при failover
- Экран **[7] Настройки → Безопасность**

**Сценарий приёмки:** при включённом kill-switch и остановленном туннеле трафик не проходит **вообще**; тест утечек показывает отсутствие обходных путей.

**Баг-чекинг:** правила WFP пережили падение службы · конфликт с правилами брандмауэра Windows · снятие правил при штатном выходе · вход в сон с активным kill-switch.

**Разбор Go:** биндинги к `fwpuclnt` через `syscall`, работа с GUID и структурами Windows API, управление временем жизни ресурсов ОС из Go.

### И-9. Живость и резервирование

**Цель:** выполнить T5, T6, T7.

**Состав:**
- **Контур 1** — пассивное наблюдение: доля неуспешных установок, время до первого байта, доля разрывов, стагнация скорости
- **Контур 2** — активная ограниченная проба: 3 замера, оценка по медиане + худшему + доле отказов; фоновый интервал 600 с, в Degraded — 5 с
- FSM: Idle → Connecting → Connected → Degraded → Failing → Failed, с `failThreshold` / `riseThreshold`
- `FailoverChain`: упорядоченный список, fail-back, exponential backoff
- `onAllDown`: `block` (дефолт) / `direct` / `retry` + уведомление в трёх каналах (модальное окно, toast, иконка трея) — **T7**
- Схема данных с полем `chainId` в `RoutingRule` — задел на per-rule цепочки
- Экран **[4] Резервирование**: конструктор цепочки, параметры проб, история переключений, «проверить сейчас»
- Виджет цепочки на экране Подключение с указанием причины последнего переключения

**Сценарий приёмки:** выключаем основной сервер — клиент переключается на резервный по цепочке и показывает причину; выключаем все — появляется модальное окно, трафик блокируется по политике `block`.

**Баг-чекинг:** флаппинг на нестабильном канале · сервер отвечает на TCP, но не пропускает трафик (ловушка L1 против L2) · переключение при активных соединениях · все узлы мертвы при свёрнутом окне · fail-back в момент нагрузки · уведомление до старта GUI.

**Разбор Go:** таймеры и `time.Ticker`, отмена через `context`, реализация конечных автоматов, тестирование зависящего от времени кода без реальных задержек.

### И-10. Системный прокси и Redirector

**Цель:** закрыть режимы 1–2 и требование T3 в лёгких режимах.

**Состав:**
- `SystemProxyManager`: реестр `HKCU`, WinHTTP, PAC-файл через локальный HTTP-сервер
- **Восстановление исходных настроек** при выходе, при падении и при старте (риск R5)
- `Redirector` с бэкендом, выбранным по итогам E1
- Интеграция драйверного бэкенда в инсталлятор
- UI-состояние «Redirector недоступен» с объяснением и предложением перейти в полный туннель
- Тумблер Redirector с честным описанием цены

**Сценарий приёмки:** в режиме «Системный прокси» браузер идёт через туннель без ручной настройки; правило на конкретный `.exe` работает в лёгком режиме; после убийства службы настройки прокси восстановлены.

**Баг-чекинг:** падение с прописанным системным прокси · пользователь менял настройки вручную · Firefox без «использовать системный прокси» · драйвер не загрузился · реакция антивируса (риск R3) · UDP-приложения.

⚠️ **Точка честного разговора.** Если E1 провалился и attestation-подпись по E2 не получена к этому моменту — итерация выпускается **без** `Redirector`, с явным UI-предупреждением, а драйверный трек продолжается отдельно. Это деградация, не отказ.

**Разбор Go:** работа с реестром Windows, взаимодействие с внешним драйвером, `cgo` на границе с C-компонентом.

### И-11. Системная интеграция и диагностика

**Цель:** довести до состояния, пригодного для реальной эксплуатации.

**Состав:**

- Учёт Fast Startup
- Автозапуск и автоподключение
- Экран **[5] Статистика**: графики, трафик, активные соединения
- Экран **[6] Журнал**: уровни, источники, поиск, экспорт диагностического пакета с маскированием (**S7**)

**Сценарий приёмки:** ноутбук уходит в сон с активным туннелем и просыпается в другой сети — клиент восстанавливается автоматически; диагностический пакет собирается в один клик и не содержит секретов.

**Баг-чекинг:** сон в момент подключения · смена Wi-Fi → LAN → док-станция · hotspot · корпоративный VPN поверх · перезагрузка через Fast Startup.

**Разбор Go:** обработка системных событий Windows, окно сообщений из Go, агрегация метрик, буферизованные каналы и backpressure.

## 7. Вход в Фазу 5

Фаза 5 — пересмотр этого плана и **проверка правильности цепочки итераций**. Вопросы, которые нужно задать самому себе в Фазе 5:

1. Нет ли итерации, которая на практике окажется зависимой от более поздней?
2. Не слишком ли крупные И-5 (TUN) и И-9 (резервирование) — не стоит ли их разбить?
3. Правильно ли, что DNS (И-6) идёт **после** TUN (И-5), а не вместе с ним — TUN без DNS даёт только IP-правила?
4. Достаточно ли рано вскрываются риски R3 (антивирусы), R5 (сломанная сеть), R17 (fake-IP ломает приложения)?
5. Не окажется ли И-10 (Redirector) заблокированным внешним сроком Д-4 — и что тогда выпускать?
6. Есть ли итерация без демонстрируемого результата — и можно ли её объединить с соседней?

# E4 — Блокирующие фильтры WFP из user-mode без драйвера

**Статус:** ✅ **Завершён. Результат положительный.**
**Итерация:** И-0
**Подтверждает:** [ADR-002](../adr/ADR-002-traffic-interception.md) — слой `WfpBlocker`; косвенно [ADR-007](../adr/ADR-007-adaptive-interception.md)
**Дата:** 2026-08-24

## Вопрос

Можно ли из пользовательского режима, **без драйвера режима ядра**, поставить фильтр WFP, реально блокирующий сетевой трафик?

От ответа зависело, реализуемы ли без драйвера четыре функции: kill-switch, политика IPv6, блокировка стороннего DoH, блокировка QUIC.

## Метод

Самопроверяющийся стенд [cmd/e4-wfp-probe](../../cmd/e4-wfp-probe/main.go) поверх [internal/platform/wfp](../../internal/platform/wfp/wfp_windows.go). Три замера подряд:

1. соединение до цели **до** установки фильтра → ожидается успех;
2. соединение **после** установки → ожидается отказ;
3. соединение **после** снятия → ожидается успех.

Замеры 1 и 3 отсекают ложный вывод «блокировка работает», когда цель просто недоступна по внешней причине.

Цель: `1.1.1.1:443`. Слой `FWPM_LAYER_ALE_AUTH_CONNECT_V4`, условие `FWPM_CONDITION_IP_REMOTE_ADDRESS`, действие `FWP_ACTION_BLOCK | FWP_ACTION_FLAG_TERMINATING`, подслой `FWPM_SUBLAYER_UNIVERSAL`, вес 15.

Сессия WFP открывается с флагом `FWPM_SESSION_FLAG_DYNAMIC`.

`WSAEACCES` — характерная ошибка именно для блокировки на слое ALE, а не таймаут и не отказ маршрутизации. Блокировка сработала на уровне авторизации соединения, до отправки SYN.

## Выводы

| # | Вывод |
|---|---|
| **1** | **Драйвер режима ядра для блокировок не требуется.** Достаточно user-mode API `fwpuclnt.dll` |
| **2** | Главный вывод исследования (RQ4) подтверждён экспериментально: WFP расщепляется на дешёвую часть (permit/block из user-mode) и дорогую (redirect через callout-драйвер) |
| **3** | Реализуемы без драйвера: kill-switch, политика IPv6, блокировка стороннего DoH, блокировка QUIC, защита окна переключения при failover |
| **4** | Динамическая сессия обеспечивает обратимость: фильтры снимаются системой при завершении процесса, включая аварийное. Проверено на практике — см. ниже |
| **5** | Права администратора обязательны. Не проблема: служба и так работает под LocalSystem ([ADR-006](../adr/ADR-006-privilege-security.md)) |

## Побочный результат: подтверждение принципа P-G

Первый запуск завершился access violation `0xc0000005` внутри `FwpmFilterAdd0` — из-за неверного значения константы `FWP_UINT32` (было `4`, то есть `FWP_UINT64`, у которого член union является **указателем**; правильное значение — `3`).

Процесс умер аварийно: `defer` не отработал, `Close()` не вызвался. **Фильтры при этом сняла система**, связь с целью осталась рабочей — проверено отдельно после падения.

Это подтверждение принципа **P-G**: корректность сетевого состояния не зависит от того, успел ли наш код прибраться. Выбор динамической сессии вместо опоры на `defer` оправдался на первом же сбое.

Разбор краша как учебный материал — [gui_client_study.md](../gui_client_study.md) §6.7.

## Что переходит в продакшн

Код `internal/platform/wfp` написан сразу как основа будущего `WfpBlocker` (итерация И-8), а не как выбрасываемый прототип. Готово: открытие/закрытие динамической сессии, добавление и удаление блокирующего фильтра по IPv4.

Требует доработки в И-8:
- условия для IPv6 (`FWP_BYTE_ARRAY16` вместо `FWP_UINT32`);
- собственный подслой вместо `FWPM_SUBLAYER_UNIVERSAL` — для управления приоритетом относительно правил брандмауэра Windows;
- условия по процессу, порту, протоколу, интерфейсу;
- транзакции WFP для атомарного применения набора правил;
- сохранение фильтров между перезапусками службы там, где это нужно для kill-switch (потребует **не**динамической сессии + собственный механизм очистки при старте).

⚠️ Последний пункт — архитектурная развилка для И-8: kill-switch, переживающий падение службы, требует отказа от динамической сессии, а значит и собственных гарантий обратимости. Решается в И-8, не сейчас.

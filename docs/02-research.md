## Сводка: три вывода, меняющие архитектуру

1. **Драйвер нужен только для одной функции, а не для четырёх.** WFP умеет **блокировать** трафик из user-mode через `fwpuclnt.dll` без всякого драйвера. Значит kill-switch, защита от IPv6-утечек, блокировка стороннего DoH и блокировка QUIC — всё это **без драйвера**. Драйвер режима ядра требуется исключительно для *перенаправления* соединений (`ALE_CONNECT_REDIRECT`), то есть только для правил по приложениям в не-TUN режимах. Это радикально меняет цену решения Q3 — см. §RQ4.

2. **Windows изменил правила игры для драйверов в апреле 2026 — прямо сейчас.** Доверие к legacy cross-signed драйверам снято по умолчанию на Windows 11 24H2/25H2/26H1 и Server 2025. Это ставит под вопрос готовые сторонние драйверы (включая WinDivert) и повышает планку для собственного. См. §RQ11.

3. **AmneziaWG в upstream sing-box не будет — запрос закрыт как «not planned».** Но существуют три живых форка, включая **официальный форк самой Amnezia**. Форк — не запасной план, а штатный путь. См. §RQ1.

### VLESS / Reality / XTLS-Vision — паритет sing-box против Xray-core

| Факт | Метка |
|---|---|
| Оба ядра говорят VLESS, VMess, Trojan, Shadowsocks; оба поддерживают REALITY и TLS; общие транспорты TCP / WebSocket / HTTP2 / gRPC | ✅ |
| sing-box поддерживает **XTLS Vision** (post-handshake fast path) и **XUDP**, интероперабелен с клиентом и сервером Xray | ✅ |
| sing-box **не** поддерживает механизм `fallbacks` внутри VLESS (у Xray) — эквивалент через поле `fallback` в общем блоке `tls` | ✅ |
| sing-box даёт сверх Xray: first-class Hysteria2, TUIC, WireGuard, TUN-inbound — всё в одном движке | ✅ |

**Вывод по RQ1:** `fallbacks` — **серверная** фича, для клиента нерелевантна. Для клиентской стороны **sing-box покрывает 100% требований Q1** (VLESS, Reality, XTLS-Vision, VMess, Trojan, Shadowsocks) плюс Hysteria2 и SOCKS5. Единственный пробел — AmneziaWG, закрывается форком.

> **Кандидат-победитель C1 подтверждён:** одно ядро (форк sing-box) закрывает весь список протоколов заказчика. Второе ядро (Xray-core) **не требуется**. Это устраняет всю сложность мульти-ядерной абстракции (C2).

## RQ4. Перехват по процессам вне TUN — ключевой вопрос P0

### Главная находка: WFP расщепляется на две части с очень разной ценой

| Задача | Требует драйвера? | Метка |
|---|---|---|
| **Блокировать** трафик по условиям (IP, порт, протокол, приложение) | ❌ **Нет.** Достаточно user-mode API `fwpuclnt.dll`: `FwpmEngineOpen`, `FwpmSubLayerAdd`, `FwpmFilterAdd`. Фильтры с действием permit/block ставятся из user-mode | ✅ |
| **Перенаправлять** соединение на локальный прокси (`ALE_CONNECT_REDIRECT`) | ✅ **Да.** Redirect — это действие `callout`, а callout по определению регистрируется kernel-mode драйвером | ✅ |

**Что это значит для нас — переоценка цены решения Q3:**

| Функция | Раньше думали | На самом деле |
|---|---|---|
| Kill-switch | нужен драйвер | **без драйвера** ✅ |
| Блокировка IPv6-утечек | нужен драйвер | **без драйвера** ✅ |
| Блокировка стороннего DoH | нужен драйвер | **без драйвера** ✅ |
| Блокировка QUIC/HTTP3 | нужен драйвер | **без драйвера** ✅ |
| Правила по приложениям в **TUN**-режиме | — | **без драйвера**, sing-box уже умеет `process_name` / `process_path` ✅ |
| Правила по приложениям в **не-TUN** режимах | нужен драйвер | **нужен драйвер** — и это единственное, ради чего он нужен |

> ⭐ **Гипотеза D3 из Фазы 1 подтверждена наполовину и в неожиданную сторону.** Не «драйвер закроет сразу три задачи», а наоборот: **три задачи закрываются без драйвера**, и он остаётся ради одной-единственной функции.

### Варианты реализации редиректа

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **Собственный WFP-калаут** | Регистрируем callout на `FWPM_LAYER_ALE_CONNECT_REDIRECT_V4/V6`, меняем адрес назначения на локальный SOCKS. Штатный, документированный Microsoft механизм | Полный контроль, чистый механизм, не требует сторонних зависимостей | Разработка драйвера с нуля, EV-сертификат, подпись через Partner Center, риск BSOD, отдельный цикл сборки и тестовая ВМ с kernel debugging |
| **WinDivert** | Готовый подписанный драйвер + user-mode API. Перехват и реинжект пакетов | Драйвер писать не надо; есть рабочий прецедент — [ProxyBridge](https://github.com/InterceptSuite/ProxyBridge) (MIT), «альтернатива Proxifier», редирект TCP **и UDP** на HTTP/SOCKS5, Windows 10+ x64, admin | ⚠️ **Статус подписи неясен и вызывает опасения — см. RQ11.** Легко детектируется (WFPExplorer, WinDivertTool), исторически используется вредоносным ПО → антивирусы реагируют |
| **Netfilter SDK (NT Kernel Resources)** | Коммерческий драйвер-перехватчик. Используется в [Netch](https://github.com/netchx/netch) (GPLv3, C#/.NET) | Проверенный прецедент в GPL-проекте | Коммерческая зависимость, для открытого проекта неудобна |

### Отрезвляющий прецедент

**Amnezia VPN** — команда с ресурсами, авторы самого AmneziaWG — на Windows реализовала split tunneling так: **по IP-адресам доступны оба режима, по приложениям — только один режим («выбранные приложения работают без VPN»)**. При этом висит открытый баг [«Windows App-based split tunneling doesn't work»](https://github.com/amnezia-vpn/amnezia-client/issues/2615) (май 2026) и отдельный [issue про LAN-доступ](https://github.com/amnezia-vpn/amneziawg-windows-client/issues/70).

Это ровно тот функционал, который заказчик требует в полном объёме и во всех режимах. Прецедент говорит: задача объективно тяжёлая, и даже профильная команда её не закрыла полностью.

## RQ11. Подпись драйверов — критическое изменение прямо сейчас (P0)

| Факт | Метка |
|---|---|
| С апрельским обновлением 2026 **доверие к legacy cross-signed драйверам снято по умолчанию** на Windows 11 24H2, 25H2, 26H1 и Windows Server 2025 | ✅ |
| Политика вводится в **evaluation mode**: ядро аудирует загрузки драйверов, чтобы оценить совместимость перед принудительным включением | ✅ |
| Программа cross-signing была объявлена устаревшей ещё в 2021; сертификаты под ней истекли | ✅ |
| Формулировка Microsoft: на защищённых системах загружаются драйверы, подписанные через **WHCP**, либо присутствующие в явном allow-list | ✅ |
| **Attestation signing** через Partner Center (EV-сертификат подписывает CAB → Microsoft attestation-подписывает драйвер) — по данным источников, **сохраняет силу** и не затронут изменениями апреля 2026 | 🟡 **Источники расходятся.** Часть формулировок допускает чтение «только WHCP», часть прямо говорит, что attestation остаётся |
| Для submission на attestation или WHCP нужен **EV-сертификат**, привязанный к аккаунту Hardware Dev Center | ✅ |
| Attestation-подписанные драйверы **нельзя** распространять розничной аудитории через Windows Update; WHQL-сертифицированные — можно | ✅ |
| Windows Server 2016+ **отвергает** attestation-подписанные драйверы, принимает только WHQL после HLK-тестов | ✅ |
| Есть сообщения о сбоях attestation-подписи для Windows 11 24H2/25H2 на Hardware Dashboard | 🟡 |
| Windows 11 24H2 усилил проверку подписи драйверов; неподписанные Microsoft сторонние драйверы блокируются | 🟡 |

### Статус WinDivert — ⚠️ главный нерешённый вопрос фазы

| Факт | Метка |
|---|---|
| Актуальная версия — WinDivert 2.2 | ✅ |
| Готовые `WinDivert32.sys` / `WinDivert64.sys` из официальной поставки **подписаны цифровой подписью** | ✅ |
| **Каким именно способом подписаны — в документации и FAQ не указано.** FAQ упоминает только получение Software Publisher Certificate (SPC) в коммерческом УЦ — а это описание **именно legacy cross-signing** | ⚠️ |
| Ошибка **577 «Windows cannot verify the digital signature»** при загрузке WinDivert — документированная, воспроизводившаяся проблема | ✅ |

⚠️ **Это блокирующая неопределённость.** Если официальный WinDivert подписан по схеме cross-signing (а формулировки FAQ на это указывают), то он **перестаёт загружаться** на актуальных Windows 11 по мере выхода политики из evaluation mode. Тогда весь путь «взять готовый WinDivert» рушится, и остаётся только собственный драйвер с attestation-подписью.

**Разрешается только экспериментом**, и эксперимент дешёвый: взять машину с Windows 11 24H2/25H2 и апрельскими+ обновлениями, поставить WinDivert, посмотреть `signtool verify /v /kp WinDivert64.sys` и попытаться загрузить драйвер. **Это первое, что нужно сделать в Фазе 4 — до написания строчки кода.**

## RQ6. fake-IP DNS на практике (P2)

Найдены конкретные, воспроизводимые проблемы — все они должны быть закрыты защитными механизмами в нашем коде:

| Проблема | Суть | Что делать |
|---|---|---|
| **Петля DNS** | Ядро возвращает fake-IP на домен **собственного прокси-сервера** → трафик виснет молча, upstream-соединение установить невозможно | Домены всех активных outbound-эндпоинтов **автоматически** вносятся в fake-ip-filter. Не оставлять это пользователю |
| **Конфликт диапазона `198.18.0.0/15`** | Это официально зарезервированный под бенчмаркинг диапазон. Некоторые приложения имеют защитные проверки и **отказываются** соединяться с адресами из него, хотя TUN маршрутизирует их корректно | Диапазон fake-IP должен быть **настраиваемым**; иметь готовый альтернативный пул |
| **Отсутствие fake-ip-filter ломает интранет и CGNAT** | Внутренние и carrier-grade NAT сервисы работают по обычному Wi-Fi, но отваливаются через туннель | Предустановленный фильтр: локальные домены, `*.local`, mDNS, WPAD, домены Active Directory |
| **DNS-утечки при неверной конфигурации** | Запросы уходят мимо прокси | Явная политика DNS + встроенный тест утечек |

**Вывод:** fake-IP обязателен для доменных правил в TUN, но требует «обвязки безопасности». Нужен и режим **redir-host / sniffing** как альтернатива — для приложений, которые fake-IP ломает.

| Находка | Метка |
|---|---|
| `URLTest` в sing-box ранжирует аутбаунды **одним скаляром** — временем до получения заголовков ответа на HEAD-запрос. Измеряет достижимость и RTT | ✅ |
| Признано ограничением: открыт [запрос на bandwidth-aware режим URLTest](https://github.com/SagerNet/sing-box/issues/4397). Там же зафиксирована правильная схема: **пассивное наблюдение** обнаруживает деградацию активного аутбаунда → запускается **активная ограниченная проба** альтернатив | ✅ |
| Одиночный замер искажается DNS-кэшем, джиттером, временной нагрузкой и троттлингом на стороне назначения. Корректно — **несколько запросов, смотреть медиану, худшее время и число отказов** | ✅ |
| Типовой интервал латентного теста у зрелых клиентов — 600 секунд | ✅ |
| DPI смотрит на сигнатуры протокола: паттерны TLS-хендшейка, заголовки, поведение соединения | ✅ |

**Вывод — модель проб из Фазы 1 §6.1 подтверждается и уточняется:**
- Основная проба — **L2** (HTTP-запрос через прокси), как и планировали. ✅
- Одного скаляра **мало** — нужны медиана, худшее и success-rate по окну. Это ровно то, что заложено в `failThreshold` / `riseThreshold`.
- **Добавить пассивное наблюдение**: деградация реального пользовательского трафика — более честный и более быстрый сигнал, чем периодическая активная проба. Активные пробы альтернатив запускать **по триггеру от пассивного наблюдения**, а не по таймеру. Это экономит трафик и ускоряет реакцию.
- Интервал 600 с у зрелых клиентов — против моих 30 с из Фазы 1. Мой дефолт слишком агрессивен для фонового режима; правильно: редкая фоновая проба + быстрая проба по триггеру.

## RQ8. CVE в привилегированных VPN-клиентах (P2)

Это раздел, ради которого стоило проводить исследование. Каждая мера S1–S8 из Фазы 1 имеет реальный прецедент нарушения:

| CVE-2025-26168, CVE-2025-26169 и др. | IXON VPN Client | Три уязвимости, LPE на Windows и Linux | Подтверждает: это **системная болезнь класса**, а не частный случай |

**Вывод:** риск R4 («LPE-уязвимость в IPC службы») из Фазы 1 недооценён — я поставил вероятность «средняя». По факту **этой ошибкой переболели практически все крупные VPN-клиенты, включая OpenVPN и AWS**. Поднимаю до «высокая». Меры S1–S8 переходят из «желательных практик» в **обязательные acceptance-критерии итерации**, с отдельным чек-листом ревью.

## RQ9. Выбор стека — с учётом разрешённой линковки (P1)

### Что изменилось после Фазы 1

Два факта переопределили задачу:
1. GPL-3.0 разрешает линковать sing-box как библиотеку (Q2).
2. AmneziaWG требует **форка** sing-box (RQ1) — значит мы в любом случае будем собирать Go-код.

Из (2) следует: **Go в проекте будет обязательно**, независимо от выбора стека. Вопрос не «Go или Rust», а «где проходит граница между Go-ядром и остальным».

### Три конфигурации

| # | Конфигурация | Прецедент | Оценка |
|---|---|---|---|
| **A. Всё на Go** | Служба на Go, ядро линкуется напрямую как пакет, GUI на Wails (Go + WebView2, бинарь ~8 МБ) | Wails v2 стабилен, применяется в проде, поддерживает подпись кода и упаковку MSI; трей, нативные диалоги, меню — есть | ⭐ Один язык, один тулчейн, один CI. Прямой доступ к внутренностям ядра без FFI и без IPC-сериализации. Минимальный размер |
| **B. Go-ядро как разделяемая библиотека + GUI на другом языке** | Ровно модель **Hiddify**: Go-ядро → `libcore` с C-ABI → FFI-биндинги в Flutter/Rust/C# | ✅ Доказано в проде на всех платформах | Свобода в выборе GUI ценой FFI-границы и двух тулчейнов |
| **C. Ядро отдельным процессом + IPC** | Модель **Clash Verge Rev** (Tauri/Rust + Mihomo sidecar) | ✅ Доказано в проде | Максимальная изоляция отказов (идея Amnezia), но теряем прямой доступ к rule-engine и метрикам, ради которого и добивались права на линковку |

### Предварительная рекомендация к Фазе 3

**Конфигурация A (всё на Go, GUI на Wails)** — при следующих аргументах:
- Форк sing-box неизбежен → Go-экспертиза и Go-CI нужны в любом случае. Второй язык добавляет стоимость, не добавляя возможностей.
- Прямая линковка даёт доступ к rule-engine, списку соединений, метрикам и hot-reload — то, ради чего выбиралась GPL-3.0.
- Форк `sing-box-lx` уже содержит **headless-демон `lxd`** и gRPC CommandClient — это буквально готовая заготовка под принцип P1 (headless-first) и под Linux server edition.
- Wails даёт ~8 МБ против ~70 МБ у self-contained .NET и ~150 МБ у Electron.
- Путь на Linux/macOS: Go + Wails кроссплатформенны из коробки.

**Контраргументы, требующие честного взвешивания в Фазе 3:**
- ⚠️ Go — не лучший язык для **драйвера** и для тонкой работы с Windows API (WFP, службы, WinDivert). Потребуется CGO или отдельный нативный компонент. Драйвер в любом случае будет на C.
- ⚠️ Wails на Windows использует WebView2 — это внешняя зависимость (обычно предустановлена в Win11, но не гарантированно в Win10).
- ⚠️ .NET 10 **уже установлен** в среде и даёт лучшую в классе интеграцию с Windows — для службы это заметное преимущество. Но ценой второго тулчейна и FFI/IPC-границы к Go-ядру.

Окончательный выбор — в Фазе 3, вместе с решением по драйверу.

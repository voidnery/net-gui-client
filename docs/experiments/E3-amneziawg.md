# E3 — совместимость обфускации AmneziaWG с живыми серверами

| | |
|---|---|
| **Вопрос** | Можно ли реализовать обфускацию AmneziaWG 2.0 поверх sing-box так, чтобы её принимали настоящие серверы заказчика? |
| **Статус** | ✅ Завершён, положительный результат |
| **Дата** | 2026-08-26 |
| **Стенд** | `cmd/e3-awg-probe`, серверы `ams1` и `fin1` заказчика |
| **Итог** | Обфускация реализована в форке `net-core/wireguard-go`, трафик идёт через туннель на обоих серверах |

## Как проверялось

Проба `cmd/e3-awg-probe` измеряет внешний IP-адрес дважды: напрямую и через
локальный прокси поднятого ядра. Совпадение адреса с адресом сервера — это
доказательство того, что туннель работает, а не только «соединение
установилось».

Критерий выбран намеренно жёстким. Рукопожатие может пройти, а данные не
ходить — именно так и выглядел один из найденных дефектов, и проверка
«подключились ли мы» его бы не заметила.

```
$ go run -tags "with_wireguard,with_quic,with_gvisor" ./cmd/e3-awg-probe testdata/live/test2-ams1.awg.conf

[1] Внешний адрес без туннеля ... <адрес провайдера>
[3] Ожидание установления туннеля ... готово
[4] Внешний адрес ЧЕРЕЗ туннель ... <адрес ams1>
✅ ПОЛОЖИТЕЛЬНЫЙ: трафик идёт через туннель AmneziaWG.
```

То же самое на `fin1`: адрес сменился на адрес `fin1`.

> Адреса и параметры обфускации серверов заказчика в этом документе заменены
> описанием. Они не являются ключами, но однозначно опознают трафик к
> конкретному серверу, а репозиторий публичный. Проверить вывод целиком можно
> локально: конфигурации лежат в `testdata/live`, закрытом `.gitignore`.

## Что выяснилось

### 1. Подмена типа обязана происходить внутри сборки сообщения

Первая реализация была обёрткой над UDP-датаграммами: пакет собирался
стандартным wireguard-go, а обфускация накладывалась снаружи. Сервер молча
отбрасывал всё.

Причина — область покрытия MAC1:

```
mac1 = MAC(HASH(LABEL_MAC1 || Spub_responder), msg[0 : offset_of_mac1])
```

Поле типа входит в эту область. Подмена после вычисления MAC даёт расхождение,
и пакет отбрасывается без диагностики.

Отсюда решение вести форк `wireguard-go` (ADR-001): снаружи задача не решается
в принципе, а не «решается неудобно».

### 2. Диагностика важнее догадок

Дефект долго не поддавался, потому что я рассуждал о причинах, не имея
измерений. Ключевой перелом наступил, когда в приёмный путь добавили счётчик
входящих датаграмм **до** классификации: выяснилось, что сервер отвечает — то
есть рукопожатие принято, — а отказ происходит дальше.

До этого «рукопожатие не проходит» было выводом, а не наблюдением. Два разных
дефекта — «нас не слышат» и «мы не понимаем ответ» — выглядели одинаково.

Диагностика оставлена в `device/awg_debug.go` за переменной окружения
`NETGUI_AWG_DEBUG=1`. Секретов она не печатает: только размеры пакетов и
значения заголовков.

### 3. Транспортные пакеты тоже несут подменённый тип

Подмена была реализована только для пакетов рукопожатия. Сессия при этом
устанавливалась успешно, но данные сервер отбрасывал, и отказ выглядел так:

```
peer(sHYI…jWWg) - received handshake response
peer(sHYI…jWWg) - retrying handshake because we stopped hearing back after 15 seconds
```

Исправлено подменой на `H4` в `RoutineEncryption`.

### 4. H1..H4 — это диапазоны, а не константы

Главная находка эксперимента. После исправления (3) сервер начал присылать
данные, но клиент их отбрасывал:

```
recv: 96 байт, заголовок=62 → НЕ ОПОЗНАН
первые байты = 3e000000 xxxxxxxx 0000000000000000 …
                 ↑тип     ↑индекс      ↑счётчик
```

Структура — обычный транспортный заголовок WireGuard: тип, индекс получателя,
счётчик, дальше шифротекст. Но в поле типа стоит `62`, а `H4` у этого сервера
оканчивается байтом `0x3E`, то есть `62`, — при том что само значение `H4`
занимает все четыре байта и на `62` не похоже.

На `fin1` картина та же: в поле типа `147`, и `H4` этого сервера оканчивается
байтом `0x93`, то есть `147`.

В обоих случаях наблюдаемое значение — младший байт `H4`. Эталон
`amneziawg-go` объясняет причину: заголовки хранятся как `UintRange`,
отправитель берёт значение через `PickOne()`, а получатель проверяет
`Contains()`. **Точное сравнение неверно принципиально** — оно случайно
работало для рукопожатия и обязано было отказать на данных.

Решение: пакеты рукопожатия опознаются по паре «размер + заголовок» (их размер
фиксирован, и этого достаточно), а пакет данных — **по остатку**: всё, что не
подошло ни под один пакет рукопожатия и не короче транспортного заголовка.
Ошибка такой классификации безопасна: дальше идёт поиск индекса получателя, и
чужой пакет отсеивается там же, где его отсеивает обычный WireGuard.

Закреплено тестом `TestClassifyTransportWithForeignHeader`
(`net-core/wireguard-go/device/awg_test.go`), проверенным мутацией: возврат
точного сравнения роняет тест.

## Что осталось за рамками

- **Мусорные пакеты (Jc/Jmin/Jmax)** отправляются и принимаются, но их влияние
  на обнаружение не измерялось: для этого нужен наблюдатель на пути трафика.
  Проверено лишь то, что они не мешают рукопожатию.
- **Совместимость с AmneziaWG 2.0** в части `I1..I5`, `Itime` и шифрования
  заголовков не проверялась: конфигураций с этими параметрами у нас нет.
  Текущая реализация соответствует набору `Jc/Jmin/Jmax/S1/S2/H1..H4`.

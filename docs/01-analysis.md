- **D1.** GPL-3.0 делает возможной прямую линковку sing-box → нужно исследовать, что даёт линковка сверх запуска процессом (доступ к внутреннему rule-engine, метрикам соединений, hot-reload конфига без разрыва) — RQ1, RQ9.

## 0. Границы и допущения

**В границах:**
- Desktop GUI-клиент для Windows 10/11 x64 (первичная цель).
- Протоколы: SOCKS5, AmneziaWG, VLESS, Hysteria2, «XRAY» (см. §2.1 — терминологическое уточнение), плюс расширяемость на другие.
- Три режима работы соединения: системный прокси / прокси / полный туннель.
- Раздельная маршрутизация (split-tunneling) по приложениям и по сайтам, две политики.
- Мониторинг живости и настраиваемое резервирование (failover).
- UX-архитектура: карта страниц, навигация, состояния.

**Вне границ на этом этапе:**
- Визуальный UI-дизайн (отдельная итерация по вашему указанию).
- Серверная часть / панель управления / биллинг.
- Порты Linux/macOS — но архитектура **обязана** их не блокировать (см. §10.4).
- Мобильные платформы.

**Допущения (требуют подтверждения):**
- A1. Клиент — «bring your own server»: пользователь импортирует свои конфиги/подписки. Своей инфраструктуры серверов нет.
- A2. Один одновременно активный «маршрут наружу» (не multi-hop цепочка из нескольких прокси подряд). Failover переключает, а не агрегирует.
- A3. Целевая аудитория — обычные пользователи, а не сисадмины: сложность прячем за разумными дефолтами.
- A4. Распространение — не через Microsoft Store (Store-песочница несовместима с драйверами/службами).

## 1. Разбор исходного требования

Разложим формулировку заказчика на атомарные утверждения и выявим неявное.

| # | Явное требование | Неявное следствие |
|---|---|---|
| T1 | Поддержка SOCKS5, AmneziaWG, VLESS, XRAY, Hysteria2 «и других» | Нужна **абстракция «транспорт/аутбаунд»** и плагинная модель. Разные протоколы реализуются разными ядрами → нужен супервизор процессов и единый конфиг-транслятор |
| T2 | Три режима: системный прокси / прокси / полный туннель | Это **три разных механизма перехвата трафика** с принципиально разной глубиной охвата. Режим — свойство *сессии*, не *профиля* |
| T3 | Во **всех** режимах — правила по приложениям и сайтам | ⚠️ **Конфликт**: в чистом «системном прокси» перехват по процессу невозможен без доп. механизма (см. §4.4). Это главный архитектурный вопрос фазы |
| T4 | Две политики: «принудительно через туннель» / «принудительно мимо» | Это не два режима, а **default-policy + список исключений**. Формализуем в §5 |
| T5 | Автоопределение живости туннеля/прокси | Нужна подсистема проб (health-check) с метриками, окнами и гистерезисом |
| T6 | Настраиваемая система резервирования путей | Пользователь задаёт **упорядоченную цепочку** (или граф) переходов. Нужен конечный автомат + политика fail-back |
| T7 | Если всё мертво — всплывающее уведомление | Нужен слой уведомлений. И **критичный незаданный вопрос**: что делать с трафиком в этот момент — блокировать (kill-switch) или пускать напрямую? |
| T8 | UI-дизайн — позже, UX — сейчас | Проектируем информационную архитектуру, навигацию, состояния и тексты, но не визуал |
| T9 | Windows сейчас, Linux (GUI + **server edition**) и macOS потом | ⚠️ «Server edition» = **headless**. Значит ядро продукта — это демон с API, а GUI — лишь один из клиентов. Фундаментально влияет на архитектуру, см. §10.4 |
| T10 | Итеративная разработка с рефакторингом и баг-чекингом каждой итерации | Нужен CI, тесты и «definition of done» на итерацию с самого начала |

### 1.1. Требования, которые заказчик не назвал, но без которых продукт нерабочий

Это не расширение скоупа — это то, без чего T1–T7 не выполняются корректно:

- **N1. DNS.** Без управления DNS все правила «по сайтам» и вся приватность разваливаются (DNS-утечки, резолв мимо туннеля). В TUN-режиме доменные правила вообще невозможны без fake-IP DNS. **Это блокирующее требование для T3.**
- **N2. Kill-switch / leak protection.** Прямое следствие T7 и T6: в момент переключения между узлами есть окно, когда трафик может уйти в открытую.
- **N3. IPv6.** Если система имеет IPv6, а туннель — нет, трафик утечёт мимо. Нужна явная политика (блокировать / туннелировать / игнорировать).
- **N4. Импорт конфигураций.** Пользователь должен как-то завести профиль: ссылки `vless://`, `hy2://`, файлы `.conf` (AmneziaWG), подписки (subscription URL), QR, JSON.
- **N5. Автозапуск и восстановление сессии** после ребута/сна/смены сети (Wi-Fi → LAN, VPN на роутере, hotspot).
- **N6. Обновления.** Обновляться должен и GUI, и служба, и **ядра протоколов** (они меняются часто, и от версии ядра зависит работоспособность).
- **N7. Хранение секретов.** Приватные ключи AmneziaWG, UUID VLESS, пароли — это секреты. Нужна политика хранения (DPAPI / Credential Manager / шифрованный файл).
- **N8. Диагностика.** Пользователь «не подключается» — нужен собираемый в один клик диагностический пакет, иначе поддержка невозможна.

## 2. Доменная модель и глоссарий

### 2.1. Терминологическое уточнение по «XRAY» ⚠️

В списке протоколов смешаны сущности разных уровней:

| Названо | Что это на самом деле |
|---|---|
| SOCKS5 | Протокол прокси (RFC 1928). Транспорт |
| VLESS | Протокол проксирования (обычно поверх TLS/XTLS/Reality/WS/gRPC). Реализуется ядрами Xray-core и sing-box |
| Hysteria2 | Протокол поверх QUIC/UDP с собственным congestion control. Своё ядро + поддержан в sing-box |
| AmneziaWG | **Форк WireGuard** с обфускацией (доп. параметры Jc/Jmin/Jmax/S1/S2/H1–H4). Отдельная реализация |
| XRAY | **Не протокол, а ядро** (Xray-core, форк v2ray-core). Внутри: VMess, VLESS, Trojan, Shadowsocks, Reality, XTLS-Vision и т.д. |

**Вопрос к вам (Q1):** под «XRAY» имеется в виду поддержка *остального набора протоколов Xray-core* (VMess, Trojan, Shadowsocks, Reality) — или конкретно требование использовать именно ядро Xray-core как движок? От ответа зависит §9.

### 2.2. Основные сущности

```
Profile (профиль подключения)
  ├─ id, name, tags, group
  ├─ Outbound (транспорт наружу)
  │    ├─ kind: socks5 | vless | trojan | vmess | ss | hysteria2 | amneziawg | wireguard | direct | block
  │    ├─ endpoint (host, port)
  │    ├─ credentials (secret-ref → защищённое хранилище)
  │    └─ transport-specific params (tls/reality/ws/grpc/quic/obfs...)
  ├─ source: manual | link | subscription(id) | file
  └─ health-policy-ref

Subscription
  └─ url, interval, last-sync, profiles[], user-agent, filters

Session (активное подключение)
  ├─ mode: SystemProxy | Proxy | FullTunnel
  ├─ activeProfile, chainState
  ├─ interceptor (что реально перехватывает трафик)
  ├─ routing-policy-ref
  └─ metrics (up/down, conns, latency)

RoutingPolicy (правила маршрутизации)
  ├─ defaultAction: Proxy | Direct
  ├─ rules[]: { matcher, action: Proxy|Direct|Block, priority }
  └─ dnsPolicy

Matcher (предикат)
  └─ processPath | processName | domain(suffix/keyword/regex) | geosite
     | ip/cidr | geoip | port | l4proto | network(wifi ssid)

FailoverChain
  ├─ nodes[]: profileId
  ├─ strategy: ordered | latency-based | round-robin
  ├─ probe: { type, target, interval, timeout, failThreshold, riseThreshold }
  ├─ failBack: none | auto(delay) | manual
  └─ onAllDown: notify + (block | direct | retry-loop)
```

## 4. Анализ трёх режимов работы

Это ядро задачи. Режимы различаются **механизмом перехвата** — от него зависит, какие правила вообще реализуемы.

### 4.1. Режим «Прокси» (локальный listener)

Клиент поднимает на `127.0.0.1` локальные inbound-порты: HTTP CONNECT и/или SOCKS5 (+ опционально «mixed»). Системные настройки **не трогаются**. Пользователь сам направляет приложения в этот порт.

- Права: **обычный пользователь**, админ не нужен.
- Охват: только то, что явно настроено.
- Правила по доменам: **да** (домен виден в CONNECT/SOCKS5-запросе).
- Правила по процессам: **частично** — можно определить владельца TCP-соединения через `GetExtendedTcpTable`/`GetExtendedUdpTable` для соединений с localhost, но это работает только для тех, кто уже пришёл к нам. «Заставить» приложение идти в прокси нельзя.
- UDP: только через SOCKS5 UDP ASSOCIATE, если приложение это умеет (почти никто не умеет).
- Риски: минимальные. Это самый безопасный и самый «слабый» режим.

### 4.2. Режим «Системный прокси»

То же самое + прописывание адреса прокси в системные настройки:
- `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` (`ProxyEnable`, `ProxyServer`, `ProxyOverride`, `AutoConfigURL`) + уведомление `InternetSetOption(INTERNET_OPTION_SETTINGS_CHANGED | INTERNET_OPTION_REFRESH)`.
- Опционально WinHTTP (`netsh winhttp set proxy` / `WinHttpSetDefaultProxyConfiguration`) — для служб и части .NET-приложений.
- Переменные окружения `HTTP_PROXY`/`HTTPS_PROXY` — для консольных утилит (только для новых процессов).

Характеристики:
- Права: HKCU — обычный пользователь; WinHTTP (машинный) — **админ**.
- Охват: приложения, уважающие WinINet/WinHTTP — Chrome, Edge, IE, большинство .NET, Office. **Не охвачены**: Firefox (своя настройка, если не «использовать системный прокси»), Telegram/Discord/Steam (свои настройки), игры, весь UDP, весь не-HTTP трафик.
- Правила по доменам: **да**, двумя путями: (а) внутри нашего локального прокси по имени хоста из CONNECT; (б) через PAC-файл (`AutoConfigURL` → наш локальный HTTP-сервер отдаёт `.pac`). PAC полезен, чтобы «direct»-трафик вообще к нам не заходил.
- Правила по процессам: ⚠️ **невозможно нативно**. Мы видим только TCP-соединение к нашему listener'у; определить процесс можно (§4.1), и даже отказать ему — но «отказать» ≠ «пустить напрямую»: приложение уже отправило запрос в прокси и получит ошибку, а не прямое соединение. **Значит T3 в этом режиме требует отдельного механизма** — см. §4.4.
- Побочный эффект: настройки прокси глобальны для пользователя. Падение клиента без корректной очистки = «интернет пропал». Нужен watchdog, восстанавливающий исходное состояние.

### 4.3. Режим «Полный туннель» (TUN)

Создаётся виртуальный сетевой адаптер (на Windows — драйвер **Wintun**), в систему прописываются маршруты (классика: `0.0.0.0/1` + `128.0.0.0/1`, чтобы перебить default route, не удаляя его; плюс `::/1` + `8000::/1` для IPv6), исключая маршрут до самого VPN-сервера. Весь L3-трафик приходит нам, разбирается собственным сетевым стеком (userspace TCP/IP или system-stack) и раскладывается по правилам.

- Права: **администратор** (установка драйвера, создание адаптера, изменение таблицы маршрутизации).
- Охват: **весь** трафик всех процессов, TCP+UDP+ICMP.
- Правила по процессам: **да** — по владельцу соединения (`GetExtendedTcpTable`), это работает надёжно, т.к. соединение приходит к нам до выхода наружу.
- Правила по доменам: ⚠️ на L3 домена нет, есть только IP. Два решения:
  - **fake-IP DNS**: мы отвечаем на DNS-запросы фиктивными адресами из зарезервированного пула (напр. `198.18.0.0/15`), запоминаем `fake-IP → домен`, и при появлении соединения на fake-IP восстанавливаем домен. Даёт 100% доменных правил, но ломает приложения, кэширующие IP или работающие с реальными IP.
  - **SNI/HTTP Host sniffing**: разбор первого пакета TLS ClientHello / HTTP-запроса. Не требует fake-IP, но не работает для не-TLS/не-HTTP и для ECH (Encrypted Client Hello).
  - На практике нужны **оба** + переключатель. `[R]`
- Риски: самый инвазивный режим. Некорректный выход = сломанная маршрутизация, «нет интернета». Нужны транзакционность и авто-откат.

### 4.4. ⚠️ Ключевая проблема: T3 против режимов 1–2

Требование «во всех режимах правила по приложениям» в режимах «прокси»/«системный прокси» **не выполняется штатными средствами Windows**. Варианты решения (выбор — после Фазы 2):

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **V1. Честное ограничение** | В режимах 1–2 правила только по доменам/IP. Правила по процессам доступны только в TUN. UI явно это показывает | Просто, безопасно, без драйверов | Формально не выполняет T3 |
| **V2. WFP connect-redirect** | Свой WFP-калаут или WinDivert: перехват на `ALE_CONNECT_REDIRECT`, перенаправление соединений выбранных процессов на локальный SOCKS. Так работает Proxifier | Полное выполнение T3 без TUN, точечный охват | Нужен **драйвер режима ядра** (подпись EV/WHQL либо использование WinDivert), высокий риск ложных срабатываний антивирусов, сложная отладка, риск BSOD |
| **V3. TUN + per-process default-direct** | Всегда поднимаем TUN, но в «лёгких» режимах default-политика = Direct, а в туннель уходят только выбранные процессы. Режимы становятся *пресетами политики*, а не разными механизмами | Один механизм на всё, максимум возможностей, минимум кода | Всегда нужны админ-права и драйвер Wintun; «системный прокси» теряет смысл как отдельный режим |
| **V4. Гибрид** | Режимы 1–2 = как в V1; отдельный **опциональный** тумблер «расширенный перехват приложений», включающий V2 | Честно, постепенно, риск изолирован в опции | Больше кода, два кодовых пути |

**Предварительная рекомендация была:** V4 (V1 в MVP, V2 после).

**✅ РЕШЕНИЕ ЗАКАЗЧИКА (Q3): вариант V2 — драйвер режима ядра включается в MVP.**

Что это влечёт и что теперь обязано попасть в исследование и план:
- Выбор механизма: **WinDivert** (готовый, подписанный Microsoft драйвер, LGPL/GPL — совместим с нашей GPL-3.0) против **собственного WFP-калаута** (полный контроль, но своя подпись, WHQL/аттестация, риск BSOD). — RQ4.
- Админ-права становятся обязательными **во всех режимах**, включая «прокси». Это удаляет главное преимущество лёгких режимов и означает, что служба нужна всегда. Пересматриваем §7 (строка UAC) и модель установки.
- Ложные срабатывания антивирусов из «вероятных» (R3) переходят в **почти гарантированные**. Требуется план: подпись кода, submission вендорам, документация для пользователей.
- Появляется новый инструментальный контур: тестовая ВМ с test-signing и kernel debugging, отдельный цикл сборки драйвера.
- ⭐ Возможное упрощение (D3): если WFP уже в системе, он же может закрыть **kill-switch** (блокировка всего трафика мимо туннеля) и **блокировку стороннего DoH/QUIC**. То есть один механизм вместо трёх разных. Проверить в Фазе 2.

## 5. Анализ раздельной маршрутизации (split-tunneling)

### 5.1. Формализация «двух режимов»

Заказчик описал две политики. Формализуем как **default action + список исключений**:

| Пользовательское название | Формально | Типичный сценарий |
|---|---|---|
| «Только выбранное через туннель» | `default = DIRECT`, правила → `PROXY` | Обойти блокировку конкретных сайтов, остальное — напрямую (быстро) |
| «Всё через туннель, кроме выбранного» | `default = PROXY`, правила → `DIRECT` | Приватность по умолчанию; исключаем банк-клиент, локальную сеть, игры |

Плюс третье действие, необходимое технически: **`BLOCK`** (для kill-switch, блокировки рекламы/телеметрии, блокировки IPv6/QUIC).

### 5.2. Порядок разрешения правил

Порядок критичен и должен быть **явным и видимым пользователю**. Предлагаемый конвейер:

```
соединение
  → [0] системные исключения (loopback, RFC1918, endpoint самого VPN, DHCP/DNS-инфра)
  → [1] правила процесса          (самые специфичные, известны сразу)
  → [2] правила домена            (если домен известен: fake-IP / sniff / CONNECT)
  → [3] правила IP / GeoIP
  → [4] правила порт / протокол
  → [5] default action
```

Открытый вопрос `[R]`: «первое совпадение выигрывает» (как в Clash/sing-box) или «самое специфичное выигрывает». Первое проще объяснить и отладить; второе удобнее пользователю. Вероятно — первое + UI, показывающий эффективный порядок и предупреждающий о «мёртвых» правилах, перекрытых вышестоящими.

### 5.3. Подводные камни

- **Правила по процессу и дочерние процессы.** Правило на `chrome.exe` — а что с рендерер-процессами? С `svchost.exe`, через который ходит половина системы? Нужно решение: сопоставление по полному пути, поддержка wildcard, явное предупреждение для системных хостов. `[R]`
- **Домен известен не всегда.** Прямое соединение по IP, ECH, DoH внутри приложения (Chrome/Firefox — по умолчанию!) — домен не виден. Chrome с включённым DoH обходит наш DNS → доменные правила ломаются. Нужна политика: блокировать сторонний DoH (по известным IP/портам) или мириться. `[R]`
- **QUIC/HTTP3.** Многие сайты уходят в UDP/443. Если наш путь плохо тянет UDP — типовое решение «блокировать QUIC, деградировать до TCP». Должно быть опцией.
- **Локальная сеть.** Принтеры, NAS, RDP — почти всегда должны быть `DIRECT`. Предустановленное правило по умолчанию.
- **Сам VPN-сервер.** Маршрут до endpoint'а обязан идти мимо туннеля, иначе петля. Управляется автоматически, не пользователем.

## 6. Анализ живости и резервирования

### 6.1. Что значит «жив»

Три разных уровня, которые нельзя смешивать:

| Уровень | Что проверяем | Метод |
|---|---|---|
| L1. Транспорт поднят | Процесс ядра жив, listener слушает, handshake прошёл | Локальная проверка процесса/сокета, парсинг логов ядра |
| L2. Туннель проходим | Через прокси проходит соединение до внешней цели | HTTP GET `204` через наш SOCKS/HTTP inbound; для WG — handshake + ping внутрь туннеля |
| L3. Качество приемлемо | Задержка, потери, стабильность | Скользящее окно измерений RTT и success-rate |

⚠️ Ловушка: наивная проба «TCP connect до endpoint сервера» проверяет только L1 и **регулярно врёт** — сервер отвечает на TCP, но трафик через него не идёт (заблокирован, исчерпан лимит, DPI режет). Основная проба должна быть **L2**.

### 6.2. Состояния соединения (FSM)

```
      ┌──────────┐
      │   Idle   │
      └────┬─────┘
           │ connect()
      ┌────▼───────────┐   fail    ┌──────────────┐
      │  Connecting    ├──────────►│   Failed     │
      └────┬───────────┘           └──────┬───────┘
           │ L1+L2 ok                     │ next in chain
      ┌────▼───────────┐                  │
      │   Connected    │◄─────────────────┘
      └────┬──────▲────┘
   L3 деградация  │ riseThreshold успешных проб подряд
      ┌────▼──────┴────┐
      │   Degraded     │  (работает, но плохо — предупреждение, не переключение)
      └────┬───────────┘
           │ failThreshold неудач подряд
      ┌────▼───────────┐
      │   Failing      │ → переключение на следующий узел цепочки
      └────────────────┘
```

Ключевые параметры (все настраиваемые, с разумными дефолтами):
- `interval` — период пробы (деф. 30 с в покое, 5–10 с в состоянии Degraded)
- `timeout` — таймаут одной пробы (деф. 5 с)
- `failThreshold` — сколько подряд неудач считать отказом (деф. 3) — **защита от флаппинга**
- `riseThreshold` — сколько подряд успехов считать восстановлением (деф. 2) — **гистерезис**
- `backoff` — экспоненциальная пауза перед повтором (деф. 2× до 5 мин)

### 6.3. Цепочка резервирования

Модель: **упорядоченный список профилей** + стратегия.

- `ordered` — строгий приоритет: 1 → 2 → 3 (точно соответствует формулировке заказчика «какое подключение каким сменяется»). Дефолт.
- `latency-based` — выбирать наименьшую задержку из живых. `[R]` — нужно ли в MVP.
- `round-robin` — по кругу. Низкий приоритет.

**Fail-back** (возврат на приоритетный, когда он ожил): опция `none | auto (после N минут стабильности) | manual`. Дефолт — `auto`, но с заметной задержкой, чтобы не дёргать соединение.

⚠️ **Переключение — это разрыв соединений.** Все активные TCP-сессии умрут. Нужна честная коммуникация в UI + опция «graceful»: дождаться дренажа старых соединений N секунд.

**Предвосхищаю развитие требования:** пользователи почти всегда потом хотят цепочку **не глобальную, а на группу правил** («для стриминга — цепочка A, для остального — цепочка B»). Архитектура должна допускать `RoutingRule → ChainId`, даже если в MVP цепочка одна. Это дёшево заложить сейчас и дорого добавить потом.

### 6.4. «Всё упало» (T7)

Действия при отказе всех узлов цепочки:
1. Показать модальное окно + toast + сменить иконку в трее (все три канала, т.к. окно может быть свёрнуто).
2. **Применить политику `onAllDown`** — обязательный явный выбор пользователя:
   - `block` (kill-switch) — трафик блокируется. **Рекомендуемый дефолт**, безопасно.
   - `direct` — пустить напрямую. Удобно, но это молчаливая деанонимизация. Требует явного согласия при включении.
   - `retry` — продолжать пробовать по кругу с backoff, трафик заблокирован до успеха.
3. Не спамить: одно уведомление на инцидент, а не на каждую пробу.

## 8. Модель привилегий и безопасности

### 8.1. Разделение на два процесса — обязательно

```
┌────────────────────────────┐        ┌───────────────────────────────────┐
│  GUI (сессия пользователя, │  IPC   │  Служба (LocalSystem, автозапуск) │
│  без прав администратора)  │◄──────►│                                   │
│                            │ Named  │  • TUN-адаптер, маршруты, WFP     │
│  • Отрисовка, ввод         │  Pipe  │  • Системный прокси               │
│  • Трей, уведомления       │        │  • Супервизор процессов-ядер      │
│  • Локальные настройки UI  │        │  • Health-check, failover FSM     │
│                            │        │  • Хранилище профилей/секретов    │
└────────────────────────────┘        └───────────────────────────────────┘
                                                    │ управляет
                                       ┌────────────┴─────────────┐
                                       │  Процессы ядер           │
                                       │  (пониженные привилегии) │
                                       └──────────────────────────┘
```

### 8.2. Поверхность атаки — главный риск класса «VPN-клиент»

Локальная служба с правами SYSTEM, принимающая команды по IPC, — **классический источник LPE-уязвимостей** (локальное повышение привилегий). Обязательные меры, закладываемые с первой итерации:

- **S1.** ACL на named pipe: доступ только членам конкретной группы / интерактивным пользователям; явный запрет сетевого доступа. Никаких `NULL DACL`.
- **S2.** Верификация клиента: проверка подписи и пути исполняемого файла подключившегося процесса, а не только его SID.
- **S3.** Строгая валидация всех входящих команд. Служба **не** принимает от GUI произвольные пути к исполняемым файлам, произвольные аргументы ядру или произвольный сырой конфиг для запуска. Только декларативная модель + генерация конфига **внутри службы**.
- **S4.** Ядра запускаются из фиксированной, защищённой ACL директории (`%ProgramFiles%`), с проверкой хеша/подписи бинарника перед запуском. Иначе — тривиальная подмена и исполнение под SYSTEM.
- **S5.** Директория данных службы недоступна на запись обычным пользователям.
- **S6.** Секреты (ключи, UUID, пароли) — не в открытом виде. DPAPI (machine scope для службы) или AES-ключ в Credential Manager.
- **S7.** Логи не должны содержать секретов; маскирование при экспорте диагностики.
- **S8.** Обновления — только по HTTPS с проверкой подписи пакета. Автообновление службы SYSTEM — отдельный повышенный риск.

### 8.3. Приватность
- Телеметрия по умолчанию **выключена**, opt-in, с явным описанием состава.
- Никаких обращений «домой» при старте, кроме явно настроенных подписок и проверки обновлений (тоже с выключателем).

## 9. Анализ реализации протоколов

### 9.1. Карта «протокол → чем реализуется»

| Протокол | Возможные реализации | Заметки |
|---|---|---|
| SOCKS5 / HTTP | Любое ядро; тривиально реализуется самостоятельно | Единственный, который реально сделать своими силами |
| VLESS (+TLS/Reality/XTLS-Vision/WS/gRPC) | Xray-core, sing-box | Reality/Vision — территория Xray; sing-box поддерживает, но паритет фич надо проверять `[R]` |
| VMess / Trojan / Shadowsocks | Xray-core, sing-box | Идут «бесплатно» вместе с ядром |
| Hysteria2 | hysteria (референс), sing-box | UDP/QUIC; чувствителен к качеству UDP-пути и к congestion control |
| WireGuard | sing-box (userspace), wireguard-windows (ядро) | — |
| **AmneziaWG** | amneziawg-go / amneziawg-windows; **в mainline sing-box, по имеющимся данным, отсутствует** | ⚠️ **Главный риск фазы.** Требует либо отдельного процесса/библиотеки, либо форка ядра. Прямая проверка в Фазе 2 |

### 9.2. Стратегические варианты (решение — после Фазы 2)

- **C1. Единое ядро (sing-box) + отдельный AmneziaWG.** Один конфиг-формат, один rule-engine, один TUN. AmneziaWG — либо отдельный процесс с выводом в SOCKS, либо форк ядра.
- **C2. Мульти-ядро с абстракцией.** Каждый протокол — своё ядро (Xray для VLESS/Reality, hysteria для Hy2, awg для AmneziaWG), а маршрутизация/TUN — наш собственный слой. Максимум паритета фич, максимум сложности.
- **C3. Собственная реализация протоколов.** Отвергается: месяцы работы, гарантированные ошибки в криптографии, невозможность поспевать за эволюцией Reality/Hysteria.

### 9.3. ⚠️ Лицензионный вопрос — блокирующий `[R]`

Лицензии ядер напрямую определяют, может ли продукт быть закрытым/коммерческим. По имеющимся у меня данным (**обязательна перепроверка в Фазе 2**):

- **sing-box — GPL-3.0.** Линковка как библиотеки → ваш код обязан быть GPL-3.0. Запуск как **отдельного процесса** обычно трактуется как aggregation и не «заражает» — но это юридическая, а не техническая граница.
- **Xray-core — MPL-2.0** (файловый copyleft, значительно мягче).
- **Hysteria — MIT.**
- **Wintun** — условия распространения требуют отдельной проверки для коммерческого использования.
- **WinDivert** — двойное LGPL/GPL.

**✅ РЕШЕНИЕ ЗАКАЗЧИКА (Q2): проект открытый под GPL-3.0.**

Последствия — все в плюс:
- sing-box можно **линковать как Go-библиотеку**, а не только запускать отдельным процессом. Это даёт доступ к внутреннему rule-engine, к списку соединений, к метрикам и к hot-reload конфига — то, что через process-границу получить трудно или невозможно.
- WinDivert (LGPL/GPL) становится юридически доступен — важно после решения Q3.
- Xray-core (MPL-2.0) и Hysteria (MIT) совместимы с GPL-3.0 в направлении «включить в GPL-проект».
- ⚠️ Остаётся обязанность: публиковать исходники, включая изменения в GPL-компонентах, и корректно оформить `COPYING`/`NOTICE` с указанием всех зависимостей.
- ⚠️ Wintun распространяется на **собственных условиях** (не GPL) — проверить отдельно в RQ2, это не снято ответом Q2.

**Пересмотр §9.2:** вариант **C1 (единое ядро sing-box + AmneziaWG)** становится ведущим кандидатом, причём AmneziaWG можно решать форком/патчем ядра, а не отдельным процессом. **Это же сильно смещает выбор стека к Go** (§10.2, S2), т.к. линковка Go-библиотеки требует Go в привилегированной части.

```
│ Orchestration   FSM сессии │ Failover │ Health-check      │
│                 Профили │ Подписки │ Правила              │
├───────────────────────────────────────────────────────────┤
│ Platform        TUN │ Маршруты │ WFP │ Системный прокси   │
│                 DNS │ Служба │ Уведомления                │
├───────────────────────────────────────────────────────────┤
│ Cores           sing-box / Xray / hysteria / amneziawg    │
└───────────────────────────────────────────────────────────┘
```

**Инвариант:** слои Orchestration и выше — платформонезависимы. Всё платформозависимое живёт только в слое Platform, за интерфейсами. Это и есть цена входа в Linux/macOS (T9).

### 10.2. Варианты технологического стека `[R]`

| # | Стек | За | Против |
|---|---|---|---|
| S1 | **Rust + Tauri 2** (GUI) + служба на Rust | Малый размер, нет рантайма, отличный системный доступ, хорошая кроссплатформенность, безопасность памяти в привилегированном коде | Ядра на Go — только как внешние процессы; экосистема Tauri моложе; Rust не установлен в среде |
| S2 | **Go + Wails**, ядра как библиотеки | Тот же язык, что у sing-box/Xray/hysteria → возможна прямая линковка и полный контроль | GPL-заражение при линковке sing-box (§9.3); GUI = webview; Go не установлен |
| S3 | **C# .NET 10 + WPF/WinUI 3**, ядра как процессы | ⭐ **.NET SDK 10 уже установлен**; лучшая в классе интеграция с Windows (службы, WMI, реестр, WFP через P/Invoke); быстрая разработка GUI; сильная типизация | Кроссплатформенный GUI слабее (Avalonia решает, но это доп. выбор); нужен рантайм или self-contained сборка (~70 МБ) |
| S4 | **Electron / Node + нативные модули** | Node 22 установлен; максимальная скорость UI-разработки; огромная экосистема | Тяжёлый рантайм (150+ МБ), высокое потребление памяти, слабый системный доступ, привилегированная часть всё равно нужна на другом языке |
| S5 | **Гибрид: служба на Rust/Go + GUI на любом** | Разделение по IPC уже требуется (§8.1) → языки могут быть разными и выбираться по задаче | Два тулчейна, два CI, сложнее сборка и отладка |

Наблюдение: поскольку §8.1 **всё равно** требует разделения GUI и службы через IPC, S5 — не компромисс, а естественное следствие. Вопрос сводится к двум независимым выборам: язык привилегированной службы и технология GUI.

### 10.3. Контракт IPC `[R]`

Кандидаты: gRPC поверх named pipe; JSON-RPC 2.0 поверх named pipe; собственный протокол «длина + JSON». Требования: двунаправленность (нужен **поток событий** от службы к GUI — статусы, метрики, логи, срабатывания failover), версионирование, обратная совместимость (GUI и служба могут обновляться независимо), низкие накладные расходы для потока метрик.

### 10.4. Headless-first — следствие T9

Раз планируется **Linux server edition**, это должно быть архитектурным принципом с первого дня, а не «допилим потом»:

> **Принцип P1.** Служба/демон полностью функциональна без GUI. Любое действие GUI выражается вызовом публичного API. GUI не содержит бизнес-логики — только представление и ввод.

Проверяемое следствие: должна существовать CLI-утилита, покрывающая 100% функций GUI. Она же — лучший инструмент интеграционного тестирования.

## 11. UX-архитектура (карта приложения)

Визуал не трогаем; проектируем структуру, навигацию и состояния.

### 11.1. Карта навигации

```
Трей-иконка (всегда)
 ├─ Статус: [цвет] Подключено / Отключено / Проблема
 ├─ Быстрое подключение ▸ (последние 5 профилей)
 ├─ Режим ▸ (Системный прокси / Прокси / Полный туннель)
 ├─ Политика ▸ (Только выбранное / Всё кроме выбранного)
 ├─ Открыть окно
 └─ Выход

Главное окно
 ├─ [1] Подключение          — домашний экран
 ├─ [2] Профили              — список серверов/подписок
 ├─ [3] Маршрутизация        — правила split-tunneling
 ├─ [4] Резервирование       — цепочки и проверки живости
 ├─ [5] Статистика           — трафик и соединения
 ├─ [6] Журнал               — логи и диагностика
 └─ [7] Настройки            — общие / сеть / DNS / безопасность / о программе
```

### 11.2. Содержание экранов

**[1] Подключение** — главный экран, оптимизирован под «один клик».
- Крупная кнопка Подключить/Отключить с явными фазами: `Отключено → Подключение → Рукопожатие → Проверка → Подключено`.
- Активный профиль (с быстрой сменой), режим работы, применённая политика.
- Живые метрики: задержка, скорость вверх/вниз, время сессии, внешний IP и локация.
- **Виджет цепочки резервирования**: визуальная цепочка `[● Основной] → [○ Резерв 1] → [○ Резерв 2]` с подсветкой активного и «мёртвых» узлов. Пользователь должен видеть факт переключения, не заходя в другие вкладки.
- Плашка предупреждения при состоянии `Degraded`.

**[2] Профили**
- Список/группы, поиск, теги. Колонки: имя, протокол, задержка, статус последней пробы.
- Действия: добавить (ссылка / QR / файл / вручную / из буфера), дублировать, тест задержки (одиночный и групповой), удалить.
- Подписки: URL, интервал обновления, «обновить сейчас», отчёт о диффе после синхронизации.
- Редактор профиля: базовый вид (host/port/креды) + расширенный (TLS/Reality/транспорт/MTU/обфускация). **Прогрессивное раскрытие**: не пугать новичка полем `Jmin`.

**[3] Маршрутизация**
- Наверху — крупный переключатель политики: «Только выбранное через туннель» / «Всё через туннель, кроме выбранного», с пояснением на человеческом языке, что это значит прямо сейчас.
- Две вкладки: **Приложения** и **Сайты**.
  - Приложения: список с иконками и путями, кнопка «Добавить приложение» — файловый диалог **и** «выбрать из запущенных» (второе гораздо удобнее), поиск.
  - Сайты: домены/маски/GeoSite/IP/CIDR, ввод построчно, импорт списков.
- Предустановленные наборы правил: «Локальная сеть — напрямую», «Российские сайты — напрямую», «Реклама и телеметрия — блокировать».
- **Тестер правил**: поле «введите домен или выберите приложение» → показывает, какое правило сработает и какое действие применится. Критично для отладки, снимает большую часть обращений в поддержку.
- Предупреждения о недоступности правил по приложениям в текущем режиме (§4.4) — прямо в интерфейсе, а не в документации.

**[4] Резервирование**
- Конструктор цепочки: drag-n-drop упорядоченного списка профилей.
- Параметры проб: тип, цель, интервал, таймаут, пороги отказа и восстановления.
- Политика fail-back и `onAllDown` (block / direct / retry) — с честным предупреждением о рисках варианта `direct`.
- История переключений: когда, с чего на что, по какой причине.
- Кнопка «Проверить цепочку сейчас» — прогоняет все узлы и показывает результат.

**[5] Статистика** — графики скорости, суммарный трафик за сессию/день/месяц, топ процессов и доменов по трафику, список активных соединений с указанием применённого действия и маршрута.

**[6] Журнал** — уровни (error/warn/info/debug), источник (GUI / служба / ядро), поиск, автопрокрутка, «Скопировать», «Экспортировать диагностику» (логи + маскированный конфиг + сетевое состояние в zip).

**[7] Настройки** — Общие (автозапуск, автоподключение, свернуть в трей, язык, тема, обновления) · Сеть (порты inbound, MTU, IPv6-политика, блокировка QUIC, доверенные сети) · DNS (серверы, DoH/DoT, fake-IP, проверка утечек) · Безопасность (kill-switch, `onAllDown`, блокировка стороннего DoH) · Дополнительно (пути к ядрам, версии, сброс к заводским) · О программе.

### 11.3. Ключевые UX-принципы

- **U1. Обратимость.** Любое изменение сети должно откатываться. Если клиент упал — система остаётся рабочей (watchdog + очистка при старте).
- **U2. Никаких молчаливых состояний.** Пользователь всегда должен видеть: подключён ли он, через что именно, и покрыт ли трафик конкретного его приложения.
- **U3. Прогрессивное раскрытие.** Обычный режим прост. Экспертные параметры свёрнуты, но доступны без «редактирования JSON руками».
- **U4. Честность про безопасность.** Опции, снижающие защиту (`onAllDown = direct`, отключение kill-switch), сопровождаются понятным предупреждением, а не мелким шрифтом.
- **U5. Объяснимость.** Тестер правил, история переключений, живая цепочка — пользователь должен понимать, *почему* система ведёт себя так, а не иначе.
- **U6. Уведомления не спамят.** Одно уведомление на инцидент, с возможностью отключить категории.

### 11.4. Критические UX-состояния, требующие проработки

Не только «всё хорошо», но и: первый запуск (нет профилей) · подключение зависло · переключение по failover (все соединения оборваны) · все узлы мертвы (T7) · служба не запущена или не установлена · нет прав · драйвер не установился · подписка не синхронизировалась · конфликт с другим VPN-клиентом · нет сети вообще.

# ADR-005: DNS-стратегия — fake-IP с обвязкой безопасности и режим sniffing

**Статус:** Принято
**Дата:** 2026-08-24
**Решает:** требование N1, RQ6, риски R7, R8, R17

## Контекст

DNS — блокирующее требование для T3, а не отдельная фича. В режиме полного туннеля перехват идёт на L3, где есть только IP-адрес; домена нет. Без механизма восстановления домена **все правила по сайтам в TUN не работают**.

Два известных механизма:
- **fake-IP**: на DNS-запрос отдаём фиктивный адрес из зарезервированного пула, запоминаем связь `fake-IP → домен`, при появлении соединения восстанавливаем домен. Покрытие ~100%.
- **sniffing**: разбираем первый пакет — SNI из TLS ClientHello или Host из HTTP-запроса. Не требует подмены DNS, но не работает для не-TLS/не-HTTP трафика и для ECH (Encrypted Client Hello).

Исследование выявило конкретные, воспроизводимые способы, которыми fake-IP ломает работу:

| Проблема | Проявление |
|---|---|
| **Петля DNS** | Ядро возвращает fake-IP на домен собственного прокси-сервера → трафик виснет молча, upstream установить невозможно |
| **Конфликт диапазона `198.18.0.0/15`** | Диапазон зарезервирован под бенчмаркинг; часть приложений имеет защитные проверки и **отказывается** соединяться с такими адресами, хотя TUN маршрутизирует корректно |
| **Отсутствие фильтра ломает интранет и CGNAT** | Внутренние и carrier-grade NAT сервисы работают по обычному Wi-Fi, но отваливаются через туннель |
| **DNS-утечки** | При неверной конфигурации запросы уходят мимо прокси |

Отдельная проблема: Chrome и Firefox по умолчанию используют собственный DoH и **обходят системный резолвер** — доменные правила при этом молча перестают работать.

## Решение

**fake-IP — режим по умолчанию, но только вместе с четырьмя обязательными защитами. Режим sniffing — переключаемая альтернатива.**

### Четыре обязательные защиты fake-IP

1. **Авто-фильтр эндпоинтов.** Домены всех активных outbound-эндпоинтов автоматически вносятся в `fake-ip-filter` при каждой смене конфигурации. Не оставляется на усмотрение пользователя — это защита от петли, а не настройка.
2. **Настраиваемый пул.** Диапазон fake-IP выбирается пользователем; по умолчанию — `198.18.0.0/15`, с готовым альтернативным вариантом на случай конфликта с приложениями.
3. **Предустановленный intranet-фильтр.** `*.local`, mDNS, WPAD, домены Active Directory, локальные суффиксы — по умолчанию мимо fake-IP.
4. **Детект петли.** Служба активно проверяет, что домен активного эндпоинта не резолвится в fake-IP, и при обнаружении переходит в состояние ошибки с понятным сообщением, а не виснет.

### Режим sniffing

Переключатель в Настройках → DNS с объяснением на человеческом языке: fake-IP даёт полное покрытие доменных правил, sniffing — совместимость с приложениями, которые fake-IP ломает.

### Политика стороннего DoH

Детект известных DoH-эндпоинтов (по IP и портам) + опциональная блокировка через `WfpBlocker` (ADR-002, user-mode WFP, драйвер не нужен). По умолчанию — **предупреждать, не блокировать**: молчаливая блокировка чужого DoH сама по себе неожиданна для пользователя.

### Прочее

- DNS-запросы для проксируемых доменов резолвятся **на стороне сервера**, а не локально.
- Встроенный тест утечек DNS и IPv6 на экране Диагностики.
- Поддержка DoH/DoT для собственного апстрима.

## Рассмотренные варианты

### A. Только fake-IP

**Плюсы:** максимальное покрытие доменных правил, простая модель.
**Минусы:** документированно ломает часть приложений; без обвязки даёт молчаливые зависания — худший тип отказа.

### B. Только sniffing

**Плюсы:** ничего не подменяет, максимальная совместимость.
**Минусы:** не покрывает не-TLS/не-HTTP трафик и ECH; доменные правила становятся частичными и непредсказуемыми — пользователь не понимает, почему правило сработало для одного сайта и не сработало для другого.

### C. fake-IP + обвязка + переключаемый sniffing ✅

**Плюсы:** покрытие по умолчанию максимальное; известные способы поломки закрыты явными защитами; для несовместимых сценариев есть выход, а не тупик.
**Минусы:** два кодовых пути; больше настроек, которые надо объяснить пользователю; обвязка — это работа, которую легко недооценить.

## Анализ компромиссов

**Покрытие против совместимости.** Это классическая развилка, и оба чистых варианта плохи: A даёт полное покрытие с непредсказуемыми поломками, B — предсказуемость с дырами в функциональности. Гибрид дороже обоих, но это единственный вариант, где пользователь не оказывается в тупике.

**Молчаливый отказ — худший режим.** Петля DNS и конфликт диапазона проявляются как «просто не работает», без сообщения. Поэтому защиты 1 и 4 не опциональны: цена их отсутствия — обращения в поддержку, которые невозможно диагностировать.

## Последствия

**Становится проще:**
- Доменные правила работают во всех трёх режимах.
- Известные способы поломки закрыты до первого пользователя.

**Становится сложнее:**
- Два режима резолва на сопровождении.
- Настройки DNS требуют объяснений в UI — иначе это экран, который никто не тронет.
- Нужна матрица совместимости приложений (E5).

**Что придётся пересмотреть:**
- Если E5 покажет массовые поломки на fake-IP — сменить дефолт на sniffing.
- ECH по мере распространения будет постепенно обесценивать sniffing → зависимость от fake-IP вырастет.

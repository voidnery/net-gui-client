# ADR-007: Адаптивный выбор механизма перехвата, отказ от собственного драйвера

**Статус:** Принято
**Дата:** 2026-08-24
**Заменяет:** решение о бэкенде в [ADR-002](ADR-002-traffic-interception.md). Двухслойная модель перехвата и интерфейс `Redirector` из ADR-002 остаются в силе
**Основано на:** [E1](../experiments/E1-windivert.md), [E2](../experiments/E2-driver-signing.md)

## Контекст

Решением Q3 заказчик подтвердил готовность к драйверу режима ядра ради правил по приложениям во всех режимах (требование T3). Два эксперимента изменили условия задачи:

**E1 — WinDivert непригоден.** Официальный `WinDivert64.sys` не имеет подписи Microsoft ни в каком виде: подписант — посторонняя проекту китайская организация, сертификат коммерческого УЦ Sectigo, истёкший 26.05.2023, валидность держится на метке времени. Это ровно та конфигурация, против которой направлена политика апреля 2026.

**E2 — доступного пути к подписи собственного драйвера нет.**

| Путь | Статус |
|---|---|
| Azure Trusted Signing (~$10/мес) | ❌ подпись драйверов Windows не поддерживается |
| SignPath Foundation (бесплатно для OSS) | ❌ выдаёт OV, Partner Center требует EV |
| Cross-signing | ❌ закрыт политикой апреля 2026 |
| EV-сертификат | 💰 от **$280/год рекуррентно**; с 15.02.2026 срок ограничен одним годом |

Заказчик не готов к рекуррентным расходам.

**Два факта, найденных при разборе живого AmneziaVPN на машине заказчика:**

1. `wintun.sys` подписан **Microsoft Windows Hardware Compatibility Publisher** (издатель — Microsoft Windows Third Party Component CA 2012). Wintun поставляется готовым и правильно подписанным — **нам не нужно подписывать ничего**, чтобы поднять TUN-адаптер.
2. В TUN-режиме sing-box поддерживает правила по процессам **нативно** (`process_name`, `process_path`) — драйвер с нашей стороны не требуется.

Из (1) и (2) следует: **механизм для выполнения T3 уже существует и бесплатен.** Вопрос лишь в том, когда его включать.

### Признание ошибки Фазы 1

Вариант V3 («всегда TUN, режимы как пресеты политики») был отвергнут в [01-analysis.md](../01-analysis.md) §4.4 с формулировкой *«убивает главное преимущество лёгких режимов — работу без админ-прав»*.

Формулировка неверна. Преимущество исчезло при принятии [ADR-006](ADR-006-privilege-security.md) — службы под LocalSystem, устанавливаемой инсталлятором. Админ-права стали разовой стоимостью установки, а не платой за каждый запуск. К моменту решения по Q3 лёгкие режимы уже не давали того преимущества, ради которого V3 отвергался.

## Решение

**Механизм перехвата выбирается автоматически по тому, что требуют текущие правила и режим — а не жёстко привязывается к названию режима. Собственный драйвер режима ядра из проекта исключается.**

| Условие | Механизм | TUN поднят |
|---|---|---|
| Режим «Прокси» или «Системный прокси», правил по процессам нет | Локальный listener (+ системные настройки прокси в соответствующем режиме) | ❌ |
| Любой режим, задано хотя бы одно активное правило по процессу | TUN, `defaultAction = DIRECT`, правила уводят в `PROXY` | ✅ |
| Режим «Полный туннель» | TUN, `defaultAction = PROXY` | ✅ |

Смена условия влечёт пересборку сессии — это разрыв активных соединений, и он должен быть предсказуем для пользователя (см. Последствия).

**Что сохраняется:**
- Двухслойная модель перехвата из ADR-002: `WfpBlocker` (user-mode WFP, без драйвера) остаётся обязательным слоем для kill-switch, IPv6, DoH и QUIC.
- Интерфейс `Redirector` остаётся в коде. Реализаций — ноль. Это точка расширения, а не мёртвый код: появится бюджет на EV или Microsoft разрешит подпись драйверов через Azure Trusted Signing — бэкенд `wfpcallout` добавляется без изменения архитектуры.

**Что исключается:** трек Д-1…Д-5 (разработка драйвера, тестовый контур с kernel debugging, EV-сертификат, attestation-submission, submission антивирусным вендорам).

## Рассмотренные варианты

### A. Купить EV-сертификат и разработать драйвер

| Измерение | Оценка |
|---|---|
| Стоимость | **$280+/год рекуррентно** + месяцы разработки |
| Сложность | Высокая |
| Риск | Высокий (R3, R13, R14) |
| Выполнение T3 | Полное |

**Плюсы:** единственный вариант, дающий правила по приложениям **без** поднятия TUN.
**Минусы:** отвергнут заказчиком по стоимости; вносит три высоких риска; добавляет компонент, требующий отдельной экспертизы и бессрочного сопровождения подписи.

### B. Всегда TUN (исходный V3)

**Плюсы:** один механизм на всё, минимум кода, T3 выполняется полностью, стоимость $0.
**Минусы:** постоянный overhead userspace-стека даже при `defaultAction = DIRECT`; постоянный риск конфликта с другими VPN (R11); постоянно повышенный риск R5 («интернет пропал»); нагрузка на CPU и батарею — даже когда пользователь не задал ни одного правила.

### C. Адаптивный выбор механизма ✅

| Измерение | Оценка |
|---|---|
| Стоимость | **$0** |
| Сложность | Средняя |
| Риск | Низкий |
| Выполнение T3 | Полное |

**Плюсы:** T3 выполняется полностью; стоимость подписи нулевая; риски R3, R13, R14 снимаются; лёгкие режимы остаются лёгкими, пока пользователь не задал правил по процессам; из проекта уходит целый компонент.
**Минусы:** механизм перестаёт быть предсказуемым «по названию режима» — требуется явная индикация в UI; появление первого правила по процессу молча меняет характеристики работы, если это не показать; логика выбора механизма — дополнительное место для ошибок.

### D. Перехват в user-mode через инъекцию DLL и перехват `connect()`

Прецедент: `socksifier`, ранние версии Proxifier и ProxyCap.

**Плюсы:** драйвера нет, подписи не нужно, лёгкие режимы остаются лёгкими всегда.
**Минусы:** ❌ **не работает для приложений в AppContainer** — соединения к localhost им запрещены, а это Edge, все UWP-приложения и Store-приложения; конфликты с античит-системами и защищёнными процессами; инъекция DLL — устойчивый триггер антивирусов, хуже чем драйвер; нужна отдельная реализация для x86 и x64; хрупкость при обновлениях приложений. По совокупности хуже варианта C по всем измерениям, кроме одного.

### E. Отложить `Redirector`, правила по приложениям только в полном туннеле

**Плюсы:** проще всего, стоимость $0.
**Минусы:** формально не выполняет T3 — в лёгких режимах правил по приложениям нет вообще. Вариант C даёт то же самое **и** выполняет T3, за счёт автоматического поднятия TUN. Строго хуже C.

## Анализ компромиссов

**Предсказуемость против лёгкости.** Вариант B прост и предсказуем: TUN всегда, поведение одно. Вариант C сложнее, но не платит за TUN, когда он не нужен. Компромисс разрешается в пользу C при условии, что **выбор механизма явно виден в UI** — иначе выигрыш в лёгкости оборачивается проигрышем в понятности, а это нарушает принцип U2 («никаких молчаливых состояний»).

**Полнота T3 против стоимости.** Вариант A — единственный, дающий правила по приложениям без TUN. Мы сознательно жертвуем этим сценарием: пользователь, которому нужны правила по приложениям, получает их — ценой поднятого туннеля. Сценарий «хочу правила по приложениям, но принципиально против TUN» остаётся непокрытым. По совокупности он не стоит $280/год плюс месяцев разработки.

**Долг перед решением Q3.** Заказчик подтверждал готовность к драйверу. Мы это решение отменяем — но не сужая функциональность: T3 выполняется полностью. Меняется способ, а не результат.

## Последствия

**Становится проще:**
- Из проекта уходит самая рискованная и самая долгая по календарю часть.
- Риски R13 (сроки подписи) и R14 (BSOD) снимаются полностью; R3 (антивирусы) резко снижается — остаётся только реакция на службу и Wintun, которые есть у любого VPN-клиента.
- Единственный внешний неконтролируемый срок в проекте исчезает — план перестаёт зависеть от Partner Center.
- MVP сокращается на целую итерацию.

**Становится сложнее:**
- Появляется логика выбора механизма и переходы между механизмами на лету.
- **Смена механизма разрывает активные соединения.** Пользователь, добавивший правило по процессу в лёгком режиме, получит разрыв. Требуется предупреждение до применения, а не после.
- UI обязан показывать, какой механизм активен и почему. Без этого нарушается U2.
- Терминология смещается: «режим» — это пресет политики, а не механизм перехвата. Тексты интерфейса нужно писать соответственно.

**Что придётся пересмотреть:**
- Если появится бюджет на EV — вернуть бэкенд `wfpcallout` за интерфейсом `Redirector`; архитектура это допускает без переделки.
- Если Microsoft разрешит подпись драйверов через Azure Trusted Signing — то же самое, но дешевле.
- Если адаптивная логика окажется источником путаницы у пользователей — откатиться к варианту B (всегда TUN), это упрощение, а не переделка.

## 0. Почему Go и как он устроен

### Зачем нам именно Go

Не «потому что модно». Причина строго техническая и изложена в [ADR-003](adr/ADR-003-tech-stack.md): ядро протоколов sing-box написано на Go, а нам нужен его форк ([ADR-001](adr/ADR-001-protocol-core.md)). Значит Go-тулчейн в проекте будет в любом случае. Взять второй язык для службы — значит платить за два тулчейна и за границу между ними, ничего не получая взамен.

### Три вещи, которые стоит понять сразу

**1. Компиляция в один статический бинарник.** Go компилируется в machine code, а не в байт-код. Нет рантайма, который надо ставить отдельно, нет DLL-зависимостей (кроме тех, что вы явно подключили). Наш `net-svc.exe` — один файл, который просто работает. Это прямая причина, почему GUI на Wails весит ~8 МБ против ~70 МБ у self-contained .NET.

**2. Сборщик мусора есть, но он не как в Java/C#.** Go GC оптимизирован под низкие паузы, а не под пропускную способность. Для сетевого приложения с тысячами одновременных соединений это правильный компромисс.

**3. Язык намеренно маленький.** В Go нет наследования классов, нет исключений, нет перегрузки операторов, нет тернарного оператора. Дженерики появились только в 1.18 и используются сдержанно. Это раздражает первую неделю и начинает нравиться на второй месяц: чужой код читается почти без разгона, потому что способов написать одно и то же немного.

### Чего в Go нет и чем это заменяется

| Привычно из C#/Java | В Go | Как вместо этого |
|---|---|---|
| `class` с наследованием | Нет | `struct` + встраивание (composition) |
| `try/catch/finally` | Нет | Возврат `error` вторым значением + `defer` |
| `null` для любого типа | Есть только для ссылочных | Нулевые значения типов: `0`, `""`, `nil` для указателей, слайсов, map, каналов |
| `Thread` / `Task` | Нет | Горутины — в тысячи раз дешевле потоков ОС |
| `async/await` | Нет | Горутины блокируются, а рантайм сам мультиплексирует их на потоки |
| `IEnumerable`, LINQ | Нет | Явные циклы. Многословнее, но однозначно |
| Свойства (`get`/`set`) | Нет | Публичные поля или явные методы |

### Именование как часть языка

В Go регистр первой буквы — **это модификатор доступа**, а не стилевое соглашение:

```go
type Profile struct {
    ID      string   // экспортируется — виден из других пакетов
    Name    string   // экспортируется
    secret  string   // НЕ экспортируется — виден только внутри своего пакета
}
```

Заглавная буква = `public`. Строчная = виден только внутри пакета. Никаких ключевых слов. Это касается всего: типов, функций, полей, методов, констант.

Для нас это важно практически: в [ADR-006](adr/ADR-006-privilege-security.md) мера **S6** требует, чтобы секреты не утекали. Неэкспортируемое поле `secret` физически недоступно другим пакетам — компилятор не даст. Язык помогает соблюдать архитектурную границу.

## 1. Модули, пакеты, структура репозитория

### Модуль

Модуль — единица версионирования и зависимостей. Описывается файлом `go.mod` в корне:

```
module github.com/bbesport/net-gui-client

go 1.26

require (
    github.com/sagernet/sing-box v1.13.19
    golang.org/x/sys v0.47.0
)
```

Первая строка — **канонический путь импорта**. Все внутренние импорты идут от него: `github.com/bbesport/net-gui-client/internal/platform/wfp`.

Версия ядра **пиннится на конкретный стабильный релиз**, а не на «последнюю». Это прямое смягчение риска R10 из реестра: ядра этой экосистемы регулярно ломают обратную совместимость конфигураций, и обновление должно быть осознанным действием с прогоном тестов, а не побочным эффектом `go get -u`.

Тонкость, важная для [ADR-001](adr/ADR-001-protocol-core.md): наш форк sing-box **сохраняет module identity** `github.com/sagernet/sing-box`, а подменяется директивой `replace` в `go.mod`:

```
replace github.com/sagernet/sing-box => ./net-core
```

Это позволяет форку оставаться совместимым с upstream-кодом, который импортирует sing-box по каноническому пути, и делает ребейз на теги upstream механической операцией. Ровно этот приём использует `sing-box-lx`.

### Пакет

Пакет — это **директория**. Все файлы в одной директории обязаны объявлять один и тот же `package`:

```go
// internal/platform/wfp.go
package platform
```

Пакет — единица инкапсуляции. Неэкспортируемые имена видны всем файлам пакета, но не за его пределами.

### Директория `internal/` — механизм, а не соглашение

Это встроенное в компилятор правило: пакет внутри `internal/` может импортироваться **только** из кода, чей путь лежит под родителем этой `internal/`.

Для нас это прямой инструмент соблюдения архитектурных границ из [03-architecture.md](03-architecture.md) §3.1:

```
net-gui-client/
├── go.mod
├── proto/                      ← контракт gRPC, публичный: его читают все клиенты
├── net-core/                   ← форк sing-box (replace-директива)
├── cmd/
│   ├── net-svc/main.go         ← служба
│   ├── net-cli/main.go         ← CLI-клиент
│   └── net-gui/main.go         ← GUI
└── internal/
    ├── orchestration/          ← платформонезависимо: FSM, failover, правила
    │   ├── session/
    │   ├── failover/
    │   ├── health/
    │   └── rules/
    ├── platform/               ← ЕДИНСТВЕННОЕ место с Windows API
    │   ├── tun/
    │   ├── route/
    │   ├── wfp/
    │   ├── redirector/
    │   └── sysproxy/
    ├── corehost/               ← линковка и управление net-core
    └── store/                  ← профили, секреты
```

Инвариант «слой Orchestration не содержит вызовов Windows API» из архитектуры проверяется механически: если в `internal/orchestration/` появится импорт `golang.org/x/sys/windows`, это видно линтером и ревью. Компилятор сам это не запретит, но структура делает нарушение заметным.

### Соглашение `cmd/`

Каждая поддиректория `cmd/` — отдельный исполняемый файл. `package main` + функция `main()`. Три бинарника из одного модуля с общим кодом в `internal/`.

### Build-теги

Комментарий особого вида в первых строках файла, до `package`:

```go
//go:build windows

package platform
```

Файл участвует в сборке только под указанное условие. Механизм, на котором держатся два решения проекта:

- **Кроссплатформенность** ([03-architecture](03-architecture.md) §3.1): `tun_windows.go`, `tun_linux.go`, `tun_darwin.go` реализуют один интерфейс. Порт на Linux — это добавление файлов, а не переписывание.
- **Форк ядра** ([ADR-001](adr/ADR-001-protocol-core.md)): AmneziaWG живёт за тегом `with_awg`. Сборка без тега даёт байт-в-байт поведение upstream.

Есть и суффиксы имён файлов: `_windows.go`, `_linux.go`, `_test.go` — компилятор применяет их автоматически, без комментария.

### Команды, которые понадобятся

```bash
go mod tidy
```

Приводит `go.mod` и `go.sum` в соответствие с реальными импортами: добавляет недостающее, удаляет лишнее.

```bash
go build ./...
```

Собирает все пакеты модуля. `./...` — рекурсивный шаблон «текущая директория и всё под ней».

```bash
go vet ./...
```

Статический анализ поверх компилятора: ловит подозрительные конструкции, которые формально валидны. Входит в наш CI ([04-development-plan](04-development-plan.md) §2, пункт DoD 4).

```bash
go test ./...
```

Запускает все тесты модуля.

## 6. Windows API из Go: syscall и x/sys

Разбор по коду [internal/platform/wfp/wfp_windows.go](../internal/platform/wfp/wfp_windows.go) — это самый «системный» код проекта, и на нём хорошо видно, где Go перестаёт вас защищать.

### 6.1. Как Go вызывает функцию из DLL

```go
var (
    modFwpuclnt = windows.NewLazySystemDLL("fwpuclnt.dll")

    procFwpmEngineOpen0 = modFwpuclnt.NewProc("FwpmEngineOpen0")
)
```

`NewLazySystemDLL` — «ленивая» загрузка: DLL не грузится, пока не понадобится. Слово `System` важно — оно заставляет искать библиотеку **только** в `%SystemRoot%\System32`, а не по обычному порядку поиска DLL. Это защита от подмены библиотеки: обычный `NewLazyDLL` мог бы подхватить одноимённый файл из рабочей директории.

Прямая связь с мерой **S4** из [ADR-006](adr/ADR-006-privilege-security.md): служба под LocalSystem не должна грузить ничего из мест, доступных пользователю на запись. Здесь язык даёт готовый безопасный вариант — надо просто выбрать правильный.

### 6.2. `.Call()` и почему всё через `uintptr`

```go
rc, _, _ := procFwpmEngineOpen0.Call(
    0,                              // serverName: NULL
    uintptr(rpcCAuthnWinNT),        // authnService
    0,                              // authIdentity: NULL
    uintptr(unsafe.Pointer(&sess)), // session
    uintptr(unsafe.Pointer(&handle)),
)
```

`Call` принимает `...uintptr` и возвращает три значения: `r1`, `r2`, `lastErr`. Типизации нет вообще — компилятор не проверит ни количество аргументов, ни их смысл. Ошиблись порядком — получите повреждение памяти, а не ошибку сборки.

Здесь `_, _` для второго и третьего значения: функции WFP возвращают код ошибки в `r1`, а `lastErr` (то есть `GetLastError`) не используют. У других API бывает наоборот — читать документацию обязательно.

### 6.3. Правило `unsafe.Pointer` → `uintptr`, которое легко нарушить

Самое важное место раздела.

`uintptr` — это просто число. Сборщик мусора Go **не считает его ссылкой** и может переместить или собрать объект, на который оно указывает. Поэтому существует жёсткое правило:

> Преобразование `unsafe.Pointer` в `uintptr` допустимо **только внутри выражения вызова**.

Правильно — так, как в коде выше: `uintptr(unsafe.Pointer(&sess))` записано прямо в аргументе `Call`. Компилятор и рантайм распознают этот шаблон и удерживают объект живым на время вызова.

Неправильно:

```go
p := uintptr(unsafe.Pointer(&sess))  // ОПАСНО: с этого момента GC про sess не знает
proc.Call(p)                          // sess мог быть перемещён или собран
```

Второй вариант скомпилируется, пройдёт `go vet` в простых случаях и будет работать — до того дня, когда GC сработает в неудачный момент. Такие ошибки воспроизводятся раз в тысячу запусков.

### 6.4. Раскладка структур обязана совпадать побайтово

```go
type value0 struct {
    typ   uint32
    _     uint32   // выравнивание
    value uintptr  // union
}
```

C-структура `FWP_VALUE0` — это `UINT32` плюс union. На x64 наибольший член union занимает 8 байт и требует 8-байтового выравнивания, поэтому между ними компилятор C вставляет 4 байта. Мы обязаны вставить их сами.

Поле `_` — пустой идентификатор: занимает место, но недоступно по имени.

Go расставил бы это выравнивание и сам, по тем же правилам. Выписано явно намеренно: **расхождение раскладки не даёт ошибки компиляции** — оно даёт запись мусора в чужую память. Явное поле превращает молчаливое предположение в утверждение, которое видно при чтении кода.

Union в Go не существует. Приём — объявить поле по наибольшему члену и трактовать его по типу из соседнего поля. В `value0` поле `value` объявлено как `uintptr`, а как его читать, говорит `typ`.

### 6.5. `windows.Errno` — превращение кода ошибки в `error`

```go
if rc != 0 {
    return nil, fmt.Errorf("wfp: FwpmEngineOpen0: %w", windows.Errno(rc))
}
```

`windows.Errno` реализует интерфейс `error` и умеет разворачивать числовой код в текст системного сообщения. Глагол `%w` в `fmt.Errorf` **оборачивает** ошибку, сохраняя оригинал доступным для `errors.Is` и `errors.As` выше по стеку. Если бы стояло `%v`, текст сохранился бы, а тип — нет, и вызывающий код не смог бы отличить «нет прав» от «неверный параметр».

Правило по проекту: оборачиваем через `%w`, префикс — имя пакета и имя вызванной функции.

### 6.6. `defer` как гарантия освобождения

```go
defer func() {
    if cerr := eng.Close(); cerr != nil {
        fmt.Fprintln(os.Stderr, "warn: закрытие движка:", cerr)
    }
}()
```

`defer` откладывает вызов до выхода из функции — включая выход по панике. Аналог `finally`, но привязанный к функции, а не к блоку.

Почему обёртка в анонимную функцию, а не просто `defer eng.Close()`: `Close` возвращает `error`, а `defer` возвращаемое значение отбрасывает. Молча проглоченная ошибка освобождения ресурса — типовой источник трудноуловимых утечек.

Важное ограничение: `defer` **не сработает** при `os.Exit`, при `panic` в другой горутине и при аварийном завершении процесса. Поэтому в коде WFP на него не полагаются как на единственную гарантию — используется динамическая сессия (`fwpmSessionFlagDynamic`), при которой фильтры снимает сама система. Это прямое выражение принципа **P-G** (обратимость сетевых изменений): корректность не должна зависеть от того, успел ли наш код прибраться.

### 6.7. Разбор реального краша: как выглядит цена отсутствия типизации

При первом запуске E4 программа упала:

```
Exception 0xc0000005 0x0 0x1010101 0x7ffdebba086e
...
wfp.(*Engine).BlockOutboundToIP  wfp_windows.go:269
```

`0xc0000005` — access violation, обращение по недопустимому адресу. Падение произошло **внутри** `FwpmFilterAdd0`, то есть уже в чужом коде.

Диагноз читается прямо из дампа регистров:

```
rdi  0x1010101
r9   0x1010101
```

`0x01010101` — это `1.1.1.1`, наш тестовый адрес, записанный побайтово. Ядро пыталось **разыменовать его как указатель**.

**Причина.** В коде было объявлено:

```go
fwpUint32 = 4   // неверно
```

А в перечислении `FWP_DATA_TYPE` значение `4` — это `FWP_UINT64`, у которого член union объявлен как `UINT64 *uint64`, то есть **указатель**. Мы сказали WFP «в union лежит указатель на 64-битное число» и положили туда число `0x01010101`. WFP послушно пошёл по этому адресу.

Правильное значение — `FWP_UINT32 = 3`.

**Что здесь поучительного.**

1. Ошибка — в одной цифре в константе. Компилятор её не видит: `4` — валидный `int`.
2. `go vet` её не видит: с точки зрения Go код корректен.
3. Тесты бы её не поймали без реального вызова: ошибка проявляется только внутри ядра.
4. Проявление — не паника Go со стеком в нашем коде, а access violation в системной библиотеке. Стек указывает на `BlockOutboundToIP`, но настоящая причина — в объявлении константы двумястами строками выше.

Это ровно тот класс ошибок, о котором предупреждает §6.2: **при вызове системных API типизации нет вообще**, и любое расхождение с C-заголовком превращается в повреждение памяти.

**Что защитило проект.** Динамическая сессия WFP (§6.6). Процесс умер аварийно — `defer` не отработал, `Close()` не вызвался. Но фильтры сняла система, и связь с целью осталась рабочей. Принцип **P-G** сработал именно так, как задумывался: корректность не зависела от того, успел ли наш код прибраться.

**Приём на будущее.** Константы, взятые из C-перечислений, теперь сопровождаются выпиской самого перечисления в комментарии — целиком, с порядком. Проверка глазами становится возможной без обращения к SDK. Это дешевле, чем ловить такое во второй раз.

### 6.8. Что здесь важнее всего

В обычном Go язык защищает вас: нет арифметики указателей, нет выхода за границы массива без паники, нет ручного управления памятью. В этом файле все три защиты выключены. Цена ошибки — не паника с понятным стеком, а повреждение памяти или неверные данные, переданные в ядро.

Отсюда правило по проекту: **весь код с `unsafe` живёт только в `internal/platform/`**, за узкими интерфейсами, и не расползается по слою оркестрации.

<a name="2"></a>
## 2. Типы, структуры, методы

Разбор по [internal/orchestration/profile/profile.go](../internal/orchestration/profile/profile.go) и [internal/orchestration/rules/rules.go](../internal/orchestration/rules/rules.go).

### 2.1. Именованный тип поверх строки

```go
type Kind string

const (
    KindSOCKS5 Kind = "socks5"
)
```

`Kind` — не псевдоним `string`, а **отдельный тип**. Обычную строку в поле типа `Kind` компилятор не пропустит без явного преобразования. Это дешёвая защита от перепутанных аргументов: `Profile{Kind: p.Name}` не соберётся.

Так же сделаны `rules.Action`. Приём массовый в Go и заменяет перечисления, которых в языке нет.

### 2.2. Методы с получателем-значением

```go
func (p Profile) Validate() error { ... }
```

`(p Profile)` — получатель по **значению**: метод работает с копией. Альтернатива — `(p *Profile)`, получатель по указателю, который позволяет менять оригинал.

Правило по проекту: если метод не изменяет объект — получатель по значению. `Validate` только читает, поэтому копия. Это делает невозможным случайную мутацию профиля при проверке.

Обратная сторона — копирование при каждом вызове. Для структуры из семи полей это неважно; для структуры с большими массивами внутри имело бы значение.

### 2.3. Встраивание структур

```go
type Rule struct {
    Matcher          // встроено, без имени поля
    Action Action
}
```

Поля `Matcher` становятся доступны напрямую: `r.Domain`, а не `r.Matcher.Domain`. Методы `Matcher` тоже поднимаются на уровень `Rule` — именно поэтому в `validate()` работает `r.isEmpty()`, хотя объявлен этот метод на `Matcher`.

Это **композиция**, а не наследование: `Rule` не «является» `Matcher` и не может быть подставлен туда, где ожидается `Matcher`. В Go нет наследования вообще; встраивание — способ переиспользовать поля и методы без иерархии типов.

### 2.4. Конструкторы вместо структурных литералов

```go
func PolicyOnlySelected(rules ...Rule) Policy {
    return Policy{Default: ActionDirect, Rules: rules}
}
```

В Go нет конструкторов как языковой конструкции — есть соглашение: обычная функция, возвращающая заполненное значение. Здесь она заодно фиксирует смысловую связь «только выбранное ⇒ действие по умолчанию Direct», которую иначе пришлось бы помнить на каждом месте вызова.

`rules ...Rule` — вариативный параметр: `PolicyOnlySelected()` и `PolicyOnlySelected(r1, r2)` одинаково валидны.

<a name="4"></a>
## 4. Ошибки: почему нет исключений

### 4.1. Ошибка — обычное значение

```go
core, err := corehost.Start(ctx, cfg)
if err != nil {
    return nil, fmt.Errorf("corehost: запуск ядра: %w", err)
}
```

`error` — встроенный интерфейс с единственным методом `Error() string`. Функция возвращает его наравне с результатом. Никакого отдельного канала распространения, как у исключений, нет.

Плата — многословность: `if err != nil` встречается часто. Выгода — **все точки отказа видны в коде**. В привилегированной службе, где пропущенная ошибка означает висящий сетевой фильтр или незакрытый адаптер, это важнее краткости.

### 4.2. `%w` против `%v`

```go
fmt.Errorf("corehost: сборка ядра: %w", err)   // оборачивает
fmt.Errorf("corehost: сборка ядра: %v", err)   // только текст
```

`%w` сохраняет исходную ошибку доступной для `errors.Is` и `errors.As` выше по стеку. С `%v` текст сохранится, а тип — нет, и вызывающий код не отличит «нет прав» от «неверный параметр».

Соглашение проекта: оборачиваем через `%w`, префикс — имя пакета, дальше — что именно не получилось.

### 4.3. Паника — не для ошибок

`panic` в этом проекте допустима только для программистских ошибок, которые не должны случаться никогда. Отказ сети, отсутствие прав, некорректный ввод пользователя — это `error`, а не паника. Служба, падающая от неверного профиля, оставила бы систему с поднятым туннелем.

<a name="5"></a>
## 5. Горутины, каналы, `context`

Разбор по [internal/testutil/socks5/server.go](../internal/testutil/socks5/server.go) — там всё это собрано в одном месте.

### 5.1. Горутина

```go
go s.acceptLoop()
```

`go` перед вызовом запускает функцию в отдельной горутине. Горутина — не поток ОС: она занимает килобайты, а не мегабайты, и рантайм сам мультиплексирует тысячи горутин на несколько потоков. Поэтому в Go нормально выделять по горутине на соединение — модель, которая с потоками ОС была бы неприемлема.

### 5.2. `sync.WaitGroup` — дождаться завершения

```go
s.wg.Add(1)
go func() {
    defer s.wg.Done()
    ...
}()
...
s.wg.Wait()   // в Close()
```

Счётчик: `Add` увеличивает, `Done` уменьшает, `Wait` блокируется до нуля. Без него `Close()` вернул бы управление, пока обработчики ещё живы, и тест увидел бы гонку.

`defer s.wg.Done()` первой строкой — чтобы счётчик уменьшился при любом выходе, включая панику.

### 5.3. Мьютекс защищает данные, а не код

```go
s.mu.Lock()
s.targets = append(s.targets, target)
s.mu.Unlock()
```

Журнал пишется из множества горутин и читается из тестовой. Без мьютекса это гонка — не «иногда неверный порядок», а неопределённое поведение вплоть до повреждения слайса.

Обратите внимание на `Targets()`:

```go
func (s *Server) Targets() []string {
    s.mu.Lock()
    defer s.mu.Unlock()
    return append([]string(nil), s.targets...)
}
```

Возвращается **копия**. Вернуть сам слайс означало бы отдать наружу ссылку на данные, защищённые мьютексом — и вся защита обесценилась бы за пределами метода.

### 5.4. Канал как сигнал

```go
closed chan struct{}
...
select {
case <-s.closed:
    return          // уже закрыт
default:
    close(s.closed) // закрываем
}
```

`chan struct{}` — канал, по которому не передают данные, только факт события. `struct{}` занимает ноль байт.

Закрытый канал немедленно отдаёт нулевое значение **всем** читателям — поэтому `close` работает как широковещательное уведомление. `select` с `default` делает проверку неблокирующей и защищает от повторного `close`, который вызвал бы панику.

### 5.5. `context.Context`

```go
func Start(ctx context.Context, cfg Config) (*Core, error) {
    ctx = include.Context(ctx)
    b, err := box.New(box.Options{Options: opts, Context: ctx})
```

`context` решает две задачи: отмена операции и передача значений по цепочке вызовов. sing-box использует вторую — контекст служит **контейнером внедрения зависимостей**: `include.Context` кладёт в него реестры протоколов, а ядро достаёт их оттуда. Глобальных синглтонов в sing-box нет, и это то, что делает возможным несколько независимых экземпляров ядра в одном процессе.

Соглашение: `ctx` всегда первый параметр.

### 5.6. Разбор реальной ошибки: контекст запроса против контекста жизни

Ошибка из этой же итерации, стоившая часа отладки.

`Manager.Connect` получал `ctx` от обработчика gRPC и передавал его в ядро:

```go
core, err := corehost.Start(ctx, corehost.Config{...})   // неверно
```

Выглядит правильно: контекст есть — передай дальше. Но **контекст gRPC-запроса отменяется, как только сервер ответил клиенту**. Ядро запускалось, рапортовало «подключено», gRPC отдавал ответ — и в этот момент контекст умирал, забирая ядро с собой.

Симптомы были обманчивы:
- `net-cli connect` сообщал «подключено» — потому что на момент ответа всё действительно работало;
- `net-cli status` показывал «подключено» — состояние хранилось отдельно;
- любой запрос через прокси возвращал **502**;
- в журнале ядра: `connection closed: ... context canceled`.

**Почему это не поймал существующий тест.** Тест `corehost` вызывал `corehost.Start(context.Background(), ...)` — контекст, который не отменяется никогда. Ошибка жила не внутри `corehost` и не внутри `session`, а **на стыке**: в том, какой именно контекст один слой передаёт другому. Тесты отдельных слоёв такое пропускают по построению.

**Исправление** — у менеджера появился собственный контекст жизни:

```go
type Manager struct {
    baseCtx context.Context   // контекст ЖИЗНИ СЛУЖБЫ
    ...
}

core, err := corehost.Start(m.baseCtx, corehost.Config{...})
```

**Правило, которое из этого следует:**

> Контекст запроса управляет только длительностью запроса. Всё, что переживает запрос, получает контекст своего владельца.

Отсюда и уточнение к соглашению «ctx не хранится в структуре»: оно относится к контекстам **запросов**. Контекст жизни объекта в поле хранить нормально — именно так `Manager` и устроен, и поле названо `baseCtx`, чтобы отличать его от запросного.

**Написан регрессионный тест**, который отменяет контекст сразу после `Connect` и затем требует, чтобы трафик ходил — [manager_test.go](../internal/orchestration/session/manager_test.go). Проверено мутацией: с возвращённой ошибкой тест падает ровно с тем же 502.

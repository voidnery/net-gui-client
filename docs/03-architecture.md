## 3. Целевая архитектура

### 3.1. Процессы и границы доверия

```
┌─ Сессия пользователя (без прав администратора) ──────────────────────┐
│                                                                       │
│   net-gui  (Wails v2: Go + WebView2)          net-cli  (Go)          │
│   ├─ Трей-агент — всегда запущен                ├─ 100% функций GUI   │
│   ├─ Окно — по требованию                       └─ инструмент тестов  │
│   ├─ Toast/модальные уведомления (T7)                                │
│   └─ Ноль бизнес-логики                                              │
└───────────────────────┬───────────────────────────────────────────────┘
                        │  gRPC поверх named pipe  (ADR-004)
                        │  DACL + верификация клиента  (ADR-006)
┌───────────────────────▼───────────────────────────────────────────────┐
│  net-svc  — служба Windows, LocalSystem, автозапуск                   │
│                                                                        │
│  ┌── Orchestration (платформонезависимо) ───────────────────────────┐ │
│  │  SessionFSM │ FailoverEngine │ HealthProber │ RulesEngine        │ │
│  │  ProfileStore │ SecretStore │ SubscriptionSync │ EventBus        │ │
│  └───────────────────────────────────────────────────────────────────┘ │
│  ┌── Platform (интерфейсы; реализация под ОС) ──────────────────────┐ │
│  │  TunManager │ RouteManager │ WfpBlocker │ Redirector             │ │
│  │  SystemProxyManager │ PowerWatcher │ NetworkWatcher              │ │
│  └───────────────────────────────────────────────────────────────────┘ │
│  ┌── CoreHost ───────────────────────────────────────────────────────┐ │
│  │  net-core — форк sing-box, линкуется как Go-пакет  (ADR-001)     │ │
│  │  Inbounds │ Outbounds │ Router │ DNS │ Connection tracking        │ │
│  └───────────────────────────────────────────────────────────────────┘ │
└───────────────────────┬───────────────────────────────────────────────┘
                        │  только если включён режим редиректа
┌───────────────────────▼───────────────────────────────────────────────┐
│  Redirector backend  (ADR-002)                                        │
│    вариант A: WinDivert       — если E1 подтвердит загрузку           │
│    вариант B: свой WFP-калаут — attestation-подпись                   │
└───────────────────────────────────────────────────────────────────────┘

        wintun.dll  — официальная подписанная DLL, side-by-side, dlopen
```

**Инвариант границ:**
- `net-gui` и `net-cli` не имеют доступа к сети, к реестру и к файлам конфигурации. Всё — через gRPC.
- Слой Orchestration не содержит ни одного вызова Windows API. Это цена входа в Linux/macOS.
- Слой Platform — единственное место с `//go:build windows`.

### 3.2. Почему трей-агент обязан быть постоянно запущен

Служба работает в session 0 и **не может показать окно пользователю**. Требование T7 («всплывающее окно при отказе всех узлов») выполнимо только если в пользовательской сессии есть живой процесс. Поэтому `net-gui` стартует вместе с сессией и живёт в трее со скрытым окном; окно — лишь представление.

Следствие: служба обязана корректно работать и **без** подключённого GUI (принцип P1), а события буферизовать — чтобы уведомление о падении, случившемся до старта GUI, всё равно дошло.

## 4. Три режима — адаптивная модель

> Пересмотрено 2026-08-24 по [ADR-007](adr/ADR-007-adaptive-interception.md) после экспериментов [E1](experiments/E1-windivert.md) и [E2](experiments/E2-driver-signing.md).

Ключевое уточнение: **режим — это пресет политики, а не механизм перехвата.** Механизм выбирается автоматически по тому, что требуют текущие правила.

### 4.1. Правило выбора механизма

| Условие | Механизм | TUN | Системный прокси |
|---|---|:---:|:---:|
| «Прокси», правил по процессам нет | Локальный listener | ❌ | ❌ |
| «Системный прокси», правил по процессам нет | Локальный listener + системные настройки | ❌ | ✅ |
| **Любой режим, есть активное правило по процессу** | **TUN**, `defaultAction = DIRECT` | ✅ | по режиму |
| «Полный туннель» | **TUN**, `defaultAction = PROXY` | ✅ | ❌ |

`WfpBlocker` (user-mode WFP, без драйвера) активен **всегда**, во всех вариантах.

### 4.2. Матрица возможностей правил

| Тип правила | Лёгкие режимы, TUN не поднят | Любой режим с поднятым TUN |
|---|---|---|
| По домену | ✅ из CONNECT / SOCKS5 (+ PAC) | ✅ fake-IP или sniffing |
| По IP / CIDR / GeoIP | ✅ | ✅ |
| По порту / протоколу | ✅ | ✅ |
| **По процессу** | — правило автоматически поднимает TUN → | ✅ **нативно**, без драйвера |
| Блокировка (BLOCK) | ✅ user-mode WFP | ✅ |
| UDP | ⚠️ только SOCKS5 UDP ASSOCIATE | ✅ полностью |

**Требование T3 выполняется полностью:** правила по приложениям доступны во всех трёх режимах. Цена — автоматическое поднятие туннеля, а не драйвер режима ядра.

### 4.3. Что обязано быть видно в UI

Адаптивность не должна быть молчаливой — это прямое следствие принципа U2:

1. **Какой механизм активен сейчас** и почему — на экране Подключение и на экране Маршрутизация.
2. **Предупреждение до применения**, а не после: добавление первого правила по процессу в лёгком режиме поднимет туннель и **разорвёт активные соединения**.
3. Пояснение, что даёт поднятый туннель: полный охват UDP, правила по процессам, но выше нагрузка и выше риск конфликта с другими VPN.

### 4.4. Собственный драйвер исключён

Интерфейс `Redirector` ([ADR-002](adr/ADR-002-traffic-interception.md)) остаётся в коде как точка расширения с нулём реализаций. Причины исключения — в [ADR-007](adr/ADR-007-adaptive-interception.md): WinDivert непригоден по подписи, а собственный драйвер требует EV-сертификата от $280/год рекуррентно при отсутствии бесплатных путей (Azure Trusted Signing не поддерживает драйверы, SignPath даёт только OV).

Единственный непокрытый сценарий: «нужны правила по приложениям, но принципиально против TUN». Сознательно оставлен непокрытым.

### 4.2. Конвейер разрешения правил

Не изменился по сути, но получил слой 0′ и явное указание, где что вычисляется:

```
соединение
 → [0]  системные исключения          — жёстко зашиты, не редактируются
        loopback · RFC1918 · endpoint активных outbound · DHCP · WPAD · mDNS
 → [0′] WFP-блокировки                — user-mode WFP, до входа в ядро
        kill-switch · IPv6-политика · сторонний DoH · QUIC
 → [1]  правила процесса              — TUN: нативно | иначе: Redirector
 → [2]  правила домена                — fake-IP / sniffing / CONNECT
 → [3]  правила IP / GeoIP
 → [4]  правила порт / L4-протокол
 → [5]  default action                — политика whitelist/blacklist
```

Семантика — **«первое совпадение выигрывает»** (как в sing-box и Clash): проще объяснить, проще отладить, совпадает с поведением ядра. Компенсация сложности для пользователя — **тестер правил** и предупреждения о перекрытых правилах в UI.

## 5. Маршрутизация: разделение обязанностей с ядром

Важное архитектурное уточнение, которого не было в Фазе 1.

sing-box имеет собственный полноценный rule-engine. Дублировать его — ошибка. Поэтому:

| Слой | Кто исполняет | Что решает |
|---|---|---|
| Пользовательская модель правил | `RulesEngine` в `net-svc` | Хранение, валидация, порядок, тестер правил, предупреждения о перекрытии |
| Компиляция в конфиг ядра | `RulesEngine` → `net-core` | Трансляция нашей декларативной модели в `route.rules` sing-box |
| Исполнение на трафике | `net-core` (sing-box) | Быстрый матчинг на каждом соединении |
| Блокировки вне ядра | `WfpBlocker` | То, что должно умереть **до** попадания в ядро |

**Мы не пишем свой матчер пакетов.** Мы пишем модель, транслятор и объяснялку. Это резко сокращает объём кода и убирает целый класс багов расхождения «UI показывает одно, ядро делает другое».

Тестер правил (§8) реализуется поверх того же транслятора плюс dry-run матчинга ядра — то есть показывает **фактическое** поведение, а не нашу интерпретацию.

## 6. Health-check и failover — пересмотрено

### 6.1. Двухконтурная модель проб

Замена схемы «активная проба по таймеру» из Фазы 1.

```
┌─ Контур 1: ПАССИВНОЕ НАБЛЮДЕНИЕ (первичный сигнал) ──────────────┐
│  Источник: реальный трафик пользователя через net-core            │
│  Метрики: доля неуспешных установок соединения, время до первого  │
│           байта, доля разрывов, стагнация скорости при активности  │
│  Стоимость: ноль трафика. Реакция: секунды                        │
└────────────────────┬──────────────────────────────────────────────┘
                     │ подозрение на деградацию
┌────────────────────▼──────────────────────────────────────────────┐
│  Контур 2: АКТИВНАЯ ОГРАНИЧЕННАЯ ПРОБА (подтверждение и выбор)    │
│  Триггеры: сигнал контура 1 · фоновый таймер ~600 с ·             │
│            ручной запуск · смена сети · выход из сна              │
│  Метод: N HTTP-проб через аутбаунд (204-эндпоинт)                 │
│  Оценка: МЕДИАНА + ХУДШЕЕ + доля отказов, не одиночный замер      │
└───────────────────────────────────────────────────────────────────┘
```

**Почему так:** активная проба по таймеру видит проблему в среднем через полпериода и тратит трафик впустую. Пассивное наблюдение видит деградацию реального трафика немедленно и бесплатно. Активная проба нужна лишь для (а) подтверждения и (б) ранжирования альтернатив перед переключением.

⚠️ Пассивное наблюдение слепо, когда трафика нет. Поэтому фоновый таймер сохраняется — но редкий (600 с), а не 30 с.

### 6.2. Уровни проверки и FSM

Уровни L1/L2/L3 из Фазы 1 §6.1 остаются без изменений. FSM из §6.2 остаётся, с уточнением параметров:

| Параметр | Было (Фаза 1) | Стало | Причина |
|---|---|---|---|
| `interval` фоновой пробы | 30 с | **600 с** | RQ7: практика зрелых клиентов |
| `interval` в состоянии Degraded | 5–10 с | **5 с** | Быстро подтвердить или опровергнуть |
| `timeout` | 5 с | 5 с | Без изменений |
| `failThreshold` | 3 | 3 | Без изменений |
| `riseThreshold` | 2 | 2 | Без изменений |
| Замеров на одну активную пробу | 1 | **3, оценка по медиане** | RQ7: одиночный замер искажается кэшем, джиттером, троттлингом |

### 6.3. Задел на будущее

Модель `FailoverChain` хранит `chainId`, а `RoutingRule` имеет **опциональное** поле `chainId`. В MVP цепочка одна и поле пустое. Это позволяет позже дать «для стриминга — цепочка A, для остального — B» без миграции схемы. Обосновано в Фазе 1 §6.3: дёшево заложить, дорого добавить.

## 7. DNS-подсистема

Полностью в ADR-005. Здесь — только контур:

- Режим по умолчанию: **fake-IP** с пулом по умолчанию и **настраиваемым** диапазоном.
- Четыре обязательные защиты: авто-фильтр доменов активных эндпоинтов · предустановленный intranet-фильтр · настраиваемый пул · детект петли.
- Альтернативный режим: **sniffing** (SNI / HTTP Host) — для приложений, которые fake-IP ломает.
- Политика стороннего DoH: обнаружение и опциональная блокировка через `WfpBlocker`.
- Встроенный тест утечек DNS/IPv6.

## 8. UX — уточнения по итогам исследования

Карта из Фазы 1 §11.1 остаётся. Изменения в содержании:

**[1] Подключение**
- Виджет цепочки резервирования показывает **причину** последнего переключения (пассивный сигнал / активная проба / ручное), а не только факт.

**[3] Маршрутизация**
- ⭐ **Индикатор доступности правил.** Экран показывает, какие типы правил активны в текущем режиме (матрица §4.1). Если правила по процессам заданы, а Redirector недоступен или выключен — явное предупреждение с кнопкой «Что это значит».
- **Тестер правил** реализуется через dry-run ядра, а не через нашу интерпретацию — показывает фактическое решение.
- Предупреждение о правилах, перекрытых вышестоящими.

**[7] Настройки → DNS**
- Настраиваемый диапазон fake-IP (последствие RQ6).
- Переключатель fake-IP / sniffing с объяснением, когда какой нужен.
- Список исключений fake-IP с предзаполненным intranet-набором.

**[7] Настройки → Безопасность**
- `onAllDown`: `block` (дефолт) / `direct` / `retry`.
- Тумблер Redirector с честным описанием: что даёт, что стоит (драйвер, возможная реакция антивируса).

## 10. Пересмотренный контур MVP

**Включено:**

> Пересмотрено по [ADR-007](adr/ADR-007-adaptive-interception.md): `Redirector` и драйверный трек исключены, добавлена адаптивная логика выбора механизма.

| Блок | Состав |
|---|---|
| Протоколы | SOCKS5, VLESS (+TLS/Reality/XTLS-Vision), Hysteria2, AmneziaWG, и «бесплатно» с ядром — VMess, Trojan, Shadowsocks, WireGuard |
| Режимы | Все три, как пресеты политики + адаптивный выбор механизма |
| Правила | Домен, IP/CIDR, порт, протокол — во всех режимах. Процесс — нативно в TUN, поднимаемом автоматически при появлении такого правила |
| Политики | Обе (whitelist / blacklist) + действие BLOCK |
| Защита | Kill-switch, IPv6-политика, блокировка стороннего DoH — **user-mode WFP, без драйвера** |
| DNS | fake-IP с четырьмя защитами + режим sniffing |
| Живость | Двухконтурная модель проб, FSM, упорядоченная цепочка, fail-back, `onAllDown` |
| Импорт | Ссылки (`vless://`, `hy2://`, `ss://`, `trojan://`, `vmess://`), файлы, буфер обмена |
| Система | Служба + трей-агент, автозапуск, автоподключение, реакция на сон и смену сети |
| Диагностика | Логи, тестер правил, экспорт диагностического пакета |
| Инфраструктура | `net-cli` с полным покрытием функций, CI, тесты |

**Отложено:** подписки · QR-импорт · статистика по процессам · тест скорости · GeoIP/GeoSite-базы · автообновление · локализация сверх RU/EN · multi-hop цепочки · per-rule цепочки резервирования · Linux/macOS.

**Условно (зависит от E1):** конкретный бэкенд `Redirector`. Архитектура позволяет начать разработку **до** ответа: интерфейс фиксирован, бэкенд подставляется.

## 11. Что дальше — вход в Фазу 4

Фаза 4 — построение плана разработки. Обязательные входные условия, которые план должен учесть:

1. **E1 и E4 — первыми пунктами плана, до написания продуктового кода.** E1 определяет бэкенд `Redirector`, E4 подтверждает главный вывод исследования. Оба — часы-дни работы.
2. **E2 (сроки подписи) запускается параллельно с первой итерацией** — это внешний процесс с длинным лагом, его нельзя ставить в конец.
3. **Вертикальный срез вперёд горизонтальных слоёв.** Первая продуктовая итерация должна давать работающую сквозную цепочку «профиль → подключение → трафик идёт», а не отдельно взятый слой.
4. **Меры S1–S8 — acceptance-критерии каждой итерации, затрагивающей IPC или запуск процессов**, а не отдельная итерация «безопасность» в конце.
5. **`net-cli` пишется вместе с функцией, а не после.** Он же — инструмент интеграционных тестов.

## 1. Метод пересмотра

План проверялся по четырём осям:

1. **Инверсии зависимостей** — есть ли итерация, которая на практике нуждается в результате более поздней.
2. **Размер и связность** — есть ли итерация, которая делает две несвязанные вещи или одну слишком большую.
3. **Покрытие рисков** — вскрывается ли каждый риск из реестра раньше, чем становится дорого.
4. **Демонстрируемость** — есть ли у каждой итерации проверяемый результат.

Плюс отдельная проверка: **что нужно для того, чтобы итерацию вообще можно было протестировать.**

### И-1. ⭐ Вертикальный срез и минимальная модель правил

**Изменено: сюда переносится минимальный `RulesEngine` (D1).**

Обоснование: правила маршрутизации — это и есть продукт (T3, T4). Отложить их до И-7 значит три итерации подряд заявлять приёмку, которую нечем проверить. И архитектурно транслятор «наша модель → `route.rules` ядра» ([03-architecture](03-architecture.md) §5) должен появиться одновременно с первым конфигом ядра, а не поверх готового.

> **Отчёт по факту выполнения — 2026-08-24.** Итерация закрыта. Одно отклонение от плана: создание форка `net-core` и пробный ребейз **перенесены в И-4** с обоснованием — см. дополнение в [ADR-001](adr/ADR-001-protocol-core.md). Кратко: вертикальному срезу на SOCKS5 форк не нужен, а ребейз при нулевой дельте не проверяет риск R16, ради которого D6 и вводился.

**Состав (изменения выделены):**
- ~~`net-core`: форк создан, линкуется как Go-пакет~~ → **перенесено в И-4.** И-1 работает на upstream sing-box v1.13.19
- ~~➕ **Пробный ребейз на более свежий тег upstream (D6)**~~ → **перенесено в И-4**, где появится дельта и проверка станет осмысленной
- `net-svc` как консольное приложение; режим «Прокси»; локальный mixed-inbound; outbound SOCKS5
- ➕ **Минимальный `RulesEngine`**: `defaultAction` + матчеры «домен» и «IP/CIDR» + действия `Proxy` / `Direct` + транслятор в конфиг ядра
- ➕ Обе политики (whitelist / blacklist) — они и есть `defaultAction`, дополнительной работы почти не требуют
- `ProfileStore`, минимальный `proto`, `net-cli`

**Сценарий приёмки:** браузер через `127.0.0.1:<порт>` ходит в интернет через SOCKS5-сервер стенда; правило «домен X — `Direct`» реально уводит трафик мимо прокси, что видно по внешнему IP; переключение политики меняет поведение на противоположное.

**Баг-чекинг — выполнен полностью**, все сценарии закреплены тестами в [failure_test.go](../internal/orchestration/session/failure_test.go) и [manager_test.go](../internal/orchestration/session/manager_test.go):

| Сценарий | Наблюдаемое поведение |
|---|---|
| Порт занят | Ошибка подключения, состояние остаётся `Idle`, причина сохранена в статусе |
| Сервер недоступен | ⚠️ Подключение **успешно**, отказ проявляется только при первом запросе. Это ловушка L1 против L2 из §6.1 архитектуры; закрывается пробой L2 в И-9. Поведение зафиксировано тестом, чтобы его изменение было осознанным |
| Неверные креды | Запрос не проходит, сервер фиксирует отклонённую аутентификацию |
| Отключение при активных соединениях | `Disconnect` не зависает, соединения обрываются, порт освобождается |
| Повторный `connect` | Явная ошибка, а не молчаливое переподключение |
| Противоречивые правила | Выигрывает первое совпадение — семантика §4.2 закреплена |
| Пустой список правил / пустой матчер / некорректная подсеть | Отсекается валидацией до сборки конфига ядра (мера S3) |

**Обратимость (DoD п. 8) — проверена вживую.** Служба убита принудительно (`kill -9`) при активной сессии: порт локального inbound освобождён, именованный канал снят, доступ в интернет не нарушен, повторный запуск прошёл чисто, состояние сессии сброшено в `Idle`, профили сохранились.

**Разбор Go:** интерфейсы и неявная реализация, структуры и методы, `context.Context`, горутины и каналы, `defer`, `errors.Is/As`, пакет `net`, `go.mod` и директива `replace` на практике.

### И-5. TUN: поднять и корректно опустить

**Сужена (D3, D4).** Итерация отвечает ровно на один вопрос: **умеем ли мы безопасно поднять туннель и гарантированно вернуть систему в исходное состояние.**

**Состав:**
- `TunManager`: загрузка официального `wintun.dll` с проверкой подписи (**S4**), создание адаптера
- `RouteManager`: маршруты `0.0.0.0/1` + `128.0.0.0/1`, `::/1` + `8000::/1`, исключение маршрута до эндпоинта
- **Снимок сетевого состояния до изменений и его восстановление** — при штатном выходе, при падении, при следующем старте
- Watchdog и очистка при старте
- Детект конфликта с другими VPN-клиентами (R11)

**Вынесено в И-7:** правила по процессам. **Вынесено в И-6:** доменные правила.

**Сценарий приёмки:** TUN поднимается, весь трафик идёт через туннель, правила по IP из И-1 продолжают работать; **убийство службы через Task Manager не оставляет систему без интернета** — сеть восстанавливается автоматически.

⚠️ Итерация **не заявляет** доменных правил и правил по процессам. Это честная граница, а не недоделка.

**Баг-чекинг:** убийство процесса на середине подключения · отсутствие `wintun.dll` · адаптер уже существует · конфликт с корпоративным VPN · отсутствие прав · перезагрузка с активным туннелем · два запуска подряд.

**Проверка R3 (D5):** повторный прогон через SmartScreen и мультисканер после добавления Wintun; сравнение с baseline из И-0.

**Состав:**

**Сценарий приёмки:** правило на конкретный `.exe` работает в TUN-режиме; тестер правил для введённого домена показывает то же решение, что ядро принимает на реальном трафике.

### И-9. Наблюдение за живостью *(новая, выделена из прежней И-9)*

**Цель:** научиться **видеть** состояние канала. Без переключений.

**Состав:**
- **Контур 1** — пассивное наблюдение: доля неуспешных установок соединения, время до первого байта, доля разрывов, стагнация скорости при активности
- **Контур 2** — активная ограниченная проба: 3 замера, оценка по медиане + худшему + доле отказов; фоновый интервал 600 с, в состоянии Degraded — 5 с
- Уровни L1 / L2 / L3; основная проба — **L2**
- Состояния `Connected` / `Degraded` с гистерезисом
- Отображение метрик и состояния `Degraded` на экране Подключение

**Сценарий приёмки:** на подконтрольном «ломающемся» узле стенда клиент отличает три ситуации: канал здоров · канал деградировал, но работает · канал мёртв. Причём **ловушку L1 против L2** (сервер отвечает на TCP, но трафик не пропускает) распознаёт корректно.

**Разбор Go:** таймеры и `time.Ticker`, отмена через `context`, скользящие окна метрик, тестирование зависящего от времени кода без реальных задержек.

### И-10. Резервирование *(новая, выделена из прежней И-9)*

**Цель:** реакция на то, что научились видеть в И-9.

**Состав:**
- FSM: Idle → Connecting → Connected → Degraded → Failing → Failed
- `failThreshold` / `riseThreshold`, exponential backoff
- `FailoverChain`: упорядоченный список, стратегия `ordered`, fail-back
- `onAllDown`: `block` (дефолт) / `direct` / `retry`
- **Уведомление в трёх каналах** — модальное окно, toast, иконка трея (**T7**)
- Схема данных с полем `chainId` в `RoutingRule` — задел на per-rule цепочки
- Экран **[4] Резервирование**: конструктор цепочки, параметры проб, история переключений, «проверить сейчас»
- Виджет цепочки на экране Подключение с причиной последнего переключения

**Зависимость:** требует И-4 (несколько протоколов), И-8 (kill-switch как механизм `onAllDown = block`) и И-9 (сигнал для переключения).

**Сценарий приёмки:** выключаем основной узел стенда — клиент переключается на резервный и показывает причину; выключаем все — модальное окно, трафик заблокирован.

**Баг-чекинг:** флаппинг на нестабильном канале · переключение при активных соединениях · все узлы мертвы при свёрнутом окне · fail-back под нагрузкой · уведомление о событии, случившемся до старта GUI.

## 7. Гейт перед И-11

Единственная точка плана с внешним неконтролируемым сроком. Решение принимается по факту:

> ## ❌ Гейт отменён — 2026-08-24
>
> По итогам [E1](experiments/E1-windivert.md) и [E2](experiments/E2-driver-signing.md) принято [ADR-007](adr/ADR-007-adaptive-interception.md): **собственный драйвер исключён из проекта**, требование T3 выполняется адаптивным поднятием TUN.
>
> **Что это отменяет:**
> - Гейт перед И-11 — исходов больше нет, итерация идёт безусловно.
> - Параллельный трек Д-1…Д-5 (см. [04-development-plan.md](04-development-plan.md) §5) — **исключён целиком**.
> - Единственный в проекте внешний неконтролируемый срок (attestation-подпись) — исчез. График больше не зависит от Partner Center.
>
> **Как меняется И-11:** вместо «Системный прокси + Redirector» — **«Системный прокси и адаптивный выбор механизма»**. Состав: `SystemProxyManager` (реестр, WinHTTP, PAC, восстановление при падении) + логика выбора механизма из [ADR-007](adr/ADR-007-adaptive-interception.md) + UI-индикация активного механизма + предупреждение о разрыве соединений при смене.
>
> **Как меняются риски:**
>
> | Риск | Было | Стало |

> | R13 — сроки подписи драйвера | Главный риск графика | ❌ **Снят полностью** |

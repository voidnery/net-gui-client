# ADR-004: Контракт управления — gRPC поверх named pipe

**Статус:** Принято
**Дата:** 2026-08-24
**Решает:** §10.3 и §10.4 (принцип P1) документа [01-analysis.md](../01-analysis.md), требование T9
**Связано с:** [ADR-006](ADR-006-privilege-security.md) — безопасность канала

## Контекст

Разделение на непривилегированный GUI и службу LocalSystem обязательно (ADR-006). Значит между ними нужен канал. Требования к нему:

- **Двунаправленность с потоками.** Служба должна стримить в GUI статусы, метрики трафика, логи, события failover — не по опросу, а push'ом.
- **Мультиклиентность.** Клиентов минимум два (`net-gui`, `net-cli`), в перспективе третий — web UI для Linux server edition (T9).
- **Версионирование.** GUI и служба обновляются независимо; старый GUI не должен ломаться о новую службу.
- **Дешевизна для потока метрик.** Метрики идут постоянно, пока открыто окно.
- **Принцип P1.** API — продукт первого класса, а не деталь реализации GUI. Любое действие GUI выражается вызовом API.

Из исследования: sing-box начиная с 1.14.0 сам предоставляет gRPC-сервис для наблюдения и управления, включая gRPC-Web и WebSocket-транспорт для двунаправленных стримов. Hiddify использует gRPC как control interface к ядру.

## Решение

**gRPC поверх Windows named pipe**, контракт описан в `.proto` и версионирован.

- Транспорт: named pipe с явным DACL (детали — ADR-006). На Linux/macOS — Unix domain socket, тот же `.proto`.
- Схема: единый пакет `proto/` в репозитории, кодогенерация для Go; для будущего web UI — тот же контракт через gRPC-Web.
- Версионирование: поле версии в handshake; политика — аддитивные изменения без ломки; несовместимость даёт понятную ошибку «обновите клиент», а не таймаут.
- Разделение на сервисы: `SessionService` (подключение, режимы), `ProfileService`, `RoutingService` (правила, тестер), `FailoverService` (цепочки, история), `DiagnosticsService` (логи, экспорт), `EventService` (единый стрим событий).

## Рассмотренные варианты

### A. gRPC поверх named pipe ✅

| Измерение | Оценка |
|---|---|
| Сложность | Средняя |
| Двунаправленные стримы | **Нативно** |
| Версионирование | **Встроено** (protobuf) |
| Мультиязычность клиентов | **Высокая** |
| Накладные расходы | Низкие (binary) |

**Плюсы:** стримы из коробки; protobuf даёт схему, кодогенерацию и правила совместимости; тот же контракт работает через gRPC-Web для будущего web UI; sing-box уже говорит на gRPC — единый подход в проекте; смена GUI-технологии не затрагивает службу.
**Минусы:** тяжелее JSON-RPC; кодогенерация в сборке; gRPC поверх named pipe требует кастомного диалера (не проблема, но и не из коробки).

### B. JSON-RPC 2.0 поверх named pipe

**Плюсы:** проще, без кодогенерации, читается глазами при отладке.
**Минусы:** стримы приходится изобретать (long-polling или свой фрейминг); версионирование вручную; схема не формализована → расхождения клиента и сервера ловятся в рантайме, а не при сборке; для потока метрик текстовый формат дороже.

### C. Собственный протокол «длина + JSON»

**Плюсы:** минимум зависимостей, полный контроль.
**Минусы:** пишем сами всё, что gRPC даёт бесплатно: фрейминг, мультиплексирование, отмену, дедлайны, версионирование. Классический случай изобретения велосипеда в месте, где он не даёт преимущества.

### D. HTTP REST на localhost

**Минусы:** локальный TCP-порт — это дополнительная поверхность атаки, доступная любому процессу в системе. Named pipe с DACL строго безопаснее. Отвергнуто по соображениям ADR-006.

## Анализ компромиссов

**Сложность против возможностей.** JSON-RPC (B) на старте проще на день-два. Но стрим метрик, стрим логов и push-события failover — это три места, где пришлось бы городить своё. gRPC окупается уже на первой из них.

**Локальный порт против named pipe.** REST (D) удобнее отлаживать, но открывает канал управления привилегированной службой всем локальным процессам. С учётом прецедентов из RQ8 это неприемлемо.

## Последствия

**Становится проще:**
- Принцип P1 выполняется автоматически: `net-cli` — просто второй gRPC-клиент.
- Linux server edition получает готовый API-слой без переделки.
- GUI можно заменить целиком, не трогая службу.
- Схема в `.proto` служит документацией контракта.

**Становится сложнее:**
- Кодогенерация в сборочном конвейере.
- Нужен кастомный диалер gRPC поверх named pipe.
- Изменения контракта требуют дисциплины совместимости.

**Что придётся пересмотреть:**
- Если web UI для server edition потребует прямого доступа из браузера — понадобится gRPC-Web прокси или отдельный HTTP-фасад поверх того же контракта.

## Задачи

1. [ ] Определить `.proto`: сервисы, сообщения, единый поток событий
2. [ ] Диалер gRPC поверх named pipe (Windows) и UDS (Linux/macOS)
3. [ ] Политика версионирования и handshake с проверкой версии
4. [ ] Буферизация событий на стороне службы — чтобы события, произошедшие до подключения GUI, не терялись (важно для T7)
5. [ ] `net-cli` как эталонный потребитель контракта — пишется вместе с каждой функцией

## Дополнение от 26.08.2026: секреты не покидают службу

**Статус:** принято в И-4 при реализации мер S6 и S7.

### Что изменилось

1. **`Profile.password` передаётся только в сторону службы.** В ответах
   `List`, `Put` и `Import` поле всегда пустое. Вместо него служба заполняет
   `has_secrets` — признака достаточно, чтобы интерфейс показал «пароль
   задан», и недостаточно, чтобы пароль узнать.

2. **Пустой пароль в `Put` означает «оставить прежний».** Это прямое
   следствие пункта 1: клиент не видит секретов и потому не может прислать
   обратно то, чего не получал. Без такого правила переименование профиля
   стирало бы пароль — причём отказ проявился бы позже и выглядел бы никак
   не связанным с переименованием.

3. **Добавлен `Import`.** Разбор ссылок и файлов конфигурации выполняется
   службой.

4. **Перечисление `Kind` расширено** значениями `HYSTERIA2`, `WIREGUARD`,
   `AMNEZIAWG`, `VLESS`. Номера прежних значений не изменялись — правило
   аддитивности соблюдено.

### Почему разбор на стороне службы

- Секреты движутся в одну сторону: содержимое уходит в службу и не
  возвращается.
- Разбор — это недоверенный ввод, а по мере S3 всякая проверка выполняется
  службой, включая ввод собственного интерфейса.
- Форматов много. Разбор в каждом клиенте — `net-cli`, `net-gui`, будущий
  web UI — означал бы три расходящиеся реализации одного и того же.

### Что осталось незакрытым

Контракт по-прежнему передаёт лишь часть полей профиля: имя, адрес, порт, имя
пользователя, пароль. Ключи WireGuard, параметры обфускации и настройки TLS в
нём не выражены — такие профили создаются только импортом.

Отсюда правило слияния в `Put`: пришедшие поля накладываются на сохранённый
профиль, остальное сохраняется. Смена типа существующего профиля отвергается —
она меняет набор обязательных параметров, которых в контракте нет.

Поле-за-полем редактирование появится тогда, когда оно понадобится интерфейсу
(итерация И-5). Расширять контракт заранее, «на всякий случай», значит
фиксировать форму данных до того, как известно, как ею пользуются.

## Дополнение от 26.08.2026: режим работы в контракте

**Статус:** принято в И-5 вместе с режимом туннеля.

Добавлено перечисление `Mode` со значениями `MODE_PROXY` и `MODE_TUNNEL`, поле
`mode` в `ConnectRequest` и в `Status`.

### Почему режим входит и в состояние, а не только в запрос

«Подключено» означает разное в двух режимах. В режиме прокси через туннель
идут только приложения, направленные на локальный порт; в режиме туннеля — весь
трафик системы. Не показывать это различие значит скрывать от пользователя,
куда идёт его трафик, — а это ровно то, ради чего он поставил VPN-клиент.

По той же причине `net-cli status` печатает режим, а экран подключения
показывает его среди подробностей активного соединения.

### Почему MODE_UNSPECIFIED означает прокси

Клиент, собранный до появления режимов, поля не заполняет. Истолковать это как
ошибку значило бы сломать старых клиентов. Истолковать как туннель — молча
изменить маршрутизацию всей системы у тех, кто просил обычный прокси. Верно
только одно прочтение, и оно закреплено тестом.

Значение вне перечисления, напротив, отвергается: это уже не старый клиент, а
опечатка или несовместимая версия.

### Умолчания в интерфейсах

- **Экран подключения:** прокси. Туннель выбирается явно и сопровождается
  предупреждением о том, что меняется маршрутизация всей системы.
- **Быстрое подключение из трея:** прокси, без возможности выбрать туннель.
  Изменение маршрутизации всей системы одним нажатием в трее — это ровно тот
  случай, когда пользователь получает не то, о чём просил.
- **`net-cli connect`:** прокси; туннель через `-mode tunnel`. Опечатка в
  значении даёт отказ, а не молчаливый переход к прокси.

### Системный прокси

Третий режим из задания — системный прокси — не является отдельным способом
передачи трафика: это настройка Windows поверх режима «прокси». Он получит своё
значение перечисления в И-11.
